API Gateways & Service Mesh

Every request that crosses a service boundary needs someone to check who's calling, decide where it goes, and decide whether it goes at all — the only real question is whether that logic lives in one box at the edge, or rides along in a sidecar next to every single service.

01 Why this is an interview trap

Ask a mid-level engineer to distinguish an API gateway from a service mesh and you'll usually get a features list: "gateways do rate limiting and auth, meshes do mTLS and retries." That's not wrong, but it's not the distinction that matters — it's two products' marketing pages, not a mental model.

The distinction that actually matters is which traffic each one sits in front of. An API gateway is the single, client-facing edge for north–south traffic — browser, mobile app, third-party integration, all funneling through one controlled entrance before anything internal happens. A service mesh is infrastructure for east–west traffic — service calling service, entirely inside your perimeter, that the gateway saw once on the way in and then never sees again. Get that backward in an interview — say a mesh replaces your gateway, or that your gateway secures service-to-service calls three hops deep — and it reads as never having actually operated either.

The second, sharper trap: enthusiastically recommending a mesh because of what it can do, without pricing what it costs. A sidecar per pod is a second container, a second thing to patch on every CVE, and — for most teams — a Kubernetes-shaped commitment they didn't previously have. The strong interview answer is a cost model, not a feature list. The console below makes both traps concrete: watch the exact same failure play out with and without a mesh in the path.

02 One front desk, and a translator riding with every employee

A gateway is a single front desk at the one entrance everyone outside the building has to walk through. A service mesh is every employee inside getting their own translator/bodyguard who silently handles all of that employee's internal conversations — checking badges, deciding whether to knock again if a door doesn't answer, and logging who talked to whom.

One sentence predicts everything below: a gateway centralizes decisions the client-facing edge needs once; a mesh centralizes decisions every single internal hop needs, over and over, for the life of the system.

The real cost of a mesh is almost never the per-hop milliseconds — it's this fleet-wide operational surface, which is precisely what section 06 below turns into an interview answer.

04 How this shows up in systems you already use

  • Kong, Amazon API Gateway, Apigee, Envoy Gateway / Contour (Kubernetes Gateway API). All of them implement the exact four-part stack in today's console: terminate client auth, enforce a rate limit, pick a backend by path/host, and shape the request before it leaves the edge. This is the north–south layer, and it's the one almost every production system has, mesh or no mesh.
  • Istio is the reference service mesh: a control plane (istiod) that computes routing/policy/certificate state, pushed down to an Envoy sidecar injected into every pod. Envoy itself was built at Lyft specifically to solve the east–west problem before "service mesh" was even a term for it.
  • Linkerd deliberately did not reuse Envoy — it wrote its own minimal Rust data-plane proxy (linkerd2-proxy) specifically to undercut the sidecar's memory/CPU/startup-time tax. It's a direct, shipped answer to the "operational complexity" side of today's trade-off.
  • Istio's ambient mode and Cilium's eBPF-based mesh (both matured over 2023–2025) remove the per-pod sidecar container entirely, moving mTLS into a shared per-node proxy instead. This is the industry's own response to the exact resource-multiplier problem shown in the bench card above — worth naming unprompted as the state of the art moving specifically to answer "isn't the sidecar tax too high."
  • Netflix's Hystrix shipped circuit breaking as an in-process Java library years before service meshes existed, and their Zuul gateway did edge routing at massive scale before "API gateway" was a category name. Good grounding for the follow-up in section 06: you never strictly need a mesh to get retries and circuit breaking — a well-run shared library got there first.

05 Hands-on: build the edge, watch it centralize four decisions

A real, runnable gateway in stdlib Python — no framework, no external services. It fronts two backend stubs (order-service, payment-service) and, on every request, does the four things a gateway centralizes: authenticate once, rate-limit with a token bucket, route by path, and reshape the request before forwarding it.

gateway_demo.py
import http.server
import socketserver
import threading
import time
import json
import urllib.request
import urllib.error

# ---------------------------------------------------------------------
# 1. TOKEN BUCKET — the actual rate-limiting algorithm, O(1) per request
# ---------------------------------------------------------------------
class TokenBucket:
    def __init__(self, capacity, refill_rate):
        self.capacity = capacity
        self.tokens = float(capacity)
        self.refill_rate = refill_rate  # tokens added per second
        self.last = time.monotonic()
        self.lock = threading.Lock()

    def allow(self):
        with self.lock:
            now = time.monotonic()
            elapsed = now - self.last
            self.last = now
            self.tokens = min(self.capacity, self.tokens + elapsed * self.refill_rate)
            if self.tokens >= 1:
                self.tokens -= 1
                return True, self.tokens
            return False, self.tokens


BUCKETS = {}
BUCKETS_LOCK = threading.Lock()

def bucket_for(key):
    with BUCKETS_LOCK:
        if key not in BUCKETS:
            BUCKETS[key] = TokenBucket(capacity=5, refill_rate=2.0)  # burst 5, sustain 2 req/s
        return BUCKETS[key]


VALID_TOKENS = {"tok-orders-svc-client", "tok-admin"}

ROUTES = {
    "/orders": ("127.0.0.1", 9001),
    "/payments": ("127.0.0.1", 9002),
}


# ---------------------------------------------------------------------
# 2. THE GATEWAY — everything a client-facing edge centralizes
# ---------------------------------------------------------------------
class GatewayHandler(http.server.BaseHTTPRequestHandler):
    def log_message(self, fmt, *args):
        pass

    def do_GET(self):
        request_id = "req-%05d" % (int(time.time() * 1000) % 100000)

        # (a) AUTHN — centralized once, at the edge
        auth = self.headers.get("Authorization", "")
        token = auth.replace("Bearer ", "").strip()
        if token not in VALID_TOKENS:
            return self._respond(401, {"error": "unauthenticated", "request_id": request_id})

        # (b) RATE LIMITING — centralized, per API key, token-bucket
        bucket = bucket_for(token)
        allowed, remaining = bucket.allow()
        if not allowed:
            return self._respond(429, {
                "error": "rate_limited",
                "request_id": request_id,
                "tokens_remaining": round(remaining, 2),
            })

        # (c) ROUTING — path prefix decides which backend owns this request
        path = self.path.split("?")[0]
        backend = next((addr for prefix, addr in ROUTES.items() if path.startswith(prefix)), None)
        if backend is None:
            return self._respond(404, {"error": "no_route", "request_id": request_id})

        # (d) REQUEST SHAPING — strip the client's headers, inject trusted ones
        upstream_url = "http://%s:%d%s" % (backend[0], backend[1], path)
        req = urllib.request.Request(upstream_url, headers={
            "X-Request-Id": request_id,
            "X-Forwarded-For": self.client_address[0],
            "X-Gateway-Auth-Subject": token,   # backend trusts this, client can never set it directly
        })
        try:
            with urllib.request.urlopen(req, timeout=1.0) as resp:
                self._respond_raw(resp.status, resp.read())
        except urllib.error.URLError as e:
            self._respond(502, {"error": "upstream_unavailable", "detail": str(e)})

    def _respond(self, code, payload):
        self._respond_raw(code, json.dumps(payload).encode())

    def _respond_raw(self, code, body):
        self.send_response(code)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)


# ---------------------------------------------------------------------
# 3. TWO STUB BACKEND SERVICES — they never see a client directly,
#    only the gateway talks to them
# ---------------------------------------------------------------------
class BackendHandler(http.server.BaseHTTPRequestHandler):
    def log_message(self, fmt, *args):
        pass

    def do_GET(self):
        payload = json.dumps({
            "service": self.server.service_name,
            "request_id": self.headers.get("X-Request-Id"),
            "authenticated_subject": self.headers.get("X-Gateway-Auth-Subject"),
        }).encode()
        self.send_response(200)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(payload)))
        self.end_headers()
        self.wfile.write(payload)


def start_backend(port, name):
    httpd = socketserver.ThreadingTCPServer(("127.0.0.1", port), BackendHandler)
    httpd.service_name = name
    threading.Thread(target=httpd.serve_forever, daemon=True).start()
    return httpd

def start_gateway(port):
    httpd = socketserver.ThreadingTCPServer(("127.0.0.1", port), GatewayHandler)
    threading.Thread(target=httpd.serve_forever, daemon=True).start()
    return httpd

def call(path, token):
    headers = {"Authorization": "Bearer " + token} if token else {}
    req = urllib.request.Request("http://127.0.0.1:9000" + path, headers=headers)
    try:
        with urllib.request.urlopen(req, timeout=1.0) as resp:
            return resp.status, resp.read().decode()
    except urllib.error.HTTPError as e:
        return e.code, e.read().decode()


if __name__ == "__main__":
    start_backend(9001, "order-service")
    start_backend(9002, "payment-service")
    start_gateway(9000)
    time.sleep(0.3)

    print("=== 1. no token -> centralized auth rejects at the edge, backends never see it ===")
    print(call("/orders/42", None))

    print("\n=== 2. valid token, routed to order-service ===")
    print(call("/orders/42", "tok-orders-svc-client"))

    print("\n=== 3. same token, routed to payment-service (one gateway, two backends) ===")
    print(call("/payments/9", "tok-orders-svc-client"))

    print("\n=== 4. burst of 8 requests on a bucket sized capacity=5, refill=2/s ===")
    for i in range(8):
        status, body = call("/orders/1", "tok-admin")
        print("  req %d: %s  %s" % (i + 1, status, body))

    print("\n=== 5. sleep 1.5s (bucket refills ~3 tokens), burst again ===")
    time.sleep(1.5)
    for i in range(4):
        status, body = call("/orders/1", "tok-admin")
        print("  req %d: %s  %s" % (i + 1, status, body))

Notice run 4: exactly 5 requests through (the bucket's burst capacity), then hard 429s — and run 5 shows the refill math working, capacity=5 at 2 tokens/sec means 1.5s buys back ~3 tokens, and the log shows precisely 3 successes before the 4th trips the limiter again. That's the token bucket, not a fixed window — it's the same reason a gateway can allow a legitimate burst without allowing sustained abuse.

The exercise: give /payments its own, tighter bucket (capacity=2, refill_rate=0.5 — payment calls are expensive downstream, so throttle them harder) and confirm a burst against /payments starts 429-ing much sooner than the same burst against /orders. Then answer without running anything: this token bucket is O(1) time and O(1) space per client key. A sliding-window log limiter that stores every request timestamp instead is O(n) space per key and O(n) (or O(log n) with a sorted structure) to prune on each check. Given that, why do production gateways — Kong, Envoy's local_ratelimit, AWS API Gateway — default to token-bucket or a fixed/sliding-window-counter approximation instead of the exact sliding-window log?

06 The senior/staff framing

What separates a strong answer from a weak one

  • Weak: "We should adopt a service mesh because it gives you mTLS, retries, and observability for free." Strong: "None of that is free — it's traded for a second infrastructure layer, a control plane plus a sidecar per pod, that your platform team now owns and upgrades forever. A mesh earns that cost when you have enough independently-deployed services, across enough different teams, that keeping a shared retry/mTLS/auth-propagation client library in version lockstep has itself become the bottleneck. Below that point, a well-maintained shared library plus a gateway at the edge covers the same ground for a fraction of the operational surface."
  • Name the actual threshold, even loosely: teams that get real ROI from Istio/Linkerd are typically running dozens-to-hundreds of services across multiple independently-shipping teams, often with a compliance driver (mTLS-everywhere for something like PCI-DSS) layered on top — not five services owned by one team.
  • The killer follow-up: "Your platform team already gets retries and circuit breaking from a shared common-http-client library every service imports. What does a mesh actually buy you on top of that?" The honest answer is two things, and naming them precisely is what separates a strong candidate: polyglot-ness (the mesh's guarantees don't depend on every team using the same language or library version) and fleet-wide policy change without an application redeploy. If the org is single-language and the library is well-versioned, that gap is much smaller than the sales pitch implies — say so.
  • Show you know exactly where the two layers meet: a gateway can do retries and circuit breaking for the one hop it sees, client → edge. It has zero visibility into the 30 further service-to-service hops behind it. That specific blind spot, not a generic "resilience" story, is the actual gap a mesh closes.

08 Spaced recap

Resurfacing Lesson 18 — Microservices vs Monolith

Lesson 18 landed on a cost model: splitting into services is worth it when independent-team scaling outpaces the coordination cost of one shared codebase — not as a default architecture. Everything in today's lesson is the direct infrastructure bill that decision generates. A monolith gets auth, routing, and retries for free from in-process function calls and a single deploy; the moment you split, someone has to own those concerns again — once at the edge (the gateway) and on every pair of services internally (the mesh, or a shared library standing in for one). Which is exactly why adopting a mesh before you've actually paid microservices' coordination tax — before you have enough services, owned by enough teams — reproduces lesson 18's core mistake one layer down: buying distributed-systems complexity before anything actually forces you to.
