Observability

Which of the three signals your system emits actually answers a given production question, how a counter on a service becomes a rate() query in Prometheus, what a span really is under the hood — and why a single missing header can make a perfectly healthy request invisible to the tracing system built to explain it.

01 Why "we have logs" is not the answer

Ask a mid-level engineer "is your service observable" and you'll usually get: "yeah, we ship logs to Datadog." That's a monitoring answer, not an observability one, and the gap between them is exactly what a staff-level interviewer is listening for.

Monitoring is a fixed set of dashboards and alerts for failure modes you already anticipated — you decided in advance which questions matter and wired up graphs for them. Observability is the ability to ask a question you did not anticipate — "why are only Android 12 users on the EU shard seeing 3-second checkouts since 14:02?" — and answer it from the telemetry you already emit, without shipping new code first. Logs alone rarely get you there at any real scale: grepping years of unstructured text for a needle is either impossibly slow or impossibly expensive, and a single log line from one service tells you nothing about the four other services that request touched.

The precise, staff-bar version of the answer names three distinct signals, says exactly which question each one is structurally suited to answer, and knows where each one breaks down — a metric can't tell you which specific request was slow; a trace can't cheaply tell you the error rate across a billion requests; a log line from one service can't show you the other four hops a request took. Add to that: can you define an SLI as a precise ratio, not a vibe? Do you know why Prometheus falls over if you put a user ID in a label? Can you say what a traceparent header actually contains? Those are the four things this lesson is built around, and the console below will let one of them break in front of you.

02 One event, three witnesses

The same thing happening inside your system — "an order was created" — can be recorded three structurally different ways at the same instant. Each shape trades detail for cost differently, and that trade is the entire reason all three exist instead of just one.

The metric is a single integer bump against a small, fixed set of labels — cheap enough to store forever, but it can't tell you which specific order this was. The log is an arbitrarily detailed, arbitrarily unique event — it can carry the order ID, the user ID, the exact payload — but it costs real money to store and index at volume, and it says nothing about the other two services in the chain. The span carries exact timing and a parent pointer, which is the only one of the three that can answer "where, across four network hops, did the 300ms go." None of the three is a superset of the others; that's the whole reason a mature system runs all three at once.

how Prometheus turns a counter into a rate

Prometheus is a pull-based system: on a fixed interval (commonly 15s), the server scrapes plain-text /metrics HTTP endpoints on every target and stores exactly one sample per series per scrape into its local time-series database. A series is the metric name plus one unique combination of label values — http_requests_total{route="/checkout",status="200"} is one series; every distinct route/status pair is another. This is why rate() exists: a raw counter only ever goes up (and resets to 0 on restart, which rate() detects and compensates for), so you compute the requests-per-second signal by dividing the delta between two scrapes by the elapsed time.

raw counter samples every 15s : [0, 195, 446, 652, 880]
rate() output (req/s)         : [13.0, 16.73, 13.73, 15.2]
(same synthetic run as the hands-on script below)

Two things trip people up here. First: cardinality. Total stored series = metric name × the product of every label's distinct value count. Twenty routes × six status codes is 120 series — fine. Twenty routes × six status codes × five million user_id values is 600 million series, and that is how you OOM a Prometheus server; this is the structural reason metrics and logs are different tools, not a style preference. Second: histogram vs. summary. A Histogram exposes cumulative bucket counters (_bucket{le="0.3"}) — the client does O(1) work per observation, and the server computes any percentile later via histogram_quantile(), which linearly interpolates within the bucket that crosses the target and is therefore aggregatable across every pod. A Summary computes its quantiles client-side and streams out an already-final number — cheaper to query, but you cannot average two pods' p99s into a fleet-wide p99; you'd need to recompute from raw data. Reach for Histogram unless you have a specific reason not to.

defining an SLO, precisely

An SLI (indicator) is a ratio you can compute continuously: good events over valid events. An SLO (objective) is a target value for that ratio over a stated window — an internal number, distinct from an SLA, which is the external, usually looser, contractual promise with financial penalties attached. The gap between SLO and 100% is your error budget: the amount of "bad" you're explicitly allowed to spend on deploys, experiments, and plain bad luck before you stop shipping features and go fix reliability instead.

SLI  (indicator): good_events / valid_events, measured continuously
     e.g. requests where latency < 300ms  ÷  all requests, for route=/checkout

SLO  (objective):  SLI >= 99.9%  over a rolling 28-day window

error budget      = (1 - 0.999) x 28 days
                  = 0.1% x 40,320 minutes
                  = 40.3 minutes of "bad" allowed per 28 days

common budgets:
  99%    ("two nines")   ~= 7h 18m / month
  99.9%  ("three nines") ~= 43m     / month
  99.99% ("four nines")  ~= 4m 22s  / month

A naive alert — "page if error rate over the last 5 minutes exceeds 1%" — pages on a 90-second blip that costs almost nothing against a 28-day budget, and trains your on-call to ignore pages. The fix that shows up in the Google SRE workbook is multi-window, multi-burn-rate alerting: only page when the budget is being consumed fast enough, confirmed across two window lengths at once, so a short spike that self-heals doesn't fire and a slow leak still gets caught before the budget is gone.

burn rate 14.4x  over 1h  (confirm over 5m)   -> page    (exhausts 28d budget in ~2 days)
burn rate  6x    over 6h  (confirm over 30m)  -> page    (exhausts budget in ~5 days)
burn rate  1x    over 3d                      -> ticket  (exhausts budget exactly on schedule)

04 How this shows up in systems you already use

  • Prometheus + Grafana + Alertmanager. The dominant open-source metrics stack: Prometheus pulls and stores (default ~15 days local retention), Grafana renders PromQL, Alertmanager dedupes and routes alerts. For retention past two weeks or a global view across many Prometheus servers, teams add Thanos, Cortex, Mimir, or VictoriaMetrics on top via remote_write.
  • OpenTelemetry (OTel). The now-standard, vendor-neutral instrumentation layer: a language SDK generates spans/metrics/logs, and the OTel Collector — a separate deployable pipeline of receivers → processors → exporters — does batching, PII scrubbing, and sampling centrally instead of inside every service. Traces land in Jaeger, Tempo, Honeycomb, or a vendor APM (Datadog, New Relic).
  • W3C Trace Context is the propagation format the console above uses — the traceparent header (version-traceid-spanid-flags) — which replaced older vendor-specific formats like Zipkin's B3 headers or Datadog's x-datadog-trace-id as the interoperable default most SDKs speak out of the box.
  • Head-based vs. tail-based sampling. Head-based (decide at the root, before you know if the trace is interesting — OTel's default ParentBased(TraceIdRatioBased)) is cheap and simple but can miss the one slow outlier in ten thousand. Tail-based sampling buffers every span for a trace at the Collector and decides after seeing the whole thing — "always keep traces with an error or over 1s" — at the cost of buffering and needing every span for one trace routed to the same Collector instance.
  • Structured JSON logs → Loki / Elasticsearch / Datadog, with trace_id injected into every log line so a dashboard can jump straight from "this span was slow" to "here are the exact log lines emitted during it" — the correlation the hands-on script below builds by hand.
  • node_exporter / cAdvisor expose host and container CPU, memory, disk, and network stats in Prometheus format — the raw material for USE-method infrastructure dashboards.
  • Error budgets and burn-rate alerting were formalized in Google's SRE book and workbook and are now standard practice at Google, Netflix, Uber, and most large-scale shops: exhaust the budget and feature launches pause until reliability work brings it back.
  • eBPF-based auto-instrumentation (Grafana Beyla, Pixie, Odigos) is the emerging alternative to hand-instrumenting every service: it captures spans and metrics from kernel-level syscall/network hooks with zero code changes, at the cost of coarser control over what gets captured.

05 Hands-on: build the mechanism, not just the vocabulary

A minimal, dependency-free tracer that implements real W3C traceparent propagation, plus a Prometheus-style histogram with the actual percentile-estimation algorithm — the two mechanisms below are the real, complete functions; the sample output further down is illustrative, shaped by running the full version of this script (synthetic request generator, Span class, and bucket definitions included) rather than a transcript of only the fragments shown on this page.

tracer.py — the propagation mechanism
def start_span(name, incoming_headers=None):
    """
    incoming_headers is None   -> plain in-process child span; fall back to
                                   whatever span is 'current' via contextvars.
    incoming_headers is a dict -> this call just crossed a simulated network
                                   boundary. Trust ONLY the headers -- a real
                                   remote service has no access to this
                                   process's call stack. Missing/invalid
                                   header means: start a brand-new trace root.
    """
    if incoming_headers is not None:
        extracted = extract(incoming_headers)
        if extracted:
            trace_id, parent_span_id = extracted
        else:
            trace_id, parent_span_id = _rand_hex(16), None   # orphaned trace
    else:
        current = _trace_ctx.get()
        if current:
            trace_id, parent_span_id = current["trace_id"], current["span_id"]
        else:
            trace_id, parent_span_id = _rand_hex(16), None
    return _SpanCM(Span(name, trace_id, _rand_hex(8), parent_span_id))

def inject(headers: dict):
    """Write the current span onto an outgoing request as a real
    W3C traceparent: version-traceid-spanid-flags."""
    ctx = _trace_ctx.get()
    if ctx is None:
        return
    headers["traceparent"] = f"00-{ctx['trace_id']}-{ctx['span_id']}-01"

def extract(headers: dict):
    if not headers:
        return None
    parts = headers.get("traceparent", "").split("-")
    if len(parts) != 4:
        return None
    _version, trace_id, span_id, _flags = parts
    return trace_id, span_id
histogram.py — bucket-based percentile estimation
def histogram_quantile(hist, q: float):
    """Reimplementation of PromQL's histogram_quantile(): find the bucket
    whose cumulative count crosses q * total, then linearly interpolate
    within that bucket's range. O(number of buckets) per query -- an exact
    percentile from raw samples needs O(n log n) to sort, or a running
    reservoir; the histogram trades precision for that constant-time cost."""
    target = q * hist.count
    prev_bound, prev_count = 0.0, 0
    for b in hist.buckets:
        count = hist.bucket_counts[b]
        if count >= target:
            if b == float("inf"):
                return prev_bound
            if count == prev_count:
                continue
            frac = (target - prev_count) / (count - prev_count)
            return prev_bound + frac * (b - prev_bound)
        prev_bound, prev_count = b, count
    return hist.buckets[-2]

Look at 2b closely — this is the exact bug the console above visualizes. One dropped header and the single trace tree splits into two disconnected roots: payments.charge_card shows up as its own orphan trace, and gateway → orders looks like it called out into nothing. Nothing crashed, nothing logged an error, latency barely moved. The only symptom is a hole in your tracing UI — which is exactly why this class of bug survives in production for months.

Also note the histogram estimate: p95 came out 248ms against a true 225ms — a ~10% overestimate purely from bucket granularity. That gap is controllable: pick bucket boundaries clustered around your actual SLO threshold (0.3s in this lesson's examples) and the interpolation error shrinks right where you need precision most; leave the default buckets and you're most accurate exactly where you don't need to be.

06 The senior/staff framing

What separates a strong answer from a weak one

  • Weak: "We'll page if the error rate goes above 1%." Strong: "First I'd define the SLI precisely — good/valid ratio, for which route, over what window — pick the SLO from the latency threshold that actually maps to user pain (not an arbitrary round number), and then alert on burn rate against the resulting error budget with two confirming windows, not a single 5-minute threshold. A blip that self-heals in 90 seconds shouldn't page; a slow leak that will exhaust a month's budget in two days should page immediately."
  • The killer follow-up: "Your on-call got paged at 2am by a 5-minute error-rate alert for something that resolved in 90 seconds. Redesign the alerting so this doesn't happen again — without missing a real incident." The answer is multi-window, multi-burn-rate alerting: a fast, high-multiplier burn confirmed over both a short and a long window pages immediately (it's real and urgent); a slow, low-multiplier burn only tickets, because there's time to fix it before the budget runs out. A single-window threshold physically cannot distinguish these two shapes.
  • A second follow-up worth having ready: "Why can't you just put user_id as a Prometheus label and slice by user when something breaks?" Cardinality — every distinct label value combination is a separate stored series, and unbounded IDs turn a few hundred series into hundreds of millions. That's precisely the job a trace or a structured log does instead; naming which of the three tools fits which question, unprompted, is the tell of someone who has actually operated this stack rather than read about it.
  • Know the SLA/SLO/SLI distinction cold: SLI is the measurement, SLO is your internal target (with an error budget attached), SLA is the external contractual promise — usually looser than your SLO on purpose, so you breach your own target and fix it before you ever owe a customer a refund.

08 Spaced recap

Resurfacing Lesson 07 — Testing Strategy for Backend Systems

Lesson 07 was about drawing a hard line around what a test can actually prove: a known scenario, run against code you can read, before it ships. Observability is the same discipline pointed the other direction — metrics, logs, and traces tell you what an unknown scenario really did in production, against inputs and failure modes nobody wrote a test for. Put them next to each other and a useful habit falls out: treat your SLO as a test you didn't have to hand-write. It runs continuously, against real traffic, and a burn-rate alert is just that test's failure notification — arriving after the fact instead of in CI, but built from exactly the same instinct your Lesson 07 test suite was.
