System design fundamentals · Phase 2 · Lesson 23

Designing for Failure

The toolkit for surviving partial failure in a distributed system — circuit breakers, retries with backoff and jitter, idempotency keys, timeout budgets, bulkheads, and backpressure — and why reaching for only one of them is exactly how a five-minute blip becomes a four-hour outage.

01 Why this is an interview trap

Ask a mid-level engineer "how do you handle a flaky downstream dependency" and you'll usually get: "add retries." That answer is dangerous precisely because it's half right. Retries fix transient blips. Under sustained failure they don't just fail to help — they actively make things worse, because every caller retrying a struggling service multiplies load into it at the exact moment it has the least spare capacity to absorb more. You've built a self-inflicted denial-of-service attack on your own dependency, and you built it on purpose.

Retry storms are a documented, recurring cause of cascading outages across the industry — a struggling database gets a wave of retried queries, falls further behind, times out more requests, which triggers more retries, until the whole tier is saturated with work that will never complete. The real interview-level distinction is: retries handle transient failure and do nothing for sustained failure — something else has to decide when to stop trying. That something is a circuit breaker. And the moment you allow any retry at all, you've silently created a second, sharper problem: every write now has an at-least-once delivery semantic, which is undefined behavior without an idempotency key.

02 The breaker in the fuse box

A circuit breaker in your home's electrical panel doesn't repair a short circuit. It trips open, physically disconnecting the circuit, so the wiring stops trying to push current into a fault. Someone (or something) checks later whether it's safe to close again. Software circuit breakers do the identical job for network calls — tracking consecutive failures instead of amperes.

Notice what OPEN buys you: the failing call never happens. No socket, no thread, no wait for a timeout — state == "open" is an O(1) check that turns a multi-second network failure into a microsecond local exception. That's the entire mechanism the console below makes visible.

the math behind a retry storm

Blind retry-until-success turns an error rate p into an offered-load multiplier of roughly 1 / (1 - p) — every failed attempt just becomes another attempt, so total load forms a geometric series.

effective_load_multiplier(p) = 1 / (1 - p)     # retries continue until success, no cap

p = 0.10  →  1.11x    mildly degraded: retries barely register
p = 0.50  →  2.00x    struggling: retries roughly double the load hitting it
p = 0.90  →  10.0x    near-dead: retries add 10x load right when capacity is lowest
p = 0.99  →  100x     this is the arithmetic of a blip becoming a multi-hour outage

A circuit breaker isn't an optimization layered on top of retries — it's the thing that stops retries from being the mechanism that finishes off an already-struggling dependency. Tripping OPEN caps p's effect on load by refusing to convert local failures into remote attempts at all.

04 How this shows up in systems you already use

  • Netflix's Hystrix (2012, now largely superseded by resilience4j) is where the circuit-breaker-as-a-library pattern came from for microservices — and it's also the origin of the thread-pool-per-dependency bulkhead, so one slow dependency's threads can never starve threads serving unrelated requests in the same process.
  • AWS SDKs default to exponential backoff with jitter since Marc Brooker's 2015 AWS Architecture Blog post "Exponential Backoff And Jitter" — the "full jitter" formula in the code below (uniform(0, min(cap, base * 2**attempt))) is close to verbatim what boto3, the Java SDK, and the CLI all still use by default.
  • Stripe's Idempotency-Key header is the canonical production implementation of idempotency keys — a client-generated UUID sent with a POST /v1/charges request guarantees a retried request replays the original result instead of charging the card twice.
  • Envoy / Istio circuit breaking config (max_connections, max_pending_requests, max_requests per upstream cluster) plus outlier detection (ejecting a host after N consecutive 5xxs) implements circuit breaking and bulkheads as infrastructure config instead of application code — the same state machine, pushed down a layer.
  • gRPC deadline propagation is a timeout budget enforced across a whole call tree: each hop forwards the remaining deadline to the next hop instead of resetting a fresh timeout, which is exactly the split_budget idea below applied automatically at every RPC boundary.
  • HikariCP / PgBouncer connection pools act as bulkheads at the database layer — capping concurrent connections per service or tenant so one noisy caller can't exhaust the pool that every other caller also depends on.
  • Kafka consumer lag and reactive-streams backpressure (Project Reactor, RxJava) are pull-based, not push-based, specifically so a slow consumer signals its own capacity instead of an upstream producer flooding it with more than it can process.
  • AWS's cell-based architecture / shuffle sharding takes bulkheads to the infrastructure level: customers are partitioned across isolated "cells" so a bad shard, a bad customer's traffic pattern, or a bad deploy can only ever take down a fraction of the fleet, never all of it.

05 Hands-on: build the toolkit

All five mechanisms below are real, runnable Python — not pseudocode. Every operation is O(1) per request (a counter compare, a semaphore acquire, a dict lookup): that's the point. Protection has to be cheaper than the failure it guards against, or it's just a second way for the system to fall over.

failure_toolkit.py — circuit breaker (state machine + injectable clock)
import time

class CircuitOpenError(Exception):
    """Raised immediately when the breaker is OPEN -- no downstream call is made."""

class CircuitBreaker:
    def __init__(self, failure_threshold=5, reset_timeout=30.0,
                 half_open_max_calls=1, time_fn=time.monotonic):
        self.failure_threshold = failure_threshold
        self.reset_timeout = reset_timeout
        self.half_open_max_calls = half_open_max_calls
        self._time_fn = time_fn
        self._state = "closed"
        self._consecutive_failures = 0
        self._opened_at = None
        self._half_open_inflight = 0

    @property
    def state(self):
        # OPEN is a stored fact; HALF-OPEN is *derived* from elapsed time --
        # which is exactly why time_fn has to be injectable to test this at all.
        if self._state == "open" and self._time_fn() - self._opened_at >= self.reset_timeout:
            return "half-open"
        return self._state

    def call(self, fn, *args, **kwargs):
        current = self.state
        if current == "open":
            raise CircuitOpenError("breaker OPEN -- fast-failing, no network call made")
        if current == "half-open":
            if self._half_open_inflight >= self.half_open_max_calls:
                raise CircuitOpenError("half-open trial already in flight")
            self._half_open_inflight += 1
        try:
            result = fn(*args, **kwargs)
        except Exception:
            self._on_failure(current)
            raise
        else:
            self._on_success()
            return result
        finally:
            if current == "half-open":
                self._half_open_inflight -= 1

    def _on_success(self):
        self._consecutive_failures = 0
        self._state = "closed"
        self._opened_at = None

    def _on_failure(self, current):
        self._consecutive_failures += 1
        if current == "half-open" or self._consecutive_failures >= self.failure_threshold:
            self._state = "open"
            self._opened_at = self._time_fn()
failure_toolkit.py — retry with exponential backoff + full jitter
import random

def retry_with_backoff(fn, max_attempts=5, base=0.2, cap=8.0,
                        sleep_fn=time.sleep, rng=random):
    """AWS 'full jitter': sleep = uniform(0, min(cap, base * 2**attempt))."""
    for attempt_no in range(max_attempts):
        try:
            return fn()
        except Exception as e:
            if attempt_no == max_attempts - 1:
                raise
            ceiling = min(cap, base * (2 ** attempt_no))
            delay = rng.uniform(0, ceiling)
            sleep_fn(delay)
failure_toolkit.py — idempotency keys (safe retries, not just eventual retries)
class PaymentAPI:
    def __init__(self):
        self._idempotency_store = {}
        self.actual_charges_made = 0

    def charge(self, idempotency_key, amount_cents):
        if idempotency_key in self._idempotency_store:
            return self._idempotency_store[idempotency_key]   # replay, no side effect
        self.actual_charges_made += 1
        response = {"status": "charged", "amount_cents": amount_cents,
                     "charge_id": f"ch_{self.actual_charges_made}"}
        self._idempotency_store[idempotency_key] = response
        return response
failure_toolkit.py — timeout budget (shrinking per-attempt deadline)
def split_budget(total_budget_ms, max_attempts):
    remaining = total_budget_ms
    plan = []
    for i in range(max_attempts):
        attempts_left = max_attempts - i
        this_attempt = max(remaining // attempts_left, 1)
        plan.append(this_attempt)
        remaining -= this_attempt
    return plan
failure_toolkit.py — bulkhead (semaphore-isolated dependency pool)
import threading

class Bulkhead:
    def __init__(self, max_concurrent):
        self._sem = threading.Semaphore(max_concurrent)

    def call(self, fn, *args, **kwargs):
        if not self._sem.acquire(blocking=False):
            raise RuntimeError("bulkhead full -- rejected to protect the rest of the process")
        try:
            return fn(*args, **kwargs)
        finally:
            self._sem.release()

(For the second half: every one of those 280 seconds of requests is fast-failing locally with a perfectly flat, perfectly fast error response — no timeout spike, no latency spike, nothing that looks like the outage that caused it. The breaker is now the thing serving wrong answers, and it looks nothing like an incident on a standard dashboard.)

06 The senior/staff framing

What separates a strong answer from a weak one

  • Weak: "I'd add retries with exponential backoff so failed requests eventually succeed." Strong: "Retries alone only help transient failures, and without a circuit breaker they amplify sustained ones. Every retried write needs an idempotency key or I've turned a network blip into a double-charge bug. Timeouts need to be a budget across the whole call chain, not a default per-hop value. And whatever protects this dependency needs a bulkhead so its failure can't exhaust the thread or connection pool that unrelated endpoints in this same process also depend on."
  • The killer follow-up: "Your circuit breaker just tripped OPEN for the payments-service dependency. What should the 200 requests already queued behind it do, and what should the caller three hops upstream actually see?" The naive answer lets them all time out naturally — slow, wasteful, and it just relocates the outage one hop up. The strong answer: drain the queue immediately with a typed, fast "dependency unavailable" error instead of a generic timeout, so upstream code can distinguish "definitely failed, don't wait" from "still might succeed" — and so the failure doesn't silently re-manifest as a mysterious timeout three services away.
  • The fix worth naming: consistent jitter is what stops synchronized retries — if every caller computes backoff from the same clock tick with no randomness, they all retry in lockstep and you get periodic load spikes instead of smooth degradation. "Full jitter" (uniform random from zero, not just +/- a percentage) is the AWS-recommended default for exactly this reason.
  • Know which problem each mechanism actually solves, because interviewers expect you to name it precisely: circuit breakers protect the caller from a known-bad dependency; bulkheads protect the caller's other work from that same dependency; retries only help failures that are actually transient; idempotency keys are what make retrying a write safe in the first place. Treating these as interchangeable "resilience patterns" instead of four answers to four different questions is the single most common way this topic loses points at the staff bar.

08 Spaced recap

From lesson 22 — Consensus Basics (Raft/Paxos)

Lesson 22 covered how a cluster of replicas agrees on one true sequence of operations even when some nodes crash or the network partitions — consensus assumes a majority of participants are honest and reachable, and produces a single authoritative answer. Today's toolkit is the client-side mirror of that problem: it assumes no such luxury. Any single dependency you call might simply be gone, and your job is to keep the rest of the system alive without waiting to find out why. The two ideas touch in one concrete place worth remembering for interviews: a Raft leader's election timeout and heartbeat loop is structurally the same "assume failure, then periodically re-test the assumption" state machine as a circuit breaker's reset_timeout. If you're ever asked to design a system that both replicates its own state via Raft and calls external dependencies, expect to defend both halves separately — consensus governs agreement inside your own cluster; this lesson's toolkit governs everything outside it that isn't playing by Raft's rules.
