Design a Payments System

A full structured interview walkthrough built around the three ideas that actually separate a passing answer from a failing one: an idempotency key that survives a retry, a double-entry ledger that can't silently lose money, and a precise answer to exactly where in the stack you're paying for strong consistency.

01 Why this interview goes wrong fast

Most "design a payment system" interviews go off the rails in the first five minutes, when a candidate reaches for the same toolbox they'd use for a news feed or a URL shortener: shard by user ID, cache aggressively, "we'll reconcile eventual consistency later." That instinct is exactly backwards on the one path that matters — the write path that moves money — and a staff-level interviewer will notice within two sentences.

Here's the trap in one concrete sentence: if an account balance is a mutable column and you write it read-then-write (SELECT balance ... then UPDATE ... SET balance = balance - 100), two concurrent requests can both read 1000, both compute 900, and both write 900 — one $100 debit vanishes even though the customer was charged twice downstream. That's the textbook lost-update anomaly, and it happens by default under READ COMMITTED, which is the default isolation level in both Postgres and MySQL. "Just use a database" is not itself a consistency guarantee.

Three ideas do almost all the work in a strong answer, and they compound: an idempotency key so a network-level retry can never turn into a second charge, a double-entry ledger so "how much money exists" is a checkable invariant instead of a number you trust, and a precise line drawn between where the system is strongly consistent and where it's allowed to be eventually consistent — because the honest answer is never "everywhere" or "nowhere." This lesson walks all three all the way down to running code.

02 Two ideas, one mental model: a gate and a ledger

Hold two pictures in your head at once. An idempotency key is a gate that lets a given request's effect happen exactly once, no matter how many times the request itself arrives. A double-entry ledger is a bookkeeping rule that makes "money appeared from nowhere" a structurally impossible state, not just an unlikely one.

The gate matters because networks lie. A client that gets no response after 30 seconds has learned nothing about whether the charge actually happened — the request could have succeeded and the acknowledgement got lost on the way back, or it could have never arrived at all. Those two situations are indistinguishable from where the client is standing, which is exactly why "just don't retry on timeout" isn't a real answer either: it trades duplicate charges for silently abandoned payments, which is worse.

The ledger matters for a different reason: it turns "is the money right" from a question you hope is true into an invariant you can check. Every posting is a set of legs — one account debited, one or more credited — and the legs for a single transaction must sum to zero. Sum every leg ever posted, across every account, and the grand total is always zero too. If it isn't, you don't have a rounding error; you have a bug that is actively fabricating or destroying money, and you find out from an assertion instead of from a support ticket three weeks later.

The "idem-key row" lane in the correct scenarios isn't a cache-based optimization sitting off to the side — it's a row in the same database as the ledger, with a UNIQUE constraint on the key column. That constraint is what actually prevents the duplicate: request B's INSERT doesn't get skipped by clever application logic, it fails at the database level, deterministically, even if two application servers run the identical code at the identical nanosecond. Section 5 builds exactly that mechanism in real Python and runs it under real thread contention.

04 How real payment systems build this

  • Stripe's Idempotency-Key header and PayPal's PayPal-Request-Id are the client-facing version of exactly the gate above: the server stores the key alongside a hash of the request body and the full response, and replays that stored response byte-for-byte on any retry that reuses the key — Stripe documents the key as valid for roughly 24 hours, after which it can be safely reused for a new request.
  • Real ledgers are never a mutable balance column. Banking cores (Thought Machine Vault, Mambu), Uber's internal ledger service, and open-source ledger engines like Formance and the Medici library for Node all model money movement as immutable, balanced journal entries across accounts — a "balance" is a derived read, never a field you UPDATE in place.
  • The ledger write path runs on strongly consistent storage on purpose. A single-region relational database under SERIALIZABLE isolation (or row locks via SELECT ... FOR UPDATE) is the common choice; distributed-strong-consistency stores like Google Spanner or CockroachDB exist specifically so a globally distributed ledger can still answer "who has the money right now" with one correct current answer instead of a per-region guess.
  • AWS QLDB and similar systems make the accounting discipline explicit at the storage layer: append-only, cryptographically verifiable journals where you never delete or mutate an entry — you post a reversing entry, exactly the way a human accountant corrects a mistake.
  • Cross-organization money movement is a manual, days-long two-phase commit. Card authorization → capture → settlement → clearing between the issuing bank, the network, and the acquiring bank is functionally a distributed transaction that no engineering team controls end-to-end, which is why internal systems favor the Saga pattern — a sequence of local transactions plus compensating "reverse the entry" transactions — over trying to hold a lock across a boundary that can be down for hours.
  • The exact same problem, one layer down the stack: Kafka's idempotent producer assigns every producer a PID and a per-partition sequence number so a retried, at-least-once network send never gets appended to the log twice. It's the identical "unique key plus at-most-once effect" idea as a payments API's idempotency key, just enforced by the broker instead of the database.

05 Hands-on: build the idempotency guard and the ledger

Real, runnable Python — an unsafe check-then-insert processor next to a safe atomic-claim processor, both posting to a shared double-entry ledger, then hit with eight concurrent "retries" of the same logical payment on the same idempotency key.

payments_demo.py
"""
Idempotency-key guard + double-entry ledger, unsafe vs safe.
Run directly: fires 8 concurrent retries of the same logical payment.
"""
import threading
import time
import uuid

# ---------------------------------------------------------------- ledger --

class UnbalancedEntryError(Exception):
    pass

class Ledger:
    """Append-only double-entry ledger. Every post() must net to zero."""
    def __init__(self):
        self._entries = []
        self._lock = threading.Lock()

    def post(self, txn_id, legs):
        # legs: list of (account, signed_amount_cents)
        total = sum(amount for _, amount in legs)
        if total != 0:
            raise UnbalancedEntryError(f"txn {txn_id} legs sum to {total}, not 0")
        with self._lock:
            for account, amount in legs:
                self._entries.append({"txn_id": txn_id, "account": account, "amount": amount})

    def balance(self, account):
        return sum(e["amount"] for e in self._entries if e["account"] == account)

    def entry_count_for(self, txn_prefix):
        return sum(1 for e in self._entries if e["txn_id"].startswith(txn_prefix))


# ------------------------------------------------------- idempotency: unsafe --

def process_payment_unsafe(store, ledger, idem_key, payer, payee, amount_cents):
    """BUGGY: check-then-insert with a gap. Mirrors two separate DB round
    trips: 'SELECT ... WHERE idempotency_key = ?' then, later, 'INSERT ...'.
    """
    existing = store.get(idem_key)
    if existing is not None:
        return existing, "replayed"

    # the race window: in real systems this is two network round trips to
    # the database, not one line of Python. Widened on purpose so the race
    # is reliable to observe instead of a rare heisenbug.
    time.sleep(0.01)

    txn_id = f"{idem_key}-{uuid.uuid4().hex[:6]}"
    ledger.post(txn_id, [(payer, -amount_cents), (payee, amount_cents)])
    response = {"status": "succeeded", "txn_id": txn_id}
    store[idem_key] = response
    return response, "processed"


# --------------------------------------------------------- idempotency: safe --

class SafeIdempotencyStore:
    """Stand-in for: idempotency_key UNIQUE NOT NULL, status TEXT,
    response_json JSONB. 'Insert if absent' is atomic because a real
    unique index makes a second INSERT fail immediately -- it never gets
    to read a half-written row."""
    def __init__(self):
        self._records = {}
        self._table_lock = threading.Lock()  # models the unique-index check+insert as atomic

    def claim_or_wait(self, idem_key, payload_hash):
        with self._table_lock:
            record = self._records.get(idem_key)
            if record is None:
                record = {
                    "status": "pending",
                    "payload_hash": payload_hash,
                    "done": threading.Event(),
                    "response": None,
                }
                self._records[idem_key] = record
                return record, True  # True == you are the owner, do the work

        # Someone else owns this key. Reject if the payload doesn't match
        # (a client reusing the same key for a different request body).
        if record["payload_hash"] != payload_hash:
            return record, "conflict"
        return record, False  # False == wait for the owner, then replay

    def complete(self, record, response):
        record["response"] = response
        record["status"] = "completed"
        record["done"].set()


def process_payment_safe(store, ledger, idem_key, payer, payee, amount_cents, payload_hash="v1"):
    record, role = store.claim_or_wait(idem_key, payload_hash)

    if role == "conflict":
        return {"error": "idempotency key reused with a different request body"}, "conflict"

    if role is False:
        record["done"].wait(timeout=5)
        return record["response"], "replayed"

    # role is True: we hold the (simulated) unique-index row. Do the work.
    txn_id = f"{idem_key}-{uuid.uuid4().hex[:6]}"
    ledger.post(txn_id, [(payer, -amount_cents), (payee, amount_cents)])
    response = {"status": "succeeded", "txn_id": txn_id}
    store.complete(record, response)
    return response, "processed"


# ------------------------------------------------------------------- demo --

def run_concurrent(fn, n_threads, *args):
    outcomes = []
    lock = threading.Lock()
    def worker():
        _, outcome = fn(*args)
        with lock:
            outcomes.append(outcome)
    threads = [threading.Thread(target=worker) for _ in range(n_threads)]
    for t in threads: t.start()
    for t in threads: t.join()
    return outcomes


if __name__ == "__main__":
    N = 8  # 8 concurrent retries of the same logical payment, same idempotency key

    print("=== unsafe: check-then-insert, no atomicity, no lock ===")
    unsafe_store = {}
    unsafe_ledger = Ledger()
    outcomes = run_concurrent(process_payment_unsafe, N, unsafe_store, unsafe_ledger,
                               "idem-unsafe-1", "wallet:alice", "wallet:bob", 5000)
    print("outcomes:", outcomes)
    print("ledger entries for this txn key:", unsafe_ledger.entry_count_for("idem-unsafe-1"))
    print("alice balance:", unsafe_ledger.balance("wallet:alice"), "cents  (expected -5000)")
    print("bob   balance:", unsafe_ledger.balance("wallet:bob"), "cents  (expected +5000)")

    print()
    print("=== safe: atomic claim + wait-for-owner ===")
    safe_store = SafeIdempotencyStore()
    safe_ledger = Ledger()
    outcomes = run_concurrent(process_payment_safe, N, safe_store, safe_ledger,
                               "idem-safe-1", "wallet:alice", "wallet:bob", 5000)
    print("outcomes:", outcomes)
    print("ledger entries for this txn key:", safe_ledger.entry_count_for("idem-safe-1"))
    print("alice balance:", safe_ledger.balance("wallet:alice"), "cents  (expected exactly -5000)")
    print("bob   balance:", safe_ledger.balance("wallet:bob"), "cents  (expected exactly +5000)")

    print()
    print("=== safe: same key, DIFFERENT payload (client bug or attempted fraud) ===")
    conflict_store = SafeIdempotencyStore()
    conflict_ledger = Ledger()
    r1, o1 = process_payment_safe(conflict_store, conflict_ledger, "idem-conflict-1",
                                   "wallet:alice", "wallet:bob", 5000, payload_hash="v1")
    r2, o2 = process_payment_safe(conflict_store, conflict_ledger, "idem-conflict-1",
                                   "wallet:alice", "wallet:bob", 999999, payload_hash="v2")
    print("first request  ->", o1, r1)
    print("second request ->", o2, r2)

    print()
    print("=== ledger invariant check: try to post an unbalanced entry ===")
    try:
        Ledger().post("bad-txn", [("wallet:alice", -5000), ("wallet:bob", 4000)])
    except UnbalancedEntryError as e:
        print("rejected as expected:", e)

Read the unsafe block again. All 8 threads see existing is None before any of them finishes inserting — every single one processes. That's not a rare race, it's the default outcome once the check-then-insert gap is wide enough to matter, and Alice is out ₹400 instead of ₹50. The safe version funnels all 8 through one atomic claim: exactly one thread gets "processed", the other 7 get "replayed", and the ledger balance is exact to the cent.

The exercise — before you scroll back up, find the "DIFFERENT payload" block in the output and answer: was the second request processed, replayed, or rejected, and which of those three outcomes would you actually want in production?

Rejected, correctly. process_payment_safe compares a hash of the request body against the hash stored with the key on its very first use, and returns a conflict instead of either silently charging the new amount or silently handing back a receipt for a request the client never actually sent this way. That's the same rule Stripe and Razorpay enforce in production: an idempotency key is scoped to one exact request body, not to a transaction "intent" that's free to drift between retries.

One thing the demo hides: Ledger.balance() is O(n) in the number of entries for that account — fine here, not fine for an account with 50,000 postings. Real ledgers keep periodic balance snapshots (checkpoint the running balance as of entry #N, then sum only what's posted after N) so a balance read stays roughly O(1) amortized, at the cost of one more thing — the snapshot — that now has to stay consistent with the entries themselves.

06 The senior/staff framing

What separates a strong answer from a weak one

  • Weak: "I'd use a message queue for the payment flow and reconcile eventually consistent state afterward." Strong: "The idempotency-key insert and the ledger-leg inserts happen inside one ACID transaction, in one database, guarded by a UNIQUE constraint — not an application-level if check and not a Redis SETNX. Everything downstream of 'money has moved' — receipt emails, fraud scoring, analytics — fans out asynchronously afterward through an outbox table or CDC, because those can tolerate eventual consistency. The ledger write cannot."
  • The killer follow-up: "Your idempotency-key cache and your ledger database are two different pieces of infrastructure that can fail independently. Redis says a key is 'pending,' but Postgres just failed over and lost the last two seconds of transactions before the retry arrives — walk me through exactly what the retried request does." The trap is candidates who put the idempotency key in a fast cache in front of a slower database because it feels like the scalable choice. The moment those two stores can disagree about whether a charge happened, you've reintroduced the exact bug idempotency keys exist to remove — just moved one layer down. The fix worth naming: the idempotency table lives in the same database and the same transaction as the ledger rows; a cache in front of it is a latency optimization for reads, never the source of truth for whether a charge happened.
  • Isolation-level specificity is a real signal. Name SERIALIZABLE, or SELECT ... FOR UPDATE, or the unique constraint, explicitly — and be ready to explain why READ COMMITTED, the default in both Postgres and MySQL, silently allows the lost-update anomaly from Section 1. "I'd just wrap it in a transaction" without naming the isolation level is the same tell as "I'd add a cache" without naming an eviction policy.
  • Know where strong consistency stops. The ledger write itself needs it; the read replica your support dashboard queries doesn't. Routing every read in the system through the primary "to be safe" is how a team turns a few-hundred-TPS ledger into the bottleneck for a tens-of-thousands-TPS read-heavy support tool.

08 Spaced recap

From lesson 23: designing for failure

Lesson 23's toolkit — circuit breakers, retries with backoff and jitter, idempotency keys, timeout budgets, bulkheads — treated idempotency keys as one tool among five, useful mainly so a retried request can't double-execute some side effect. Today pointed that exact same tool at the one system where "double-executed side effect" has a currency symbol in front of it: the mechanism is identical — a unique key, a stored response, a safe replay path — the stakes are just an order of magnitude higher. That's precisely why interviewers save the payments question for the round where they want to see whether the idea actually generalizes under pressure, not just recite back in the shape it was first taught.
