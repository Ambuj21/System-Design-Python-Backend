Applied system design in Python · Phase 3 · Lesson 24

Build a Rate Limiter in Python

Two algorithms, from scratch, with real burst behavior you can run: a token bucket and a sliding-window log — the two ends of Lesson 20's trade-off table, turned into locked, tested, breakable code.

01 "I know the algorithm" isn't the bar

Every mid-level candidate can say "token bucket allows bursts, sliding window is more precise." That sentence is a vocabulary check, not a systems-design signal. The actual bar at senior/staff level is: can you write the fifteen lines that implement it correctly, and can you name the two ways those fifteen lines quietly break in production?

The two failure modes aren't exotic. One is a boundary-condition bug: get the eviction comparison in a sliding window backwards by a single character (<= instead of <) and you double-count a request sitting exactly on the window edge. The other is a concurrency bug: "check if a token is available, then take it" is two separate operations, and if two requests race between the check and the take, both can pass when only one token existed. Neither shows up in a single-threaded demo. Both show up in week one of production traffic.

Everything below — the diagrams, the interactive console, the code — is built from two Python classes that actually exist and actually ran on this machine, including a real reproduction of that race condition. Nothing here is simulated data dressed up to look like a measurement.

02 A bucket you fill, a log you trim

Both algorithms answer the same question — "has this key made too many requests?" — by tracking completely different state.

Both structures answer "allow or reject" in well under a microsecond. The difference only shows up in how they remember the past — one forgets continuously, one forgets in discrete jumps. That distinction is what the interactive console demonstrates next.

04 Where these two algorithms actually run

  • AWS API Gateway throttling is literally documented as "burst limit" and "rate limit" per key — that's a token bucket by name: burst limit is the bucket's capacity, rate limit is the refill rate. If you've ever hit a 429 after a spike that then recovered within seconds, you were watching a token bucket refill.
  • nginx's limit_req module implements a leaky bucket, not a token bucket — a genuinely different mechanism worth distinguishing in an interview. Token bucket meters admission but lets accepted requests through instantly, in a burst; leaky bucket queues requests and drains them at a constant output rate, actively smoothing traffic before it hits an upstream. Reach for leaky bucket when you need to protect a downstream that can't absorb bursts at all; reach for token bucket when the client experience of an occasional burst is fine.
  • GitHub's REST API rate limit resets on a fixed hourly clock boundary (the X-RateLimit-Reset header) — a fixed window, the simplest and crudest of the four classic algorithms. Its well-known flaw: a client can burn its full quota in the last second of one window and its full quota again in the first second of the next, getting up to 2x the intended rate in a short straddle around the boundary. Naming this flaw unprompted is a strong signal.
  • Stripe's public engineering writeup on API rate limiting describes exactly this build: token-bucket-style limiters backed by Redis, with the check-and-decrement made atomic via a Lua script executed inside Redis itself — the distributed version of the lock in the code below.
  • Envoy and Kong's rate-limit filters, and Redis's own redis-cell module, implement GCRA (the Generic Cell Rate Algorithm) — mathematically equivalent to token bucket, but storing a single "theoretical arrival time" value per key instead of a token count, which makes it cheaper to keep atomic in a single Redis command.
  • At very high request volumes, most edge/CDN-scale limiters skip the exact sliding-window log entirely and use a sliding-window counter — two fixed-window counters blended by a weighted estimate — trading a small, bounded amount of accuracy (up to ~2x burst in the worst case) for O(1) memory per key instead of O(requests-in-window). You'll meet this approximation explicitly in the hands-on exercise below.

05 Hands-on: build both, then break both

Full working code below — every output block on this page is the real result of running it on this machine (CPython 3.10.12), not a mocked-up transcript.

rate_limiters.py
import threading
import time
from collections import deque


class TokenBucket:
    """Allows bursts up to `capacity`, then throttles to `refill_rate` tokens/sec.

    Tokens accrue continuously and refill is computed lazily on each call
    from elapsed wall-clock time, so the bucket needs no background
    thread or timer.
    """

    def __init__(self, capacity: float, refill_rate: float, clock=time.monotonic):
        self.capacity = capacity
        self.refill_rate = refill_rate   # tokens per second
        self._tokens = capacity          # buckets start full
        self._clock = clock
        self._last_refill = clock()
        self._lock = threading.Lock()

    def _refill_locked(self) -> None:
        now = self._clock()
        elapsed = now - self._last_refill
        if elapsed > 0:
            self._tokens = min(self.capacity, self._tokens + elapsed * self.refill_rate)
            self._last_refill = now

    def allow(self, cost: float = 1.0) -> bool:
        with self._lock:
            self._refill_locked()
            if self._tokens >= cost:
                self._tokens -= cost
                return True
            return False

    @property
    def tokens(self) -> float:
        with self._lock:
            self._refill_locked()
            return self._tokens


class SlidingWindowLog:
    """Exact rate limiting: at most `limit` requests in any trailing `window_seconds`.

    Keeps a timestamp log of *accepted* requests only. Eviction is strict
    (`timestamp <= cutoff` is stale) so a request exactly window_seconds
    old no longer counts -- get this comparison backwards and you
    double-count the boundary millisecond under sustained load.
    """

    def __init__(self, limit: int, window_seconds: float, clock=time.monotonic):
        self.limit = limit
        self.window = window_seconds
        self._log = deque()
        self._clock = clock
        self._lock = threading.Lock()

    def _evict_locked(self, now: float) -> None:
        cutoff = now - self.window
        while self._log and self._log[0] <= cutoff:
            self._log.popleft()

    def allow(self) -> bool:
        with self._lock:
            now = self._clock()
            self._evict_locked(now)
            if len(self._log) < self.limit:
                self._log.append(now)
                return True
            return False

    @property
    def count(self) -> int:
        with self._lock:
            self._evict_locked(self._clock())
            return len(self._log)

Note the eviction uses a strict <= to drop entries and a strict < to admit — that pairing is deliberate. A timestamp exactly window_seconds old is dropped, not kept; a log with exactly limit entries admits nothing new. Flip either one and the boundary millisecond gets double-counted.

Both classes take an injectable clock callable instead of calling time.monotonic() directly — that one parameter is what makes the tests below deterministic instead of full of real time.sleep() calls and flaky timing assertions.

Read the last four rows again. Both limiters reject the same first burst past 5. But by t=6.0, token bucket has quietly refilled to full (5 idle seconds × 1 tok/s = 5 tokens) and accepts the whole second burst — while sliding window log is still holding all five t=0.x timestamps, because none of them are 10 seconds old yet, so it rejects every request in the second burst. Same starting capacity, same input, genuinely different outputs. That gap is the entire algorithmic trade-off, not a rounding difference.

test_rate_limiters.py — burst behavior, asserted
from rate_limiters import TokenBucket, SlidingWindowLog

class FakeClock:
    def __init__(self, t=0.0): self.t = t
    def __call__(self): return self.t
    def advance(self, dt): self.t += dt


def test_token_bucket_absorbs_a_burst_up_to_capacity():
    clock = FakeClock()
    bucket = TokenBucket(capacity=5, refill_rate=1.0, clock=clock)
    results = [bucket.allow() for _ in range(8)]   # 8 requests, same instant
    assert results == [True, True, True, True, True, False, False, False]
    assert bucket.tokens == 0

def test_sliding_window_log_does_not_partially_recover_within_the_window():
    clock = FakeClock()
    log = SlidingWindowLog(limit=5, window_seconds=10.0, clock=clock)
    for _ in range(5): assert log.allow()
    clock.advance(6.0)          # still well inside the 10s window
    assert not log.allow()      # unlike token bucket, waiting buys nothing yet
    assert log.count == 5

def test_boundary_is_exclusive_not_inclusive():
    clock = FakeClock()
    log = SlidingWindowLog(limit=1, window_seconds=10.0, clock=clock)
    assert log.allow()          # t=0
    clock.advance(10.0)         # entry is now exactly 10.0s old
    assert log.count == 0       # must already be evicted, not still counted
    assert log.allow()          # slot is free again

test_concurrency.py — the bug the single-threaded tests can't catch
class UnsafeTokenBucket:
    """Same accounting, but the check and the decrement are two
    separate, un-locked steps -- a classic check-then-act race."""
    def __init__(self, capacity):
        self.capacity = capacity
        self.tokens = capacity

    def allow(self, cost=1.0):
        if self.tokens >= cost:
            time.sleep(0)          # widen the gap between check and write
            self.tokens -= cost
            return True
        return False

def hammer(allow_fn, n_workers=50):
    results = []
    threads = [threading.Thread(target=lambda: results.append(allow_fn())) for _ in range(n_workers)]
    for t in threads: t.start()
    for t in threads: t.join()
    return sum(results)

sys.setswitchinterval(0.0001)   # force frequent GIL hand-offs to widen the race window
print(hammer(TokenBucket(capacity=10, refill_rate=0.0).allow))     # locked
print(hammer(UnsafeTokenBucket(capacity=10).allow))                # unlocked

The locked version is exactly correct on every run: 10 accepted, 40 rejected, no exceptions. The unsafe version over-admitted on 16 of 20 trials — not occasionally, usually. The exact counts will vary if you re-run this yourself (it's a real race, not a scripted number), but the over-admission itself reproduces reliably. This is the same bytecode-boundary hand-off from Lesson 01's GIL model: if self.tokens >= cost and self.tokens -= cost are separate bytecode ops, and sys.setswitchinterval(0.0001) just makes it easy to catch a thread getting swapped out in the gap between them. A single un-locked Lock() in the real class closes that gap completely — that's the entire fix.

06 The senior/staff framing

What separates a strong answer from a weak one

  • Weak: "Token bucket and sliding window log both rate-limit, pick either one." Strong: "Token bucket is O(1) memory per key and smooths bursts continuously — the right default for API quotas where an occasional burst is fine. Sliding window log is exact but O(active-requests-in-window) memory per key — I'd reach for it only where the exactness is worth paying for, like a security-sensitive action throttle, and at real scale I'd use the sliding-window-counter approximation instead to get back to O(1) memory."
  • The killer follow-up: "This has to enforce one limit per API key across 50 stateless app servers behind a load balancer. Where does the state live, and what breaks?" The state can't stay in-process anymore — it has to move to a shared store like Redis. That resurrects the exact check-then-act race from the concurrency test above, except now it's a race across machines, not threads, so a language-level Lock() can't fix it. The real fix is pushing the check-and-decrement into a single atomic operation on the store itself — a Lua script executed inside Redis, or redis-cell's built-in GCRA command — so the read-modify-write happens as one indivisible step on the server holding the data.
  • Worth naming unprompted: paying a network round-trip to Redis on every single request is real added latency on the hot path. Production systems at scale often run a hybrid — a fast, approximate local token bucket per app server for the common case, periodically reconciled against the authoritative global count in Redis — accepting a small, bounded amount of over-admission in exchange for not hitting the network on every request.
  • Know the memory-scaling axis cold: token bucket costs two numbers per key regardless of traffic volume. Sliding window log costs one timestamp per request currently inside the window — at high per-key limits and high key cardinality, that difference is the reason nobody runs an exact log at CDN edge scale.

07 Check your understanding

Before you move on

Your team runs SlidingWindowLog(limit=1000, window_seconds=60) per API key, backed by a single Redis instance, for 2,000,000 active keys during peak traffic. Each logged timestamp costs roughly 80–100 bytes of real Redis memory once sorted-set overhead is counted (not the 8 bytes you'd guess from "it's just a float") — that figure is a commonly-cited ballpark for Redis's per-member skip-list overhead, not something measured on this page, so sanity-check it yourself before relying on it.

Back-of-envelope the worst-case memory footprint. Given that number, what would you actually change about the implementation to run on a tenth of that memory — without simply switching to a naive fixed window and reintroducing the boundary-burst problem?

Resurfacing Lesson 20 — Rate Limiting Algorithms

Lesson 20 laid out the whiteboard-level family — fixed window, sliding window (log and counter), token bucket, leaky bucket — and the trade-off table between them: burst tolerance, memory cost, and accuracy at the window boundary. TokenBucket and SlidingWindowLog above sit at the two opposite ends of it, and the two bugs you saw firsthand — the <=/< boundary comparison and the unlocked check-then-act race — are exactly the failure modes that separate "can recite the trade-off table" from "has shipped one of these and had it paged someone at 3am."
