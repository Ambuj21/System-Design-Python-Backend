Python backend internals · Phase 1 · Lesson 01

The GIL & the Concurrency Model

What actually happens, instruction by instruction, when you reach for threads, processes, or asyncio — and why one of these choices can make your program measurably slower, not faster.

01 Why this is an interview trap

Ask a mid-level engineer "what does the GIL do" and you'll usually get: "it means Python can't do real multithreading." That answer is close enough to sound right and wrong enough to fail a staff-level bar.

The GIL doesn't ban threads. CPython uses OS threads constantly — in production, right now, in whatever async framework you last shipped. What it bans is two threads executing Python bytecode at the exact same instant. Bytecode versus a syscall is the entire concept, and it's usually where the real conversation starts.

02 The one-key room

Picture the Python interpreter as a single small room where bytecode gets executed. There is exactly one key to that room.

That single sentence — the key is dropped for I/O, never for CPU work — predicts everything the console below shows.

Read the CPU-bound table again. Threading isn't just "no speedup" — it's slower than doing nothing clever at all. Four threads fighting over one key spend real wall-clock time on lock hand-off and context switches, on top of getting zero parallelism. This is the single most common wrong intuition among engineers with 3–5 years of experience.

04 How this shows up in systems you already use

  • gunicorn / uvicorn worker model. A production FastAPI or Django deployment doesn't pick one model — it stacks them. gunicorn -w 4 -k uvicorn.workers.UvicornWorker forks 4 processes (real parallelism across cores, sidestepping the GIL entirely), and inside each process a single event loop handles hundreds of concurrent connections cooperatively. Process-level parallelism for CPU headroom, async for I/O concurrency — that hybrid is the actual answer to "how does Python serve traffic at scale."
  • NumPy, Pandas, most C-extension libraries release the GIL while their C loop runs. This is why a threaded matrix-multiply can get real speedup in Python even though "the GIL prevents parallelism" — the hot loop isn't running Python bytecode at all. A strong candidate volunteers this exception unprompted.
  • CPython 3.13's free-threaded build (PEP 703) can run without a GIL at all. It's still opt-in and the C-extension ecosystem is mid-migration, but staff-level candidates are expected to know it exists and roughly what it trades away (single-thread performance, ABI stability) for true multi-core threading.
  • Redis's single-threaded command loop is the same one-key idea taken to its extreme on purpose — no lock contention, ever, because there's only ever one writer. Same mechanism, opposite lesson: sometimes you get correctness for free instead of throughput.

05 Hands-on: measure it yourself

Don't take the benchmark cards above on faith — here's the actual code that produced them. Run it locally; the CPU-bound numbers inverting is the whole lesson in one table.

bench.py
import time, threading, multiprocessing

def cpu_task(n=15_000_000):
    x = 0
    for i in range(n):
        x += i * i
    return x

def bench_threading(workers=4, n=15_000_000):
    t0 = time.perf_counter()
    threads = [threading.Thread(target=cpu_task, args=(n,)) for _ in range(workers)]
    for t in threads: t.start()
    for t in threads: t.join()
    return time.perf_counter() - t0

def bench_multiprocessing(workers=4, n=15_000_000):
    t0 = time.perf_counter()
    procs = [multiprocessing.Process(target=cpu_task, args=(n,)) for _ in range(workers)]
    for p in procs: p.start()
    for p in procs: p.join()
    return time.perf_counter() - t0
output (this machine, 12 cores, CPython 3.10.12)
=== CPU-bound task (4 workers, n=15,000,000 each) ===
sequential      : 1.953s
threading       : 5.868s   <- slower than doing nothing clever at all
multiprocessing : 0.548s   <- near-linear speedup

=== IO-bound task (8 workers, 0.3s fake network delay each) ===
sequential      : 2.403s
threading       : 0.304s   <- full overlap
asyncio         : 0.302s   <- identical overlap, 1 thread instead of 8

The exercise — predict before you run it, then check:

import sys
print(sys.getswitchinterval())      # default 0.005 (5ms) — how often CPython forces a GIL handoff
sys.setswitchinterval(0.0005)       # 10x more frequent forced switches
# rerun bench_threading() — does the CPU-bound number get better or worse?

It gets worse. Tighter switching means more forced hand-offs — more overhead, still zero parallelism. There is no switch-interval value that makes GIL-bound threads fast for CPU work; you're only ever tuning how much you lose.

06 The senior/staff framing

What separates a strong answer from a weak one

  • Weak: "Python can't do real multithreading because of the GIL." Strong: "Threads help exactly when the workload spends time outside the interpreter — I/O, or C code that drops the GIL. For CPU-bound Python, threads add scheduling overhead with zero parallelism; I'd reach for multiprocessing or push the hot path into C/Rust/NumPy."
  • The killer follow-up: "Your FastAPI handler calls a synchronous, CPU-heavy function directly — what happens to every other in-flight request?" The event loop is one thread. That call runs to completion holding the only thread the whole process has; every other coroutine — including unrelated requests — is frozen until it returns. Toggle "inject a blocking call" in the console above and watch tasks 1, 3, 4 flatline.
  • The fix worth naming: loop.run_in_executor(...) or asyncio.to_thread(...) to hand CPU work to a thread/process pool, keeping the event loop free.
  • Know the resource-cost axis, not just the throughput one: threads are cheap (~KB stack) and share memory; processes are expensive (MB+ each, no shared memory without IPC) but get real parallelism; coroutines are ~free but only exist within one thread.
