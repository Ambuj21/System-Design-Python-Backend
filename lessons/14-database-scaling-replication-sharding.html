Database Scaling: Replication & Sharding

How a single database becomes many machines instead of one — the exact mechanics of leader-follower replication and the lag that makes "just add a read replica" dangerous, then the three real ways to split data across shards, and why resharding one of them is a Saturday-night migration while another is a five-minute config edit.

01 Why "just add a replica, then shard it" falls apart

Ask how you'd scale a single Postgres or MySQL instance past one box and the fast answer is always the same two moves: add read replicas, then shard the writes. Both moves are correct. Both also replace one easy-to-reason-about failure mode — "the database is down" — with several quieter ones that only show up under real load, and staff-level interviews live in that gap, not in the fast answer.

Replication doesn't hand you a second copy of the truth. It hands you a copy that is, at any given instant, some number of milliseconds to seconds behind the truth — and every design decision built on top of that copy either accounts for the gap or ships a bug that only appears in production, under load, at the worst possible time. In October 2018, that exact gap took GitHub down for roughly a day: a 43-second network partition caused their failover tooling to promote a MySQL replica that hadn't received the newest writes, and for a window, two databases in two data centers both believed they were the primary. Section 02 walks through exactly how.

Sharding has the same shape of problem, one layer up. Splitting data across N machines is trivial with synthetic, uniformly-distributed test data. It stops being trivial the day one real customer, one real feature, or one real access pattern turns out not to be uniform — and by then the data is live, sharded, and expensive to move. That's the resharding pain and the hot-shard/hot-key problem the console in section 03 lets you break yourself.

02 One writer, many readers, one growing gap

A leader-follower database isn't "one database, copied." It's one leader replaying an append-only log of every change, and N followers independently replaying that same log at their own pace.

Every write lands on exactly one node, the leader. Before it does anything else, the leader appends the change to a durable, ordered, append-only log — Postgres calls it the WAL (write-ahead log), MySQL calls it the binlog, MongoDB calls it the oplog. The leader's queryable table data is, mechanically, just the result of replaying that log from the start. Followers connect to the leader, stream new log entries as they're appended, and replay each one against their own copy of the data. A follower is never a live mirror — it is, by construction, always some number of entries behind, permanently catching up.

How far behind is a design decision, not an accident. Asynchronous replication acknowledges the client's write the instant it's durable on the leader alone — fast, but if the leader dies before any follower applies that entry, the write is gone. Synchronous replication waits for at least one follower to confirm before acknowledging — safer, but every write now pays a network round trip to that follower, and if the follower is unreachable, writes stall. Most production systems land in between, semi-synchronous: wait for a follower to acknowledge receipt of the log entry, not that it has been applied yet — MySQL's semi-sync plugin and Postgres's synchronous_commit=remote_write both work this way.

The GitHub incident, mechanically: their replication was semi-synchronous — a write is acknowledged once at least one replica confirms receipt of the binlog entry, not that every replica has it. On October 21, 2018, a network partition of about 43 seconds split their primary MySQL cluster from part of their infrastructure. Their automated failover tool, orchestrator, correctly detected the primary as unreachable and promoted a replica — but the replica it promoted, in a different data center, hadn't received the very newest semi-sync-acknowledged writes made just before the partition. For a window of time, two clusters in two data centers were both accepting writes as if each were the one true primary. Untangling which writes actually happened, and reconciling roughly a day's worth of divergent history from binlogs without silently dropping data, is why GitHub's own public post-incident report runs to thousands of words instead of "we failed over, all good."

04 How this shows up in systems you already use

  • PostgreSQL streaming replication / AWS RDS & Aurora read replicas. Standard Postgres followers stream the WAL and expose lag as a first-class metric (pg_stat_replication.replay_lag). Aurora's replicas are a genuinely different mechanism worth naming if it comes up: its storage layer is shared across writer and readers, so replicas skip WAL shipping entirely and read from the same distributed storage the writer wrote to — which is why Aurora's replica lag is typically single-digit milliseconds, not the seconds ordinary streaming replication can hit under load.
  • MySQL binlog replication and GitHub's orchestrator. GitHub automates failover with orchestrator, which promotes the most caught-up replica when the primary disappears — exactly the machinery that, during the October 2018 network partition, promoted a replica that hadn't received the newest semi-sync-acknowledged writes, producing two primaries accepting divergent writes until it was caught and manually reconciled.
  • MongoDB replica sets elect a primary via a Raft-like consensus protocol and support a majority write concern — the driver-level equivalent of synchronous replication, trading write latency for the guarantee that an acknowledged write survives a primary failure.
  • DynamoDB partitions by hashing the partition key, and its single most common production failure mode has an official name: a "hot partition," throttled independently of the table's overall provisioned capacity even when the table as a whole is nowhere near its limit. AWS's own documented fix is write sharding — append a random or rotating suffix to a hot key to spread it across several physical partitions, then scatter-gather on read.
  • Redis Cluster doesn't hash keys straight to nodes. It hashes each key into one of 16,384 fixed slots (CRC16(key) % 16384), then maps slots to nodes. Resharding moves slot ownership, not individual keys one at a time — which is exactly why it can rebalance live without the "practically every key moves" problem naive mod-N hashing has.
  • Vitess (YouTube, Slack, GitHub, Square, Etsy) shards vanilla MySQL underneath a routing layer, and its Reshard workflow is a real, production version of what this lesson's console only simulates: it copies data to new shards via change-data-capture, keeps them continuously in sync, and cuts traffic over with a brief, controlled pause — the online-resharding machinery behind "five-minute config change" claims.

05 Hands-on: measure the actual cost of resharding

Consistent hashing is the real fix for hash-based resharding pain, and it's compact enough to implement and measure directly. The script below builds a naive key % n router and a consistent-hashing ring with virtual nodes, then measures exactly what fraction of 20,000 keys move when a 4-shard cluster grows to 5.

shard_bench.py
import hashlib
import bisect
from collections import Counter


def stable_hash(s: str) -> int:
    """MD5-based hash -> stable across runs/processes (unlike Python's salted str hash())."""
    return int(hashlib.md5(s.encode()).hexdigest(), 16)


def naive_shard(key: str, n: int) -> int:
    return stable_hash(key) % n


class ConsistentHashRing:
    """Classic consistent-hashing ring with virtual nodes (Dynamo/Cassandra-style)."""

    def __init__(self, shards, vnodes=150):
        self.vnodes = vnodes
        self.ring = {}          # hash position -> shard name
        self.sorted_positions = []
        for shard in shards:
            self.add_shard(shard)

    def add_shard(self, shard):
        for i in range(self.vnodes):
            pos = stable_hash(f"{shard}#vn{i}")
            self.ring[pos] = shard
        self.sorted_positions = sorted(self.ring.keys())

    def remove_shard(self, shard):
        self.ring = {pos: s for pos, s in self.ring.items() if s != shard}
        self.sorted_positions = sorted(self.ring.keys())

    def get_shard(self, key: str) -> str:
        h = stable_hash(key)
        idx = bisect.bisect(self.sorted_positions, h)
        if idx == len(self.sorted_positions):
            idx = 0
        return self.ring[self.sorted_positions[idx]]


NUM_KEYS = 20000
keys = [f"user:{i}" for i in range(NUM_KEYS)]

# ---- naive modulo hashing: 4 shards -> 5 shards ----
before_naive = {k: naive_shard(k, 4) for k in keys}
after_naive = {k: naive_shard(k, 5) for k in keys}
moved_naive = sum(1 for k in keys if before_naive[k] != after_naive[k])

# ---- consistent hashing ring: 4 shards -> 5 shards ----
shard_names = ["shard-0", "shard-1", "shard-2", "shard-3"]
ring = ConsistentHashRing(shard_names, vnodes=150)
before_ch = {k: ring.get_shard(k) for k in keys}
ring.add_shard("shard-4")
after_ch = {k: ring.get_shard(k) for k in keys}
moved_ch = sum(1 for k in keys if before_ch[k] != after_ch[k])

print(f"=== resharding cost: adding a 5th shard, {NUM_KEYS:,} keys ===")
print(f"naive modulo (key % n)      : {moved_naive:6,} keys moved  ({moved_naive/NUM_KEYS:.1%})")
print(f"consistent hashing (150 vn) : {moved_ch:6,} keys moved  ({moved_ch/NUM_KEYS:.1%})   theoretical ideal: {1/5:.1%}")

dist_naive = Counter(before_naive.values())
print(f"\n=== load distribution BEFORE resharding, naive modulo, 4 shards ===")
for i in range(4):
    n = dist_naive[i]
    print(f"  shard-{i}: {n:6,} keys ({n/NUM_KEYS:.1%})")

dist_ch = Counter(before_ch.values())
print(f"\n=== load distribution BEFORE resharding, consistent hashing, 4 shards, 150 vnodes/shard ===")
for s in shard_names:
    n = dist_ch[s]
    print(f"  {s}: {n:6,} keys ({n/NUM_KEYS:.1%})")

# ---- effect of vnode count on load balance (why vnodes matter) ----
print(f"\n=== load imbalance vs. vnode count (max shard load / perfectly-even load) ===")
for vn in (1, 5, 20, 150):
    r = ConsistentHashRing(shard_names, vnodes=vn)
    d = Counter(r.get_shard(k) for k in keys)
    even = NUM_KEYS / 4
    worst = max(d.values())
    print(f"  vnodes={vn:<4} worst shard load = {worst/NUM_KEYS:.1%}  (vs. {even/NUM_KEYS:.1%} perfectly even, {worst/even:.2f}x)")

Notice the code reaches for hashlib.md5 instead of Python's built-in hash(). Since Python 3.3, hash() on strings is randomized per-process via PYTHONHASHSEED as a defense against hash-flooding denial-of-service attacks — which means the same key would route to a different shard every time your process restarts. Never reach for the built-in hash() for anything that has to stay stable across processes, restarts, or machines; that's a correctness bug hiding as a one-line convenience.

The complexity story behind those numbers: naive modulo hashing does O(1) work per lookup but O(K) work — K being total key count — every time the shard count changes, because nearly every key's hash % n result changes when n does. The consistent-hashing ring does O(log(N·V)) work per lookup — a binary search over N shards × V virtual nodes — but only O(K/N) work when a shard is added or removed, because only the arc of keyspace between the new node's ring position and its neighbor's has to move. That asymmetry is the entire reason Dynamo, Cassandra, and Riak all standardized on it in the mid-2000s, and it's exactly what the "hash-based" column of the console's comparison table above is describing.

Run it and shard removal behaves exactly like growth for the ring — close to K/4 keys move, only the arc adjacent to the removed node's ring positions gets reassigned, while naive modulo remaps almost everything again. And no, more virtual nodes do not touch the ACME problem: vnodes redistribute how evenly many different keys land across shards; they do nothing for one key that is simply hot on its own. Consistent hashing routes by key identity — one key, one shard, always. The actual fix for a genuinely hot key lives above the sharding layer entirely: a read-through cache in front of it, or rewriting it as ACME#0 through ACME#9 and fanning reads and writes out across all ten with application-level scatter-gather — the same write-sharding trick AWS documents for DynamoDB's hot partitions in the real-world list above.

06 The senior/staff framing

What separates a strong answer from a weak one

  • Weak: "I'd use synchronous replication so we never lose data." Strong: "That depends what 'never lose data' costs elsewhere. Fully synchronous replication to every follower means the write path stalls the instant any one follower is slow or unreachable — you've traded data-loss risk for availability risk, not eliminated risk. Most production systems land on semi-synchronous: wait for one follower to acknowledge receipt, not full application, which bounds the data-loss window without paying full sync latency on every write."
  • The sharpest follow-up: "Your leader dies right now, mid-write, with one async follower one entry behind. The client already got a 200. Walk me through failover — is that client's write still there afterward?" The honest answer is: not necessarily. If the promoted follower hadn't applied that last entry, the write the client believes succeeded is gone — and if the old leader ever rejoins the cluster still holding that entry, you now have two histories that disagree, which is exactly GitHub's October 2018 incident. A strong candidate names the fix unprompted: fence the old leader (STONITH — shoot the other node in the head) so it can never accept writes or silently rejoin as if nothing happened, and reconcile divergent history from the WAL/binlog before it's allowed back into the cluster.
  • Weak (sharding): "Shard by hashing the user ID — that's what everyone does." Strong: "That depends entirely on the dominant query pattern. Hash-based sharding is right when every query is a point lookup by that key; it's wrong the moment you need range scans, because 'all orders from the last 30 days' turns into a fan-out query against every single shard. Range-based sharding keeps scans local to one shard but concentrates new writes on whichever shard owns the newest range. The key choice is a query-pattern decision before it's a hashing decision."
  • Know the vocabulary a staff interviewer expects unprompted: a hot shard holds a disproportionate share of data or load because of how the keyspace was split; a hot key gets disproportionate traffic regardless of how well-distributed the rest of the keyspace is. Resharding, of any kind, fixes the first. It cannot fix the second — a hot key needs caching, splitting, or dedicated capacity, not a different partitioning scheme.

08 Spaced recap

Resurfacing lesson 05 — ORM & Database Internals

Lesson 05 covered what your ORM is actually doing underneath the abstraction — lazy-loading triggering silent N+1 queries, and how a B-tree index turns a lookup from a full table scan into a handful of page reads. Sharding doesn't fix a bad query pattern; it multiplies its blast radius. An N+1 loop that was merely wasteful against one primary becomes, post-sharding, N+1 round trips potentially fanned out across N different physical databases, each with its own connection pool — and a pool sized for one database will exhaust connections and file descriptors fast once it's cloned across dozens of shards without resizing. The indexing discipline from lesson 05 matters more here, not less: an unindexed query doesn't just slow down one query anymore, it can back up an entire shard's connection pool and manufacture a hot-shard incident that has nothing to do with sharding strategy and everything to do with one missing index.
