Rate Limiting Algorithms

Every rate limiter answers the same two questions — how many requests came from this key recently, and does the answer change depending on exactly when you ask — with a different, deliberate trade between memory, precision, and burst tolerance. That's the real mechanism behind token buckets, leaky buckets, and sliding windows. "Just use Redis" is the easy 10% of this problem; the other 90% is making one atomic decision when fifty app servers ask the same question at the same instant.

01 Why "put a counter in Redis" is the easy half

Ask a mid-level engineer how they'd rate-limit an API and you'll usually get: "increment a Redis counter, set a TTL, reject once it hits the limit." That answer is directionally correct and incomplete on two separate axes, and a good interviewer will pull on both.

First, the algorithm you picked — a bare counter with a TTL is the fixed-window algorithm, and fixed windows have a precise, well-known failure mode: a client can burst up to double the configured limit by timing requests around the window edge. Not a rare adversarial trick — it happens to any bursty client, by accident, constantly.

Second, the "increment a counter" step itself is almost never one atomic operation the way people describe it. "Check the count, then increment if under the limit" is a classic check-then-act race the instant it runs from more than one process — which in a real fleet is always. The console below makes both problems visible; the hands-on section proves the second one by actually running 30 concurrent requests against a limit of 10 and watching 15 get through.

02 Buckets that fill, buckets that drain, clocks that reset

Every algorithm in this lesson is one of two mental models: a bucket with a fixed capacity that fills or drains over time, or a clock that counts how many requests landed in some span of time and occasionally forgets. The bucket family (token bucket, leaky bucket) cares about quantity available right now. The clock family (fixed window, sliding log, sliding counter) cares about how many happened recently. Same goal, structurally different failure modes.

The clock family throws the bucket away entirely and just counts. Fixed window: one counter, hard reset every N seconds — cheap, but the reset itself is the bug. Sliding log: remember every timestamp, count how many fall in the trailing N seconds — exact, but memory grows with traffic. Sliding counter: approximate the sliding log with two integers instead of a full log — the pragmatic middle that most production systems actually ship.

Bucket starts full, so the first 10 requests are free regardless of how fast they arrive — that's the whole burst allowance, spent in one shot. After that, admission is gated purely by refill: one new token every second, no memory of window edges at all.

Production leaky-bucket limiters almost never keep a literal queue array per key — they store one float per key (the "theoretical arrival time," or TAT) and derive the backlog arithmetically from it. That formulation has a name, GCRA (Generic Cell Rate Algorithm), and it's mathematically identical to a strict FIFO leaky bucket while costing the same O(1) memory as a token bucket. It's what Lyft's ratelimit service and several commercial API gateways actually run.

Read that middle column again. Token bucket and leaky bucket admit more requests inside the boundary-straddling burst (13 of 14) than fixed window does (12 of 14) — the algorithm everyone assumes is "the strict one." That's not a bug in the numbers; it's what burst-tolerant actually means: bucket algorithms don't know or care where a window edge is, only whether accumulated capacity plus refill covers the request rate. "Sliding beats fixed" is true for accuracy against a nominal rate; it is not automatically true for how many requests get through a specific burst. Which property you want is a design decision, not a default.

04 How this shows up in systems you already use

  • NGINX's limit_req module is documented, by name, as implementing the leaky bucket algorithm — requests over the configured rate either queue (burst=N) or get an immediate 503, and the module's own docs describe the queue draining at a strictly constant rate, exactly the shaping behavior in the console above.
  • AWS API Gateway throttling is explicitly documented as a token bucket: a steady-state rate plus a separate burst capacity, refilling continuously. The two numbers you configure — rate and burst — are literally refill_rate and capacity from this lesson's algorithm.
  • Stripe's API rate limits are documented as token-bucket-based, with separate buckets per API key and per endpoint category (read vs. write) — the same "smaller bucket for cheap ops, tighter bucket for expensive ones" pattern shows up in most large public APIs.
  • Lyft's open-source ratelimit service (widely used as the Envoy/Istio rate-limiting sidecar) implements GCRA specifically because it needs one Redis round-trip and O(1) memory per key at fleet scale — a literal per-key queue array, as in the console's mental model, would not survive that traffic volume.
  • Redis's own official "Rate limiter" pattern docs walk through the naive INCR+EXPIRE fixed-window approach, name the exact race condition demonstrated in the hands-on section below, and recommend a Lua script or MULTI/EXEC to close it — this isn't a hypothetical interview gotcha, it's in Redis's own guidance.
  • Kong Gateway's rate-limiting plugin lets operators choose fixed or sliding window per route — an explicit acknowledgment that this is a real per-endpoint tradeoff, not a single "correct" algorithm the platform should hardcode.

05 Hands-on: build it, then break it with concurrency

Three real scripts, all actually executed for this lesson — a single-process token bucket, then the distributed race condition, then the fix. The Redis in the last two isn't mocked: it's an embedded real redis-server binary (v6.2.14, via the redislite package) reached over a local unix socket, so the Lua script you're about to see runs unmodified against production Redis, ElastiCache, or MemoryDB too.

token_bucket.py — single process, no network involved yet
class TokenBucket:
    """capacity tokens, refilled at `rate` tokens/sec. `now` is injected
    so this demo runs in milliseconds instead of needing real sleeps --
    in production you'd pass time.monotonic()."""
    def __init__(self, capacity, rate, now=0.0):
        self.capacity = capacity
        self.rate = rate
        self.tokens = capacity        # starts full: burst allowed immediately
        self.last = now

    def allow(self, now):
        elapsed = now - self.last
        self.tokens = min(self.capacity, self.tokens + elapsed * self.rate)
        self.last = now
        if self.tokens >= 1:
            self.tokens -= 1
            return True
        return False

bucket = TokenBucket(capacity=10, rate=1.0, now=0.0)

print("-- burst of 14 requests at t=0.00 --")
for i in range(14):
    before = bucket.tokens
    ok = bucket.allow(now=0.0)
    print(f"  req {i+1:>2}  tokens_before_consume={before:5.2f}  -> {'ALLOW' if ok else 'DENY'}")

print()
print("-- 3.5s of idle time pass (bucket refills at 1 tok/sec) --")
preview = min(bucket.capacity, bucket.tokens + (3.5 - bucket.last) * bucket.rate)
print(f"  t=3.50  tokens now = {preview:.2f}")

print()
print("-- 5 more requests arrive at t=3.50 --")
for i in range(5):
    ok = bucket.allow(now=3.5)
    print(f"  req {i+1:>2}  tokens_after={bucket.tokens:5.2f}  -> {'ALLOW' if ok else 'DENY'}")

That's correct and cheap — for one process. The instant you run this behind a load balancer with 30 app servers, each server has its own tokens variable, and the "limit" becomes (your configured limit) × (number of servers). The fix is obvious — move the state into Redis, shared by everyone — and it's exactly where the second bug hides.

race.py — the naive distributed version, actually run with 30 concurrent workers
import threading, time, redis
r = redis.Redis(...)  # shared by every app server in the fleet
LIMIT = 10
KEY = "rl:naive:counter"

def worker(i):
    current = int(r.get(KEY) or 0)
    time.sleep(0.003)          # the network round-trip gap real fleets have
    if current < LIMIT:
        r.incr(KEY)
        allowed.append(i)

threads = [threading.Thread(target=worker, args=(i,)) for i in range(30)]
for t in threads: t.start()
for t in threads: t.join()

over-admitted by       : 5 requests past the limit

The 3ms sleep between the read and the write isn't cheating the demo — it stands in for the real network hop between two separate round-trips to a shared Redis, the exact gap 30,000 real concurrent requests would find on their own without any help. GET and INCR are each individually atomic; the sequence of "read, decide, write" is not, and that's the whole bug.

atomic.py — same test, one Lua script instead of two round-trips
LUA = """
local current = tonumber(redis.call('GET', KEYS[1]) or '0')
if current < tonumber(ARGV[1]) then
  redis.call('INCR', KEYS[1])
  return 1
else
  return 0
end
"""
script = r.register_script(LUA)

def worker(i):
    time.sleep(0.003)
    if script(keys=[KEY], args=[LIMIT]) == 1:
        allowed.append(i)

Redis executes Lua scripts on its single command thread, start to finish, with no other client's command able to interleave in the middle — the entire check-and-increment becomes one indivisible step no matter how many app servers are calling it. This is the actual mechanism behind "Redis makes distributed rate limiting easy": not that Redis is shared storage, but that Redis gives you a place to make a multi-step decision atomic.

the exercise — predict before you run it
def worker(i):
    time.sleep(0.003)
    new_val = r.incr(KEY)      # INCR alone is atomic -- no Lua at all here
    if new_val <= LIMIT:
        allowed.append(i)

Predict: does incrementing first and checking the result close the race completely, same as the Lua version? And after 30 concurrent runs, what will the raw counter value be — 10, 15, or 30? Run it, then check.

limit set to           : 10
concurrent requests    : 30
requests admitted      : 10
final raw counter value: 30  (correctly over-shoots -- 20 requests were rejected, but each still paid for one INCR)

It closes the race — exactly 10 admitted, every time, no Lua required — because INCR itself is a single atomic Redis command; there's no read-then-write gap left to interleave into. But the counter now means "total attempts," not "admitted requests," since every worker increments regardless of the outcome. If you need the counter for billing or analytics, you need the Lua version (or a compensating decrement on rejection); if you only need the yes/no decision, increment-first is simpler and just as correct.

06 The senior/staff framing

What separates a strong answer from a weak one

  • Weak: "I'd rate-limit using Redis with a counter and a TTL." Strong: "I'd pick the algorithm based on which failure mode I can tolerate — fixed window if a 2x burst at the edge is fine and I want O(1) everything, sliding counter if I need close-to-exact accuracy without paying for a per-request log, token bucket if I want to explicitly allow saved-up burst capacity, GCRA/leaky bucket if I'd rather queue and add latency than ever drop a request outright. Then I'd make sure the check-and-increment is one atomic Redis operation — Lua script or a single INCR — because two round-trips race under real concurrency, not just adversarial load."
  • The killer follow-up: "Your rate limiter's Redis primary goes down for 4 seconds during a traffic spike. What happens to every request in your fleet during that window, and does your algorithm choice make that better or worse?" There's no free answer here: fail-open (let requests through when Redis is unreachable) means your rate limiter offers zero protection during exactly the moment you needed it most; fail-closed (reject everything) means a Redis blip becomes a self-inflicted full outage. The algorithm barely matters for this question — what matters is that the candidate names the tradeoff explicitly instead of assuming Redis is always up.
  • A second-order point worth volunteering: sliding window and fixed window both depend on time being consistent across whoever's computing the window boundary. If that computation happens app-server-side instead of inside the Redis script, clock skew across the fleet reintroduces a subtler version of the same correctness bug — another reason the atomic operation should own the clock too (Redis's own TIME command inside the Lua script, not time.time() on 30 different machines).
  • Know where the limiter physically lives, not just its algorithm: at the edge/API-gateway (one decision point, simplest correctness story, but a single choke point) versus per-service (more flexible per-endpoint limits, but now N services each need the same atomicity discipline this lesson just demonstrated).

08 Spaced recap

Resurfacing lesson 13 — Caching Strategies & Invalidation

Lesson 13 spent a lot of effort on one idea: a cache is a deliberately inconsistent copy of the truth, and the entire job is bounding how wrong it's allowed to be, for how long, via TTLs and invalidation. A rate limiter's counter is that same object wearing a different hat — a Redis key with a TTL is structurally a cache entry, and "the window resets" is TTL expiry with extra steps. The race condition you just watched cost you 5 over-admitted requests for the identical reason an uncoordinated cache stampede costs you a thundering herd from lesson 13: multiple callers racing to read-then-write a shared, invalidatable value with no atomicity guarantee between the two steps. Different subsystem, same bug shape — which is exactly why the fix was the same instinct both times: make the read-decide-write sequence one atomic operation instead of three separate ones.
