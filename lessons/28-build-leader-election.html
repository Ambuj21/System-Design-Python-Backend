Applied system design in Python · Phase 3 · Lesson 28

Build a Toy Leader-Election Algorithm in Python

Terms, votes, randomized timeouts, and the exact arithmetic of a split vote — implemented as a real event-driven simulation you can run, not a slide with circular arrows on it.

01 Why this is an interview trap

Ask an engineer "how does leader election work" and you'll usually get: "the nodes vote, and whoever gets the most votes wins." That's the Wikipedia-summary version, and it survives about two follow-up questions before it falls apart.

It doesn't say what a term is, or why every vote is scoped to one. It doesn't explain why the timeout before a node starts an election has to be randomized — not fixed, not synchronized, specifically randomized. And it has no answer for the question every staff-level interviewer eventually asks: what actually stops two nodes from both believing they're the leader at the same time? "Majority vote" isn't the answer — it's the setup for the answer.

The honest way to actually understand this is to build the state machine yourself: five simulated nodes, real randomized timeouts, real vote bookkeeping, and — deliberately — a scenario engineered to produce a split vote, so you watch the cluster fail to elect anyone and recover on its own a few hundred milliseconds later. That's the whole lesson. Everything below is real, runnable Python.

02 The vacant chair

Five nodes sit around a table with one chair at the head, currently empty. Nobody is in charge. Filling that chair — and only that chair, only once per term — is the entire problem.

Two rules do all the work here. One vote per node per term — once N1 says yes to this candidate in term 4, it physically cannot also say yes to a different candidate in term 4, because voted_for is a single field, not a list. And majority, not unanimity — with 5 nodes you need 5 // 2 + 1 = 3 votes, never all 5. Those two rules are the entire safety argument for "only one leader per term," and the console below is built to make you watch what happens when they collide with bad timing instead of good timing.

Randomization isn't a nice-to-have detail bolted onto leader election; it is the liveness mechanism. Every node drawing from the same tight range is statistically the same failure mode as no randomization at all.

04 How this shows up in systems you already use

  • etcd runs this exact algorithm (real Raft, not a toy) to elect a leader among its cluster members, and Kubernetes' entire control plane sits on top of it — every kubectl apply is ultimately a write that etcd's Raft leader has to commit. etcd's real defaults are a 100ms heartbeat interval and a 1000ms election timeout: a comfortable 10x margin, same shape as the console above.
  • HashiCorp Consul and Nomad both use the same open-source Raft library (hashicorp/raft) to elect the server that owns writes to the catalog / job state. It's the same state machine you just watched, running in production clusters that route real service discovery traffic.
  • Kafka's KRaft mode (KIP-500, the default since Kafka 3.3+ and the only mode since Kafka 4.0) replaced ZooKeeper's external coordination with an internal Raft-based controller quorum — the controller leader election you're reading about here is now literally inside Kafka's own binary.
  • MongoDB replica sets elect a primary with a Raft-derived protocol, but add a twist worth knowing: votes can be weighted by a configured priority, so a node you've marked as preferred is more likely to win the race even under identical timeout randomization — a deliberate departure from "every vote counts equally."
  • ZooKeeper (ZAB) and classic Paxos-based systems solve the same election problem with a different protocol shape — worth naming in an interview specifically because it shows you know "leader election" is a problem class with several correct solutions, not a synonym for "Raft."

05 Hands-on: build and run it

This is a genuine discrete-event simulation — a heapq priority queue of timestamped events, not a polling loop — with the real Raft election state machine underneath: terms, per-term voting, majority quorum, and heartbeat-driven timer resets. No threads, no sockets; the mechanism is real even though the network is simulated.

raft_election.py — the simulator core
import heapq, itertools, random
from enum import Enum

class Role(Enum):
    FOLLOWER = "follower"
    CANDIDATE = "candidate"
    LEADER = "leader"

MSG_LATENCY = (1, 4)        # ms, one-way simulated network jitter
HEARTBEAT_INTERVAL = 50     # ms, leader -> followers

class Node:
    def __init__(self, node_id, all_ids, timeout_range):
        self.id = node_id
        self.peers = [p for p in all_ids if p != node_id]
        self.timeout_range = timeout_range
        self.role = Role.FOLLOWER
        self.current_term = 0
        self.voted_for = None
        self.votes_received = set()
        # bumped on every timer reset; a scheduled timeout event that
        # doesn't match the CURRENT epoch has been superseded -- ignore it.
        # (the discrete-event-sim equivalent of cancelling a real timer)
        self.timer_epoch = 0

class Simulator:
    def __init__(self, n_nodes=5, timeout_range=(150, 300), seed=42,
                 forced_first_timeouts=None):
        self.rng = random.Random(seed)
        self.ids = list(range(n_nodes))
        self.nodes = {i: Node(i, self.ids, timeout_range) for i in self.ids}
        self.events = []                  # heap: (time, seq, kind, payload)
        self.seq = itertools.count()
        self.log = []
        self.now = 0.0
        self.majority = n_nodes // 2 + 1
        for i in self.ids:
            t = (forced_first_timeouts or {}).get(i, self.rng.uniform(*timeout_range))
            self._schedule(t, "election_timeout", {"node": i, "epoch": 0})

    def _schedule(self, delay, kind, payload):
        heapq.heappush(self.events, (self.now + delay, next(self.seq), kind, payload))

    def run(self, until=2000):
        while self.events and self.now < until:
            t, _, kind, payload = heapq.heappop(self.events)
            self.now = t
            getattr(self, f"_handle_{kind}")(payload)
        return self.log

    def _reset_election_timer(self, node):
        node.timer_epoch += 1
        t = self.rng.uniform(*node.timeout_range)
        self._schedule(t, "election_timeout", {"node": node.id, "epoch": node.timer_epoch})

    def _handle_election_timeout(self, p):
        node = self.nodes[p["node"]]
        if node.role == Role.LEADER or p["epoch"] != node.timer_epoch:
            return                                   # stale or already leader
        node.current_term += 1
        node.role = Role.CANDIDATE
        node.voted_for = node.id
        node.votes_received = {node.id}
        self._reset_election_timer(node)              # re-arm in case THIS election also fails
        for peer in node.peers:
            self._schedule(self.rng.uniform(*MSG_LATENCY), "request_vote",
                            {"to": peer, "from": node.id, "term": node.current_term})

    def _handle_request_vote(self, p):
        node = self.nodes[p["to"]]
        term, candidate = p["term"], p["from"]
        if term > node.current_term:                  # newer term always wins -> step down
            node.current_term, node.role, node.voted_for = term, Role.FOLLOWER, None
        grant = (term == node.current_term) and node.voted_for in (None, candidate)
        if grant:
            node.voted_for = candidate
            self._reset_election_timer(node)           # heard from a legit candidate, don't also time out
        self._schedule(self.rng.uniform(*MSG_LATENCY), "vote_response",
                        {"to": candidate, "from": node.id, "term": term, "granted": grant})

    def _handle_vote_response(self, p):
        node = self.nodes[p["to"]]
        if node.role != Role.CANDIDATE or p["term"] != node.current_term or not p["granted"]:
            return
        node.votes_received.add(p["from"])
        if len(node.votes_received) >= self.majority:
            node.role, node.leader_id = Role.LEADER, node.id
            self._schedule(0, "heartbeat", {"leader": node.id, "term": node.current_term})

    def _handle_heartbeat(self, p):
        leader = self.nodes[p["leader"]]
        if leader.role != Role.LEADER or p["term"] != leader.current_term:
            return
        for peer in leader.peers:
            self._schedule(self.rng.uniform(*MSG_LATENCY), "append_entries",
                            {"to": peer, "term": leader.current_term, "leader": leader.id})
        self._schedule(HEARTBEAT_INTERVAL, "heartbeat", p)   # keep beating on its own term

    def _handle_append_entries(self, p):
        node = self.nodes[p["to"]]
        if p["term"] < node.current_term:
            return
        node.current_term, node.role = p["term"], Role.FOLLOWER
        node.leader_id = node.voted_for = p["leader"]
        self._reset_election_timer(node)               # heartbeat = proof of life, reset the clock

def summarize(sim):
    """After a run: which node (if any) is leader, and in what term it won."""
    for node in sim.nodes.values():
        if node.role == Role.LEADER:
            return {"leader": node.id, "term": node.current_term}
    return {"leader": None, "term": None}

Four RPC handlers, one timer-epoch trick, one priority queue. That's the entire election subset of Raft — log replication and snapshotting are a different lesson. Notice what's not here: no global clock, no "wait for everyone." A candidate becomes leader the instant votes_received crosses majority, exactly like the diagram in section 02.

demo 1 — real output: a manufactured 3-way split vote

Nodes 0, 2 and 4 are pinned to time out at the identical instant, forcing three simultaneous candidates for term 1. With only nodes 1 and 3 left to hand out votes, the best any single candidate can reach is 1 (self) + 2 (both other followers) = 3 — but only if both followers happen to pick the same candidate. This seed doesn't:

Notice term 1 never got a second chance: only two of the three candidates (node 0 and node 2) even managed to collect one external vote apiece, so nobody reached 3 and every node in that round eventually re-times-out and moves to term 2 with a freshly randomized delay. Node 4 — one of the original three candidates — re-armed after losing the term-1 split and happened to draw the shortest new timeout of anyone in the cluster, so it ran uncontested in term 2 and reached majority 5.0ms after starting its campaign. This is exactly why elections need not converge on the first try, and exactly why they still converge quickly: each retry re-rolls the dice with a wide enough range that ties become rare fast.

exercise — predict before you run it

Question: at the same narrow (150–155ms) timeout window that produced a 55.2% split-vote rate for a 5-node cluster — does shrinking the cluster to 3 nodes make split votes more or less likely? What about growing it to 9? Write down a guess before reading the output.

from raft_election import Simulator, summarize

for n in (3, 5, 7, 9):
    trials, splits = 1000, 0
    for seed in range(trials):
        s = Simulator(n_nodes=n, timeout_range=(150, 155), seed=seed)
        s.run(until=8000)
        if summarize(s)["term"] > 1:
            splits += 1
    print(f"n={n}: split-vote rate = {100*splits/trials:.1f}%")

(1,000 trials here vs. 2,000 in the bench cards above — expect the n=5 number to wobble a point or two between runs; that's Monte Carlo sampling noise, not a bug.)

Bigger clusters split more often at a fixed timeout window, monotonically. More nodes means more chances that two of them draw nearly-identical timeouts out of the same narrow range, and — separately — a bigger cluster needs relatively more of the remaining nodes to break the tie. This is the concrete reason production Raft deployments don't just widen the timeout window a little as they scale membership; the range has to stay wide relative to the broadcast time regardless of N.

06 The senior/staff framing

What separates a strong answer from a weak one

  • Weak: "Raft elects a leader by majority vote, and random timeouts stop everyone running at once." Strong: "Safety and liveness are separate guarantees here, proven separately. Safety — at most one leader per term — is structural: voted_for is a single field, so any two majorities out of N nodes must overlap in at least one node, and that node can't have granted two different candidates a vote in the same term. That holds even if every clock in the cluster is adversarially synchronized. Liveness — someone eventually gets elected — is the part that depends on timing, specifically the inequality broadcastTime ≪ electionTimeout ≪ MTBF from the Raft paper: RPCs need to complete well inside the timeout window, and the timeout needs to be well inside the mean time between real node failures, or the cluster thrashes."
  • The killer follow-up: "Two nodes both believe they're the leader for term 7. Walk me through, using the actual vote bookkeeping, why that's impossible." The answer has to name quorum intersection explicitly: any two sets of 3-or-more nodes out of 5 share at least one node; that shared node can grant at most one vote in term 7; therefore at most one candidate can collect a majority in term 7. A candidate answer that says "it just can't happen" or points at randomization hasn't actually proven anything — randomization affects how fast you get a leader, not whether two leaders coexist.
  • Worth raising unprompted: what happens during a network partition. The old leader, stuck in the minority side, keeps sending heartbeats nobody outside its shard hears — it doesn't know it's been deposed. The majority side times out and elects a new leader on a higher term. When the partition heals, the stale leader receives a message carrying that higher term, and the term > current_term check in the code above forces it to step down immediately. Term numbers are the mechanism that resolves this, not a heartbeat timeout on the old leader's side.
  • Resource/complexity framing an interviewer wants to hear: one election round costs O(N) RequestVote RPCs per candidate (broadcast to all peers), so a c-way split costs O(c·N) messages for that round — cheap, and rare in a healthy cluster. Steady-state cost is dominated by heartbeats instead: a leader sends N-1 heartbeats every interval, indefinitely, which is the real, ongoing "control-plane tax" of running Raft.
