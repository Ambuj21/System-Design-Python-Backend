Python backend mastery · Phase 1 · Lesson 09

Packaging & Deployment

How a Python service actually gets from source code into a running, load-balanced, self-healing fleet — and the two decisions in that path (image layout, rollout strategy) that separate a smooth deploy from a 3am page.

01 Why this is an interview trap

Most candidates can recite "Docker packages your app, Kubernetes runs it." That sentence is true and tells an interviewer nothing about whether you've actually operated either one under load. The questions that separate levels here aren't about syntax — they're about what happens in the failure case.

Two concrete traps: first, a 1.2GB image that takes 90 seconds to pull onto a fresh node is not a cosmetic problem — during an incident, that's 90 seconds your autoscaler is not helping you, per pod, on every node that doesn't already have the image cached. Second, and far more common in interviews: engineers assume Kubernetes "waits until the new version is confirmed healthy before touching the old one" during a rolling update. It doesn't, by default — it does availability arithmetic every reconcile tick, and it will remove old capacity before the replacement has even started its first readiness check. We'll prove that with real, executed code below, not a claim.

The console in this lesson is driven by the exact tick trace of a Deployment-controller simulation you'll run yourself in the hands-on section — not a hand-animated guess at the behavior.

Read the toggle result again. With the probe broken, rolling update still sacrifices one old pod's worth of capacity before it knows anything is wrong — the first replacement is unconditional. Blue-green never touches Blue until every Green pod is proven. That asymmetry, not "which one is newer," is the actual tradeoff.

04 How this shows up in systems you already use

  • The Kubernetes Deployment controller literally runs the scale-up/scale-down arithmetic you'll execute yourself below, once per reconcile loop, comparing status.availableReplicas against the surge/unavailable budget — pkg/controller/deployment/rolling.go upstream.
  • kube-proxy's two dataplane modes encode a real complexity tradeoff: iptables mode matches a Service's virtual IP by walking a linear chain of NAT rules — O(n) in the number of Services/endpoints, a documented scaling cliff past a few thousand Services on a cluster. IPVS mode dispatches via a hash table — O(1) — which is why large clusters (and eBPF-based dataplanes like Cilium) move off iptables entirely.
  • Google's distroless images (gcr.io/distroless/python3-debian12) and Chainguard's Wolfi-based images take the multi-stage idea further: no shell, no package manager, no coreutils in the final layer at all — smaller attack surface, at the cost of not being able to kubectl exec ... sh into a running container to debug it.
  • Argo Rollouts and Flagger implement blue-green and canary as Kubernetes CRDs layered on top of ordinary Deployments, and add the piece neither rolling update nor blue-green has natively: automated analysis against Prometheus metrics (error rate, p99 latency) before advancing traffic — catching the "healthy but functionally wrong" class of bug that a readiness probe structurally cannot.
  • Istio/Envoy/Linkerd generalize the traffic-shifting idea to arbitrary percentages (1%, 5%, 50%) independent of pod count, which is what makes true canary releases possible — you can't get a 1% traffic split from pod proportions alone with only 4 replicas.
  • startupProbe (GA since Kubernetes 1.20) exists specifically because livenessProbe used to kill slow-starting containers — a JVM warming up, a Python process loading a large ML model — before they ever got a chance to become ready; a startup probe suspends liveness/readiness checks until the app confirms it has finished booting.
  • CrashLoopBackOff is the kubelet's exponential backoff after repeated liveness-triggered restarts: 10s, 20s, 40s… capped at 5 minutes — a direct, load-bearing consequence of how you configure failureThreshold and periodSeconds.

05 Hands-on: the Dockerfile, and the controller math

Two artifacts. The Dockerfile is what you'd actually ship. The Python script is a faithful reimplementation of the Deployment controller's per-tick arithmetic — genuinely executed below, and it's what generated every number in the console above.

Dockerfile — multi-stage, non-root, cache-ordered
# syntax=docker/dockerfile:1

########## Stage 1: builder ##########
FROM python:3.11 AS builder

RUN apt-get update && apt-get install -y --no-install-recommends \
        build-essential gcc libpq-dev \
    && rm -rf /var/lib/apt/lists/*

WORKDIR /app
# Copy ONLY the lockfile first — this layer only invalidates when deps change,
# not on every source edit. This ordering is the entire cache-hit-rate trick.
COPY requirements.txt .

RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install -r requirements.txt

COPY . .

########## Stage 2: final ##########
FROM python:3.11-slim AS final

RUN useradd --create-home --uid 1000 appuser
WORKDIR /app

# Only these two paths cross the stage boundary. No compiler, no apt
# cache, no .git, no test suite ends up in the pushed image.
COPY --from=builder /opt/venv /opt/venv
COPY --from=builder /app /app

ENV PATH="/opt/venv/bin:$PATH" \
    PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

USER appuser
EXPOSE 8000
ENTRYPOINT ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
.dockerignore (skip this and multi-stage buys you less than you think)

Illustrative image sizes — no Docker daemon is available in this environment, so these are commonly-reported, order-of-magnitude figures for a typical FastAPI service with a couple of C-extension dependencies, not a measurement taken here:

python:3.11 (full base)                       ~1.0 GB
naive single-stage (deps + compiler baked in) ~1.1-1.3 GB
multi-stage, final = python:3.11-slim         ~150-220 MB   (5-7x smaller)
multi-stage, final = distroless/python3       ~80-120 MB    (no shell/pkg mgr)

The Alpine trap worth naming out loud: Alpine's musl libc means many packages with C extensions (cryptography, psycopg2, pydantic-core, numpy) don't ship musl wheels on PyPI, so pip falls back to compiling from source — which drags the build toolchain back in, makes CI slower, and has historically triggered musl-specific DNS resolution bugs in cluster networking. slim (glibc, Debian-based) is usually the pragmatic default; Alpine's size advantage rarely survives contact with a real dependency tree.

rollout_sim.py — the Deployment controller's reconcile math, actually run
def simulate_rollout(desired, max_surge, max_unavailable, probe_passes=True, max_ticks=15):
    old_total, old_ready = desired, desired
    new_total, new_ready = 0, 0
    not_yet_ready = 0   # created last tick, still running its readiness probe

    for tick in range(1, max_ticks + 1):
        if not_yet_ready:
            if probe_passes:
                new_ready += not_yet_ready
            not_yet_ready = 0

        max_total = desired + max_surge
        room_to_surge = max(0, max_total - (old_total + new_total))
        scale_up = min(room_to_surge, max(0, desired - new_total))
        if scale_up > 0:
            new_total += scale_up
            not_yet_ready += scale_up

        min_available = desired - max_unavailable
        can_remove = max(0, (old_ready + new_ready) - min_available)
        scale_down = min(can_remove, old_total)
        old_total -= scale_down
        old_ready = old_total
        # ... print the tick, check for completion (full script runs this for real)

Look at tick 1 in the first run: old ready/total is already 3/3 — one old pod is gone before the new one (still 0/1, unready) has done anything. The controller only needs available >= desired - maxUnavailable to hold; it doesn't care whether that headroom comes from a proven old pod or an unproven new one being trusted to arrive. That's the mechanism the console's playhead is tracing.

The exercise — predict before you run it: for desired=10, max_surge=2, max_unavailable=3, what's the lowest available count you'll see, and how many ticks does the rollout take?

simulate_rollout(desired=10, max_surge=2, max_unavailable=3)

Actual answer, from running it: min_available = 10 - 3 = 7, and the trace holds at exactly 7/10 available for the first three ticks before completing at tick 5 — peak pod count only ever reaches 10, not the 12 that maxSurge=2 would allow, because the controller never creates more new pods than desired requires. If you predicted the floor would be lower than 7 or the peak would hit 12, you were reasoning about the limits instead of the arithmetic that actually runs each tick.

06 The senior/staff framing

What separates a strong answer from a weak one

  • Weak: "Blue-green is safer because rollback is instant, so we should just always use it." Strong: "Rollback speed is real, but it isn't free — blue-green needs 2x steady-state capacity for the cutover window, and because it flips 100% of traffic at once, a bug that passes the readiness probe but is logically wrong hits every user the instant you cut over. Rolling update trades slower rollback for a smaller, self-limiting blast radius — by default only maxSurge worth of traffic (often 25%) ever reaches a bad version before you'd notice and halt it."
  • The killer follow-up: "Your readiness probe is GET /healthz returning 200 whenever the process can accept connections. You ship a version where that endpoint is correct, but a specific code path — say, currency conversion — silently returns wrong numbers for 8% of requests. Walk me through what each strategy does with that version, and tell me which single component in this whole picture's job it actually was to catch this, and why it didn't." The honest answer: neither strategy catches it. A readiness probe verifies infrastructure health, not business correctness — it was never the right tool for this bug. Catching it needs automated canary analysis against real metrics (error rate, business KPIs), which is exactly what Argo Rollouts / Flagger add as a layer on top of either strategy, not a replacement for it.
  • Know the peak-vs-floor distinction, not just "which is safer": rolling update's floor dips below 100% capacity during the rollout by design (that's what maxUnavailable means); blue-green's floor never dips, but its peak briefly doubles your bill.
  • Name the actual default recommendation: rolling update for routine, low-risk deploys of stateless services (cheap, native to Deployment, no extra tooling); blue-green or canary when you need a hard guarantee against capacity dips, an instant abort button, or you're shipping something you don't fully trust — a new dependency version, a schema-adjacent change, a migration.

07 Check your understanding

Before you move on

A Deployment runs with replicas=10 and the Kubernetes defaults (maxSurge=25%, maxUnavailable=25%). A teammate says: "We're fully protected during rollouts — Kubernetes always waits for a new pod to pass its readiness probe before touching an old one, so capacity never drops below 10."

Are they right? Trace the first two reconcile ticks by hand — what happens to the old-pod count in tick 1, before any new pod has had a chance to pass its probe — and state the actual capacity floor you'd expect to observe during this rollout.

08 Spaced recap

Resurfacing: Lesson 06 — Redis Caching Patterns

Lesson 06 covered the cache stampede — many requests missing a cold key at once and all hammering the origin together. A rolling or blue-green deployment manufactures the exact same failure at the infrastructure layer: every replacement pod boots with an empty in-process cache, and if several land in the same short window, that's several independent cold starts hitting your database simultaneously — a stampede caused by pod churn, not TTL expiry. The fix is the one from Lesson 06: keep hot keys in a shared Redis layer that survives pod restarts, so a new pod inherits a warm cache instead of re-priming it — and don't mark a pod Ready on "process is up" alone; gate readiness on "can reach the cache," too.
