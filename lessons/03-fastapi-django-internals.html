Python backend mastery · Phase 1 · Lesson 03

FastAPI & Django Internals

What actually happens between a socket accepting bytes and your view function returning a dict — the protocol boundary, the middleware onion, the dependency graph, and the exact line where the ORM decides to talk to the database.

01 Why "FastAPI is async, Django is sync" fails the bar

Most candidates' mental model stops at: "FastAPI uses ASGI so it's non-blocking, Django uses WSGI so it's one-thread-per-request." That distinction is real, but it's the least interesting thing you can say about either framework, and treating it as the whole answer means you have nothing left when the interviewer asks the second question.

The traps that actually separate levels here: whether you know middleware execution order can literally invert between the two frameworks for the exact same declared list; whether you know FastAPI's Depends() graph is resolved once per request as a cached DAG, not re-executed per usage site; whether you can name the precise line of Django ORM code that sends SQL versus the ten lines before it that just built a query object; and whether you know ASGI is a calling convention, not a promise that your code won't block.

Every one of those four is demonstrated below with real, executed output — nothing in this lesson is asserted without being run first.

02 Envelopes inside envelopes

A request never reaches your view function directly. It's handed to the outermost middleware, which decides whether to inspect it, mutate it, or pass it one layer further in — until something at the center actually reads the letter and writes a reply.

That last sentence is where FastAPI and Django quietly disagree with each other — both in which layer ends up "outer," and in what an uncaught exception does to the layers in between. The console below runs both, for real.

Starlette's BaseHTTPMiddleware gives you no such guarantee — cleanup code you assume will run on every request only runs on the happy path unless you write the try/finally yourself. This is the single most common blind spot engineers carry from Django into a FastAPI codebase.

  


  

    
04 How this shows up in systems you already use

    
    
      
  • ASGI didn't start life inside FastAPI. The spec came out of Django Channels (Andrew Godwin, ~2015-16) as a way to give Django websockets and long-lived connections without abandoning WSGI compatibility. Starlette adopted it as a framework-agnostic standard a few years later, and FastAPI is built directly on top of Starlette's ASGI machinery — the "modern async framework" is, historically, downstream of Django's own concurrency problem.
    • 
      
  • Django's own ASGI support doesn't make the ORM async. django.core.handlers.asgi.ASGIHandler (3.0+) lets Django run under uvicorn and serve async def views, but a plain Article.objects.filter(...) call is still fully synchronous — Django wraps it with sync_to_async under the hood, or you reach for the native async ORM methods (aget, afilter, acreate, added in 4.1+) so it doesn't block the loop. Describing this as "the ORM went async" in an interview is describing a footgun as a feature.
    • 
      
  • FastAPI's app.dependency_overrides dict. Test fixtures swap a real DB session for a fake one with app.dependency_overrides[get_db] = get_test_db — this only works because the dependency graph is keyed by the callable object's identity, not by name, which is the same mechanism behind the per-request caching you'll see in section 05.
    • 
      
  • Django REST Framework's APIView.dispatch() is a second, smaller onion nested one level inside Django's own — authentication_classes, then permission_classes, then throttle_classes run in a fixed declared order before your get()/post() ever executes. Same mental model, one layer down.
    • 
      
  • APM agents — Datadog, Sentry, New Relic — instrument exactly the seam this lesson is about. Their ASGI middleware wraps scope/receive/send; their WSGI middleware wraps environ/start_response. It's the same raw hook point exercised with real code in section 05, just with a tracing span attached instead of a print().

05 Hands-on: three things you can only trust once you've run them

    
All output below is real, captured on this machine — Python 3.10.12, FastAPI 0.109.0 / Starlette 0.35.1, Django 5.2.17, httpx 0.26.0 used as the ASGI/WSGI test transport.


    
1. The protocol boundary, with no framework in the way. Before either framework touches a request, uvicorn or gunicorn calls exactly one Python callable using exactly one calling convention. Here they are, driven directly — no FastAPI, no Django — showing the raw contract each framework is built on top of.


    
raw_protocols.py

    
import httpx, asyncio

# ---------- raw WSGI app: one synchronous callable ----------
def wsgi_app(environ, start_response):
    print("[WSGI] method:", environ["REQUEST_METHOD"], "path:", environ["PATH_INFO"])
    body = b"hello from wsgi"
    start_response("200 OK", [("Content-Type", "text/plain")])
    return [body]                      # returns an iterable of byte chunks

with httpx.Client(transport=httpx.WSGITransport(app=wsgi_app), base_url="http://testserver") as c:
    r = c.get("/hello")
    print("[WSGI] client received:", r.status_code, r.text)

# ---------- raw ASGI app: one async callable, event-driven ----------
async def asgi_app(scope, receive, send):
    print("[ASGI] scope type:", scope["type"], "method:", scope["method"])
    event = await receive()                                    # pull an event
    print("[ASGI] received:", event["type"])
    await send({"type": "http.response.start", "status": 200,
                "headers": [(b"content-type", b"text/plain")]})  # push an event
    await send({"type": "http.response.body", "body": b"hello from asgi"})

async def run_asgi():
    async with httpx.AsyncClient(transport=httpx.ASGITransport(app=asgi_app), base_url="http://testserver") as c:
        r = await c.get("/hello")
        print("[ASGI] client received:", r.status_code, r.text)

asyncio.run(run_asgi())


    
output (real, this machine)

    
[WSGI] method: GET path: /hello
[WSGI] client received: 200 hello from wsgi
[ASGI] scope type: http method: GET
[ASGI] received: http.request
[ASGI] client received: 200 hello from asgi


    
WSGI (PEP 3333) is a single synchronous function call: server builds an environ dict once, your app returns bytes, done — no way to stream in either direction, no way to hold the connection open. ASGI is a long-lived async call with two separate event channels: receive() pulls events (body chunks, disconnects), send() pushes events (response start, body chunks, more later). That's the entire protocol-level difference — everything else, including "async," is a consequence of it, not the definition of it.


    
2. Depends() is a cached graph, not a re-run tree. Two independent dependencies both declare Depends(get_db). If FastAPI treated dependencies as a tree, get_db would run twice per request. It doesn't.


    
dep_cache.py

    
from fastapi import FastAPI, Depends
from starlette.testclient import TestClient

app = FastAPI()

def get_db():
    print("   [dep] get_db: opening session")
    yield "db-session"

def get_current_user(db=Depends(get_db)):
    print("   [dep] get_current_user resolved")
    return "user-42"

def get_permissions(db=Depends(get_db)):   # also depends on get_db, independently
    print("   [dep] get_permissions resolved")
    return ["read", "write"]

@app.get("/items")
def read_items(user=Depends(get_current_user), perms=Depends(get_permissions)):
    print(f"   [handler] user={user} perms={perms}")
    return {"user": user, "perms": perms}

client = TestClient(app)
client.get("/items")


    
output (real, this machine)

    
   [dep] get_db: opening session
   [dep] get_current_user resolved
   [dep] get_permissions resolved
   [handler] user=user-42 perms=['read', 'write']


    
One "opening session," not two. FastAPI builds the dependency tree once, at route-registration time, by walking each path operation's signature with inspect.signature(); at request time it resolves that pre-built DAG bottom-up, caching each callable's result by object identity (Depends(fn, use_cache=True) is the default) so a dependency shared by N branches still runs once. Cleanup for yield-based dependencies is managed by an AsyncExitStack and unwinds in LIFO order after the handler returns — which is exactly why get_db's teardown in section 03's trace panel fires after the handler, not after each individual Depends() call site.


    
3. Where Django's ORM actually fires. A QuerySet is an immutable, lazy description of a query — every chained method returns a new QuerySet wrapping an updated internal Query object. No socket to the database opens until one of a handful of trigger points.


    
demo/models.py

    
from django.db import models

class Article(models.Model):
    title = models.CharField(max_length=200)
    views = models.IntegerField(default=0)


    
run_lazy_demo.py

    
import django
from django.conf import settings
settings.configure(
    DATABASES={"default": {"ENGINE": "django.db.backends.sqlite3", "NAME": ":memory:"}},
    INSTALLED_APPS=["demo"], USE_TZ=True,
)
django.setup()

from django.db import connection, reset_queries
from demo.models import Article
# ... schema created, 3 rows inserted ...
reset_queries()

print("=== step 1: build a queryset ===")
qs = Article.objects.filter(views__gt=5).order_by("-views")
print("queries fired so far:", len(connection.queries))

print("=== step 2: chain another filter (still lazy) ===")
qs2 = qs.exclude(title__icontains="onion")
print("queries fired so far:", len(connection.queries))

print("=== step 3: force evaluation with list() ===")
results = list(qs2)
print("queries fired so far:", len(connection.queries))
print("SQL actually sent:", connection.queries[-1]["sql"])

print("=== step 4: .exists() and len() each fire their OWN query ===")
reset_queries()
qs3 = Article.objects.all()
print("exists() ->", qs3.exists(), "| queries:", len(connection.queries))
print("len(qs3) ->", len(qs3), "| queries:", len(connection.queries))
print("iterating qs3 again ->", [a.title for a in qs3], "| queries:", len(connection.queries))


    
output (real, this machine)

    
=== step 1: build a queryset ===
queries fired so far: 0
=== step 2: chain another filter (still lazy) ===
queries fired so far: 0
=== step 3: force evaluation with list() ===
queries fired so far: 1
SQL actually sent: SELECT "demo_article"."id", "demo_article"."title", "demo_article"."views"
  FROM "demo_article" WHERE ("demo_article"."views" > 5
  AND NOT ("demo_article"."title" LIKE '%onion%' ESCAPE '\')) ORDER BY "demo_article"."views" DESC
=== step 4: .exists() and len() each fire their OWN query ===
exists() -> True | queries: 1
len(qs3) -> 3 | queries: 2
iterating qs3 again -> ['ORM internals', 'ASGI vs WSGI', 'Middleware onion'] | queries: 2


    
Two chained filters, zero queries. list() is the trigger, and it fires exactly one query carrying both filters merged into a single WHERE clause — the ORM never sends "step 1's SQL" and "step 2's SQL" separately, because nothing was ever sent until evaluation. Step 4 is the sharper trap: .exists() and len() each hit the database independently even though they're describing "the same" queryset, because .exists() runs a cheap SELECT 1 ... LIMIT 1-style check without populating the result cache, while len() forces full materialization. Only after the cache is populated does re-iterating become free — the final line costs nothing new.


    
the exercise — predict before you run it

    
You've seen that iterating a materialized queryset is free (no new query). Add this to the script and predict the query count for each line before running it:

    
reset_queries()
fresh = Article.objects.all()
first = fresh[0]                 # single-index access
print(len(connection.queries))   # ?
print(fresh._result_cache)       # ?  -- did indexing populate the cache for later iteration?

reset_queries()
ranged = Article.objects.all()[1:3]   # range slice
print(len(connection.queries))        # ?  -- built vs. evaluated

    
Both are traps in opposite directions. A single index (qs[0]) evaluates immediately — it issues its own SELECT ... LIMIT 1 and leaves _result_cache still None, so a subsequent for a in fresh pays for a second, full query. A range slice (qs[1:3]) stays fully lazy — it builds a new QuerySet carrying LIMIT 2 OFFSET 1 and fires zero queries until that is itself iterated. "Slicing a queryset is lazy" is true and false depending on which kind of slice you mean, and that exact distinction has ended more than one mid-level interview.

  


  

    
06 The senior/staff framing

    

      
What separates a strong answer from a weak one

      
    
        
  • Weak: "FastAPI is faster because it's async, Django is slower because it's sync." Strong: "ASGI buys higher connection concurrency for I/O-bound fan-out — many slow upstream calls per request — because one event loop thread can interleave them. It buys nothing for CPU-bound or blocking-sync work, and it actively hurts you if a handler blocks the loop: unlike Django's one-thread-per-request WSGI model, the failure mode isn't 'this request got slow,' it's 'every concurrent request on this worker got slow, including ones with no relation to whatever blocked.'"
    • 
        
  • The killer follow-up: "You migrate a Django view to a FastAPI async def endpoint and call your existing synchronous Django ORM / psycopg2 code directly inside it, with no run_in_executor or asyncio.to_thread. What happens to the other 200 in-flight requests on that worker?" — answered concretely in the recap below.
    • 
        
  • The nesting-reversal question is a real screen: ask a candidate to state which of two declared middleware actually ends up outermost. Most engineers with real production time in exactly one of these two frameworks get the other one backwards on the first try — which is diagnostic of whether they've internalized the mechanism or just pattern-matched one framework's docs.
    • 
        
  • Know the exception-safety asymmetry cold: Django's convert_exception_to_response() gives every middleware layer a free safety net; Starlette's BaseHTTPMiddleware gives you none by default. Shipping a FastAPI middleware that assumes Django-style guarantees is a real, recurring production bug, not a hypothetical.

08 Spaced recap

    

      
Resurfacing lesson 01 — the GIL & the concurrency model

      
Lesson 01 established the core mechanism: an event loop is one OS thread, and CPython still only lets one thread execute bytecode at a time. The killer follow-up in section 06 above is that exact fact wearing a FastAPI costume. FastAPI dispatches ordinary def path operations and sync dependencies to a background threadpool automatically — documented, deliberate behavior — but an async def endpoint runs directly on the event loop thread with no such safety net. One synchronous, blocking call inside it — a tight pure-Python loop, a blocking DB driver, a stray time.sleep — holds the only thread the whole process has for as long as it runs, freezing every other in-flight coroutine. It's the "holds the key, never lets go" failure mode from lesson 01's CPU-bound benchmark, just triggered from inside a request handler instead of a threading.Thread.
