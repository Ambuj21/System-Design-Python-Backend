System design fundamentals · Phase 2 · Lesson 21

CDNs

"A CDN caches static files closer to users" is true and almost useless. The real system lives in three decisions: what goes into the cache key, how you force thousands of autonomous edge nodes to forget something on command, and what stops a synchronized cache miss from becoming a denial-of-service attack your own architecture launches against itself.

01 Why "it's just a cache" fails the interview

In June 2021, a single Fastly customer made an ordinary, valid configuration change. Within minutes, a large share of Fastly's global edge network started returning errors — Amazon, Reddit, the UK government's gov.uk, and thousands of other sites went down for roughly 49 minutes. It wasn't a DDoS, and it wasn't a data-center fire. A latent bug in the edge/caching logic itself — the exact layer this lesson is about — had been sitting there since a deploy weeks earlier, waiting for the right input.

That's the level this topic actually operates at. "CDN" sounds like infrastructure trivia — "put a cache in front of it" — but a real CDN answer at senior/staff level has to cover: how a cache key is computed (get it wrong and you either poison the cache across users or destroy your hit ratio), how you invalidate an object across every one of thousands of edge locations without a global lock, and how you stop a routine cache-refresh event from stampeding your origin the moment it's most fragile.

02 The funnel: many edges, one origin

A CDN is a tree-shaped cache hierarchy wearing a global map. Understanding it means understanding two separate mechanisms: how a request finds "the nearest" node, and what that node does when it doesn't already have the answer.

Finding the node is either Anycast or DNS, and interviewers sometimes probe which one a given CDN uses. Anycast (Cloudflare's approach) announces the identical IP address from every point of presence via BGP; ordinary shortest-AS-path internet routing does the geographic steering for free, and failover is just BGP withdrawing a route — no DNS TTL to wait out. DNS-based routing (classic Akamai, and most multi-CDN setups) gives every PoP a distinct IP and has the CDN's authoritative nameservers return the "best" one per resolving nameserver's location (GeoDNS / latency-based routing) — coarser, since you're steered by your resolver's location rather than your own, but it doesn't require running your own Autonomous System.

What the node does once the request lands is the lookup hierarchy the diagram below draws: compute the cache key, check the local edge cache. Hit → served in single-digit milliseconds, nothing else happens. Miss → ask the regional shield tier. Shield hit → served to the edge, edge caches it, done. Shield miss → exactly one request goes to origin, no matter how many edges asked at once. That last step is origin shielding, and it's the subject of the console in the next section.

cache-key design

What actually goes into that key is the highest-leverage config decision a CDN setup makes: HTTP method, host, path, the query string, and whichever request headers the origin names in its Vary response header. Two failure modes pull in opposite directions:

  • Over-inclusive key → fragmentation. Hash the full querystring plus every header — session id, request id, the whole cookie jar — and no two requests ever collide. Every "hit" is a guaranteed miss, and the CDN degrades into an expensive pass-through with a rounding-error hit ratio. The cache_key_demo.py output in the hands-on section shows this exact failure caused by nothing more exotic than utm_source tracking noise.
  • Under-inclusive key → cache poisoning. Leave a response-affecting header out of both the key and Vary, and the edge will happily serve user B a response that was only correct for user A's session cookie — or serve a response that was only valid because of a header a proxy upstream stripped. This is a real, named vulnerability class (web cache deception, and header-based poisoning via unkeyed inputs like X-Forwarded-Host), not a theoretical concern.

invalidation & purging: the other half of the problem

Every cached object stops being trusted in one of three different ways, and conflating them is a common interview stumble.

Passive expiry (TTL). Cache-Control: max-age=300 — or the CDN-specific Surrogate-Control header, which Varnish/Fastly read instead of the browser-facing header so the edge TTL can outlive the browser TTL — just tells each edge independently when to stop trusting its copy. There's no coordination between edges; each runs its own clock. That gives you eventual consistency with a hard, known ceiling: propagation is bounded by max-age, never faster.

Active purge. When you can't wait out the TTL — a wrong price went live, a legal takedown, a leaked image — you push an explicit invalidation to every edge that might hold the object. Purge-by-URL only works if you can enumerate every cache-key variant, and per the cache-key section above, you usually can't. That's what surrogate keys (Fastly's term) / cache tags (Cloudflare's) solve: tag every response touching product 42 with a key like product-42 at write time, then purge that one tag and every edge drops every object carrying it, regardless of URL.

Soft purge — stale-while-revalidate (RFC 5861). A hard purge creates exactly the synchronized-miss stampede the console above simulates: one API call, and every edge holding the object misses at once. stale-while-revalidate sidesteps that — the edge keeps serving the technically-expired copy to every caller while exactly one background request refreshes it, the same single-flight discipline as origin shielding, just triggered by staleness instead of concurrent misses. Production CDNs run both: soft purge to avoid causing a stampede, origin shielding to contain one anyway (a cold PoP, a region failover, a purge that had to be hard because the content was actually wrong).

Phil Karlton's line — "there are only two hard things in computer science: cache invalidation and naming things" — has real teeth here. Storing one copy was never the hard part; coordinating tens of thousands of autonomous copies to agree on when they stop being true is.

purge propagation — order of magnitude, per each vendor's own docs (not measured here)
  • Fastly "Instant Purge": published as propagating across their global network in well under a second (Fastly documents figures around 150ms), because the purge is pushed through the same low-latency control plane that drives their edge config, not re-crawled per PoP.
  • Cloudflare purge-by-URL: documented as typically effective within seconds worldwide; a full "purge everything" is documented as taking up to roughly 30 seconds to reach every edge location.
  • CloudFront invalidation: AWS documents typical completion in "a few minutes" — an order of magnitude slower than a push-based control plane, and CloudFront additionally bills per invalidation path past a monthly free allotment, which nudges teams toward short TTLs plus versioned URLs over frequent invalidation calls.

These exact numbers move as vendors ship changes — treat the relative ordering (control-plane push << crawl/queue-based invalidation) as the durable lesson, not the millisecond counts.

04 How this shows up in systems you already use

  • Fastly Shielding. You designate one PoP near your origin as the "shield." Every other PoP's cache miss is routed through it instead of straight to origin, and Fastly's Varnish-derived core collapses concurrent misses for the same key into one in-flight request — the exact mechanism the console above visualizes and origin_shield_demo.py measures.
  • AWS CloudFront Origin Shield is the same idea as a named, opt-in feature (added 2020): an extra caching layer in the AWS region nearest your origin, specifically sold on reducing origin load and improving cache hit ratio for exactly this stampede scenario.
  • Cloudflare Tiered Cache auto-selects a nearby upper-tier data center to sit between edge and origin, so a cold cache in Jakarta can be filled from a warm neighbor in Singapore instead of round-tripping to an origin in Virginia.
  • Varnish Cache is the reference implementation much of this industry is built on (Fastly's core is Varnish-derived). Request coalescing has been built in since early Varnish releases, plus two purpose-built states worth knowing by name: grace mode (serve stale while revalidating — Varnish's stale-while-revalidate) and hit-for-pass (remember that a response was uncacheable, so you stop re-attempting to cache it on every request instead of hammering the backend each time).
  • Netflix Open Connect pushes the hierarchy to its logical extreme: caching appliances physically racked inside ISP networks, so "the edge" is inside the last mile itself rather than a regional PoP a few hops away.

05 Hands-on: cache keys and origin shielding, for real

Two scripts. The first shows cache-key design going right and wrong with real hashed keys. The second is the exact single-flight mechanism the console above draws, measured with real wall-clock numbers.

cache_key_demo.py
import hashlib
from urllib.parse import urlsplit, parse_qsl, urlencode

IGNORED_PARAMS = {"utm_source", "utm_medium", "utm_campaign", "gclid", "fbclid", "_ts"}


def naive_key(method: str, url: str, headers: dict) -> str:
    """What a lot of people ship first: hash the raw request line + all headers."""
    raw = f"{method} {url} {sorted(headers.items())}"
    return hashlib.sha1(raw.encode()).hexdigest()[:12]


def smart_key(method: str, url: str, headers: dict, vary: tuple[str, ...] = ("Accept-Encoding",)) -> str:
    """
    Production-grade key: method + lowercased host + case-sensitive path,
    sorted query with tracking params stripped, plus ONLY the header
    values this resource's Vary response header actually names.
    """
    parts = urlsplit(url)
    host = parts.netloc.lower()
    path = parts.path

    q = [(k, v) for k, v in parse_qsl(parts.query, keep_blank_values=True) if k not in IGNORED_PARAMS]
    q.sort()
    query = urlencode(q)

    vary_bits = tuple(headers.get(h, "") for h in vary)
    raw = "|".join([method.upper(), host, path, query, str(vary_bits)])
    return hashlib.sha1(raw.encode()).hexdigest()[:12]

     A/B bucket, auth-gated content) leaving Cookie out of the key is
     the classic cache-key-confusion bug: user B gets user A's response.
origin_shield_demo.py — the mechanism the console above visualizes
import asyncio, time

ORIGIN_LATENCY = 0.25
EDGE_POPS = 40
ORIGIN_CONCURRENCY_CAP = 8

origin_call_count = 0
origin_inflight_now = 0
origin_inflight_peak = 0
origin_rejected = 0


async def origin_fetch(key: str) -> str:
    global origin_call_count, origin_inflight_now, origin_inflight_peak, origin_rejected
    if origin_inflight_now >= ORIGIN_CONCURRENCY_CAP:
        origin_rejected += 1
        raise RuntimeError("503 origin overloaded")
    origin_call_count += 1
    origin_inflight_now += 1
    origin_inflight_peak = max(origin_inflight_peak, origin_inflight_now)
    try:
        await asyncio.sleep(ORIGIN_LATENCY)
        return f"<rendered:{key}>"
    finally:
        origin_inflight_now -= 1


async def edge_request_unshielded(pop_id: int, key: str):
    try:
        return await origin_fetch(key)
    except RuntimeError:
        return "ERR:503"


# per-key asyncio.Lock guarding a single in-flight origin fetch
_shield_locks: dict[str, asyncio.Lock] = {}
_shield_cache: dict[str, str] = {}


async def edge_request_shielded(pop_id: int, key: str):
    if key in _shield_cache:
        return _shield_cache[key]
    lock = _shield_locks.setdefault(key, asyncio.Lock())
    async with lock:
        if key in _shield_cache:          # double-checked: filled while we waited
            return _shield_cache[key]
        try:
            value = await origin_fetch(key)
        except RuntimeError:
            return "ERR:503"
        _shield_cache[key] = value
        return value


async def run_trial(shielded: bool):
    key = "/flash-sale/hero-banner.jpg"
    fn = edge_request_shielded if shielded else edge_request_unshielded
    results = await asyncio.gather(*(fn(i, key) for i in range(EDGE_POPS)))
    ok = sum(1 for r in results if not str(r).startswith("ERR"))
    return ok, EDGE_POPS - ok

The exercise — predict before you run it:

# Instead of all 40 PoPs expiring within the same ~millisecond, jitter
# their TTLs across a wider window before firing at the origin:
#
#   await asyncio.sleep(random.uniform(0, 5))   # per-edge, before calling fn(i, key)
#
# Rerun run_trial(shielded=False) with jitter added. Does origin_rejections
# still happen? Then answer: even after jitter fixes THIS run, why would a
# staff engineer keep the shield layer in production anyway?

Jitter fixes it here because it directly attacks the one thing causing the collision: everyone expiring at the same TTL-computed instant. But jitter only helps against TTL-driven synchronization. A hard purge, a newly-deployed PoP with a cold cache, or a multi-region failover all produce the exact same synchronized-miss pattern without going anywhere near a TTL clock — jitter has nothing to smooth there. That's why shielding is defense-in-depth and jitter is prevention for one specific cause: you want both, not either.

06 The senior/staff framing

What separates a strong answer from a weak one

  • Weak: "A CDN caches static assets closer to users to cut latency." Strong: "A CDN is a tiered cache with a consistency model you have to design on purpose. The cache key determines correctness and hit ratio simultaneously — get it wrong in either direction and you either leak data across users or pay for a cache that never hits. TTL gives you a bounded, coordination-free consistency window; explicit purge (ideally tag-based, not per-URL) gives you speed at the cost of a stampede risk, which is exactly what origin shielding and stale-while-revalidate exist to absorb."
  • The killer follow-up: "You just purged a leaked image from every edge. Forty seconds later, a user in Mumbai still sees the old one. Name three unrelated root causes for that exact symptom." A strong answer separates layers instead of guessing: (1) the browser's own cache — Cache-Control: immutable or a mismatched ETag, nothing to do with the CDN at all; (2) purge propagation lag, or a regional control-plane partition, still inside documented p99; (3) an intermediate cache your purge API doesn't reach — a corporate proxy, an ISP transparent cache, or a shield/tiered layer that wasn't in the purge's declared scope; (4) the purge targeted the wrong cache key — missed a Vary dimension like device type or a mobile app using a different key entirely.
  • The fix worth naming for the stampede case specifically: request coalescing (single-flight per cache key) plus stale-while-revalidate so the fallback under load is "serve slightly old," not "serve nothing."
  • Know the layers a request actually crosses: client → (possibly a proxy you don't control) → Anycast/DNS routing to a PoP → edge cache → optional regional shield → origin. A "CDN purge" only ever clears the layers you own.

08 Spaced recap

From Lesson 20 — Rate Limiting Algorithms

Lesson 20's token-bucket and sliding-window counters usually run at exactly this layer — most edge platforms let you attach a rate limiter to the same PoP the console above is stampeding, so an abusive client gets throttled before it ever reaches the cache-key lookup, let alone the origin. The distinction worth stating out loud in an interview: origin shielding defends against a stampede of legitimate, synchronized traffic (a TTL expiring on schedule, a flash sale everyone knew was coming); rate limiting defends against adversarial or simply excessive traffic from one identity. Same goal — protect the origin — different threat model, and production edge configs run both in the same request path, rate limiter first.
