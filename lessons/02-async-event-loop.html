Async/Await Mechanics & the Event Loop

What await literally does to a running coroutine — where it suspends, what continuation it leaves behind, and how a single thread decides what runs next — plus the exact mechanism behind the two-line fix for the blocking-call trap lesson 1 left hanging.

01 The trap sitting under lesson 1's cliffhanger

Ask a mid-level engineer what await does and you'll usually get: "it pauses execution until the result comes back, without blocking the thread." That's a description of the effect. It says nothing about the mechanism — and staff-level interviews probe the mechanism. What exactly gets suspended? Where does the paused state live while you wait? What decides which coroutine runs next, and in what order? Go vague here and the interviewer already suspects you've never had to debug a stalled event loop in production.

Lesson 1 ended on a single sentence: a synchronous, CPU-heavy call inside an async def handler freezes every other in-flight request on that worker. This lesson is the mechanism behind that sentence — await, the ready queue, and the two real fixes (run_in_executor / asyncio.to_thread) that hand blocking work off the loop thread entirely.

Every number in the console and benchmark cards below was produced by running the scripts in the hands-on section, right here, on CPython 3.10.12 — not estimated.

02 Three stations, one running slot

An event loop is not a pool of workers. It's one thread cycling through three stations: a ready queue of coroutines waiting their turn, a single running slot where bytecode actually executes, and an OS-level selector holding the coroutines that are out waiting on the network or disk.

Notice what's not in this picture: a second running slot. There is exactly one. If the coroutine in it never hits an await — because it called something synchronous and blocking instead — the loop never gets a turn to pop anything else. That's the entire blocking-call trap in one sentence, and the console below makes it visible.

04 How this shows up in systems you already use

  • FastAPI's request lifecycle, end to end. uvicorn (the ASGI server) accepts a connection and wraps each incoming request in its own asyncio.Task via loop.create_task. Starlette routes it to your path operation and checks asyncio.iscoroutinefunction: an async def handler is awaited directly on the loop thread; a plain def handler is routed through starlette.concurrency.run_in_threadpool, which — like asyncio.to_thread — hands it to a worker thread and awaits the result. That's why "just use def instead of async def" is a legitimate, if blunt, fix for an accidentally-blocking FastAPI handler.
  • uvloop replaces the standard library's selectors-based event loop with one built on libuv (the same C library behind Node.js), implementing the exact ready-queue/selector cycle from the diagram above in C instead of Python. It's a drop-in loop policy swap and is commonly 2-4x faster on I/O-heavy workloads for exactly that reason — less Python-level bookkeeping per loop iteration.
  • asyncpg vs psycopg2. asyncpg speaks the PostgreSQL wire protocol directly in an async-native way — every network round trip is a real await, a real suspension point. psycopg2's C extension makes a genuinely blocking socket call; used inside async def without to_thread, it's the exact blocking-call trap from this lesson, and it's one of the single most common production incidents in Python backends that "moved to async" without auditing every driver in the stack.
  • httpx.AsyncClient / aiohttp connection pools are built entirely on this suspend/resume model — a pool of sockets registered with the selector, coroutines parked on whichever one frees up, no thread per connection.
  • Celery / background job queues are the answer when the work is too heavy even for a thread pool — genuinely CPU-bound or long-running. to_thread moves work off the loop thread but still competes for the GIL and the process's memory; a task queue moves it to an entirely separate process (or machine), the same threading-vs-multiprocessing tradeoff from lesson 1, now applied to "what do I do with the work I just took off my event loop."

05 Hands-on: prove the suspension, not just the speedup

Two scripts. The first is the easy, well-known result. The second is the one that actually explains the blocking-call trap — it measures how late an unrelated coroutine's heartbeat lands, not just total wall time.

bench_gather.py
import asyncio, time

async def fetch(n, delay=0.3):
    await asyncio.sleep(delay)
    return n

async def sequential():
    t0 = time.perf_counter()
    r1 = await fetch(1)
    r2 = await fetch(2)
    r3 = await fetch(3)
    return time.perf_counter() - t0

async def concurrent_gather():
    t0 = time.perf_counter()
    await asyncio.gather(fetch(1), fetch(2), fetch(3))
    return time.perf_counter() - t0

async def concurrent_create_task():
    t0 = time.perf_counter()
    tasks = [asyncio.create_task(fetch(i)) for i in (1, 2, 3)]
    await asyncio.gather(*tasks)
    return time.perf_counter() - t0

async def main():
    print(f"sequential (await, await, await)   : {await sequential():.3f}s")
    print(f"asyncio.gather(...)                : {await concurrent_gather():.3f}s")
    print(f"create_task + gather               : {await concurrent_create_task():.3f}s")

asyncio.run(main())
output (this machine, CPython 3.10.12)
sequential (await, await, await)   : 0.901s
asyncio.gather(...)                : 0.301s
create_task + gather               : 0.301s

create_task and gather land on the same number because gather(fetch(1), fetch(2), fetch(3)) already wraps each bare coroutine in a Task internally before scheduling it — that's what makes it eligible for the ready queue at all. A bare coroutine object does nothing until something drives it; wrapping it in a Task is what gets loop.call_soon() called on its first step.

bench_blocking.py
import asyncio, time

def blocking_db_call():
    # e.g. a synchronous DB driver call -- no `await` possible inside it
    time.sleep(0.3)
    return "row"

async def heartbeat(label, t0, n=6, interval=0.05):
    ticks = []
    for _ in range(n):
        await asyncio.sleep(interval)
        ticks.append(round(time.perf_counter() - t0, 3))
    print(f"{label} tick times, elapsed since gather() started (want ~0.05 apart): {ticks}")

async def bad_handler(t0):
    blocking_db_call()          # called directly, NOT awaited -> freezes the loop
    print(f"bad_handler returned at t={time.perf_counter()-t0:.3f}s (ran ON the loop thread)")

async def good_handler(t0):
    await asyncio.to_thread(blocking_db_call)   # handed to the default ThreadPoolExecutor
    print(f"good_handler returned at t={time.perf_counter()-t0:.3f}s (ran on a WORKER thread)")

async def run_bad():
    print("--- direct blocking call inside async def ---")
    t0 = time.perf_counter()
    await asyncio.gather(bad_handler(t0), heartbeat("heartbeat", t0))
    print(f"total wall time: {time.perf_counter()-t0:.3f}s\n")

async def run_good():
    print("--- same work via asyncio.to_thread ---")
    t0 = time.perf_counter()
    await asyncio.gather(good_handler(t0), heartbeat("heartbeat", t0))
    print(f"total wall time: {time.perf_counter()-t0:.3f}s")

async def main():
    await run_bad()
    await run_good()

asyncio.run(main())
output (this machine, CPython 3.10.12)
--- direct blocking call inside async def ---
bad_handler returned at t=0.300s (ran ON the loop thread)
heartbeat tick times, elapsed since gather() started (want ~0.05 apart): [0.351, 0.401, 0.451, 0.501, 0.552, 0.602]
total wall time: 0.602s

--- same work via asyncio.to_thread ---
good_handler returned at t=0.305s (ran on a WORKER thread)
heartbeat tick times, elapsed since gather() started (want ~0.05 apart): [0.054, 0.104, 0.155, 0.205, 0.255, 0.306]
total wall time: 0.306s

In the bad run, heartbeat's first tick — which should land at ~0.05s — lands at 0.351s. It isn't slow; it's frozen, because the one running slot is occupied by time.sleep(0.3) and there's no await point for the loop to reclaim control at. In the good run every tick lands within a few milliseconds of its target, because to_thread gave the loop a real suspension point immediately.

what to_thread actually does — real CPython 3.10 stdlib source
# Lib/asyncio/threads.py
async def to_thread(func, /, *args, **kwargs):
    loop = events.get_running_loop()
    ctx = contextvars.copy_context()
    func_call = functools.partial(ctx.run, func, *args, **kwargs)
    return await loop.run_in_executor(None, func_call)

# Lib/asyncio/base_events.py — what run_in_executor(None, ...) does with it
def run_in_executor(self, executor, func, *args):
    if executor is None:
        executor = self._default_executor or concurrent.futures.ThreadPoolExecutor(...)
        self._default_executor = executor
    return futures.wrap_future(executor.submit(func, *args), loop=self)

to_thread is a thin wrapper: it copies the current contextvars context (so context-local state survives the thread hop) and calls run_in_executor(None, ...), which submits your function to a concurrent.futures.ThreadPoolExecutor — the default pool sizes itself to min(32, os.cpu_count() + 4), 16 workers on this 12-core machine. executor.submit() returns a concurrent.futures.Future, a completely different object from an asyncio.Future. futures.wrap_future() bridges the two: it creates a real asyncio.Future and registers a done-callback on the thread-pool future that, when the worker thread finishes, uses loop.call_soon_threadsafe() to safely resolve the asyncio Future from the correct thread. await-ing that asyncio Future is what actually suspends your coroutine — mechanically identical to awaiting a socket read, just with a thread-pool worker instead of the OS selector on the other end.

the exercise — predict before you run it

Rewrite concurrent_gather() so that fetch() calls time.sleep(delay) directly instead of await asyncio.sleep(delay) — same total simulated work, no actual await inside the coroutine. Predict the new wall time for asyncio.gather(fetch(1), fetch(2), fetch(3)) before running it. (It's 0.9s, not 0.3s — gather only multiplexes coroutines at their await points; a coroutine that never yields gets none of the benefit, no matter how many siblings are gathered with it.)

06 The senior/staff framing

What separates a strong answer from a weak one

  • Weak: "await pauses execution until the result is ready, without blocking the thread." Strong: "await suspends the coroutine's frame at that point, registers the coroutine as a callback on the awaited Future, and returns control to the loop's _run_once(). The loop drains its FIFO ready queue, then blocks in epoll_wait until an OS event or the next scheduled timer fires — that's the actual sleep."
  • The killer follow-up: "Your endpoint runs asyncio.gather(fetch_a(), fetch_b()), and fetch_b happens to call requests.get(...) instead of an async HTTP client. What happens?" Nothing about gather forces concurrency — it only interleaves coroutines at their own await points. If fetch_b never yields, the loop is captured for its entire blocking duration, fetch_a's progress stalls too, and you're back to the sequential case with none of the intended overlap. This is precisely what the exercise above measures.
  • The fix worth naming precisely: await asyncio.to_thread(requests.get, url) or swap to httpx.AsyncClient — the first relocates the blocking call to a worker thread, the second removes the blocking call entirely by speaking the protocol asynchronously.
  • Worth volunteering unprompted: Python 3.11's asyncio.TaskGroup is the structured-concurrency replacement for gather — on the first exception it cancels every sibling task automatically and raises an ExceptionGroup, closing the classic "gather leaves orphaned tasks running after one of them raises" footgun that plain gather has.

08 Spaced recap

Resurfacing lesson 1 — the GIL & the concurrency model

The running slot in today's diagram is the same one-key room from lesson 1, just relabeled. asyncio doesn't add a second key — it's a scheduler that time-slices one Python thread at every await boundary, still bound by the same GIL constraint that only one thread executes bytecode at a time. That's exactly why the blocking-call trap exists: a coroutine that never yields behaves like the GIL-hogging pure-Python loop from lesson 1's threading benchmark, except now it starves cooperative coroutines instead of OS threads. And the fix is the same shape as lesson 1's, one level down: to_thread hands the blocking work to another OS thread — cheap, shares memory, still GIL-bound for actual Python bytecode, but free during the blocking syscall itself, which is exactly the gap the loop needs reclaimed.
