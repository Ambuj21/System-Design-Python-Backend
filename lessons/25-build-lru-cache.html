Applied system design in Python · Phase 3 · Lesson 25

Build an LRU/LFU Cache in Python

Turning Lesson 06 and 13's caching theory into code means answering one brutally specific question: how do you make both get(key) and put(key, value) run in true O(1) time, with no linear scan hiding inside a "simple" list? A doubly linked list plus a hashmap is the entire answer for LRU — and swapping the eviction signal from recency to frequency turns out to be a much bigger structural change than most candidates expect.

01 Why this is a trap even though everyone's seen it

"Implement an LRU cache" (LeetCode 146) is one of the most over-prepped questions in the entire interview circuit, which is exactly why it stops being a coding question at senior/staff level and becomes a systems-understanding question. Almost everyone has memorized class LRUCache(OrderedDict) with move_to_end and popitem(last=False). Almost nobody can explain, from memory, why that one-liner is actually O(1) — or rebuild the mechanism by hand when the interviewer says "now do it without OrderedDict."

The real bar isn't "can you produce working code." It's whether you understand that the O(1) guarantee comes from two structures cooperating — a hashmap for O(1) lookup, and a doubly linked list for O(1) reordering and eviction without shifting anything else — and whether you can reason about what breaks when the eviction signal changes from "when was it touched" (LRU) to "how often has it been touched" (LFU). Lessons 06 and 13 covered eviction policies and multi-layer cache coordination conceptually. This lesson is where that theory has to compile.

The most common failure mode isn't getting the algorithm wrong — it's proposing something that looks O(1) but has a hidden O(n) inside it: an array with "just remove and re-insert the touched element," a Python list where .remove() silently scans, or an LFU cache that finds the minimum frequency by scanning every key on every eviction. Sections 03 and 05 are built specifically to make that hidden cost visible.

02 One hashmap, one doubly linked list, four pointer writes

The hashmap never stores a value — it stores key → node pointer. The doubly linked list is where the actual value lives, threaded through prev/next pointers in strict recency order. Touching a key means: hashmap lookup (O(1)), unlink that node from wherever it sits (O(1), four pointer writes), relink it at the head (O(1), four more). Nothing else in the list moves.

That's the whole mechanism for LRU. LFU keeps the same hashmap-for-lookup idea but replaces the single ordered list with a list per frequency — so eviction has to find the lowest occupied frequency, not just walk to a fixed tail. Section 03 makes that distinction concrete.

04 The exact structure, in production, right now

  • functools.lru_cache (CPython standard library). When you decorate a function with @lru_cache(maxsize=128), you are using this lesson's mechanism, precompiled: CPython's C implementation (_functoolsmodule.c) maintains a circular doubly linked list plus a dict, exactly the shape built in section 05, just faster than anything you'd write in pure Python.
  • Java's LinkedHashMap(capacity, 0.75f, true) with removeEldestEntry overridden is the textbook OOP version of the same idea — an access-ordered doubly linked list threaded directly through the hashmap's own entries. Most "implement LRU" interview answers in Java are this four-line subclass.
  • InnoDB's buffer pool doesn't use plain LRU. MySQL inserts new pages at the midpoint of the list (around the 5/8 mark), not the head, specifically so one large sequential scan — a backup job, an unindexed query — can't race through and evict the entire warm working set just by touching everything once.
  • ARC (Adaptive Replacement Cache) — used in ZFS's page cache and in enterprise storage controllers — runs two LRU lists side by side (recently-used-once vs. frequently-used) and adaptively shifts the boundary between them. It's a production admission that pure LRU and pure LFU each fail on real workloads often enough that hedging between the two signals wins in practice.
  • Redis's allkeys-lru / allkeys-lfu maxmemory-policy (lesson 06 covered the sampling and decay mechanics in depth) is the probabilistic, approximate, production-scale version of the two exact structures built by hand in section 05 — Redis just refuses to pay for a perfectly precise doubly linked list across millions of keys.

05 Hands-on: build both, then measure the O(1) claim

lru_lfu.py — the LRU cache
class _Node:
    __slots__ = ("key", "value", "prev", "next")
    def __init__(self, key=None, value=None):
        self.key, self.value = key, value
        self.prev = self.next = None

class LRUCache:
    def __init__(self, capacity):
        self.capacity = capacity
        self.map = {}                 # key -> _Node   (O(1) lookup)
        self.head = _Node()           # sentinel, MRU side
        self.tail = _Node()           # sentinel, LRU side
        self.head.next = self.tail
        self.tail.prev = self.head

    def _unlink(self, node):
        node.prev.next = node.next
        node.next.prev = node.prev

    def _push_front(self, node):
        node.next = self.head.next
        node.prev = self.head
        self.head.next.prev = node
        self.head.next = node

    def get(self, key):
        node = self.map.get(key)
        if node is None:
            return -1
        self._unlink(node)
        self._push_front(node)        # every hit refreshes recency
        return node.value

    def put(self, key, value):
        if key in self.map:
            node = self.map[key]
            node.value = value
            self._unlink(node)
            self._push_front(node)
            return None
        evicted = None
        if len(self.map) >= self.capacity:
            lru_node = self.tail.prev          # O(1): tail.prev is always the victim
            self._unlink(lru_node)
            del self.map[lru_node.key]
            evicted = lru_node.key
        node = _Node(key, value)
        self.map[key] = node
        self._push_front(node)
        return evicted
lru_lfu.py — the LFU cache (frequency buckets, not a heap)
from collections import OrderedDict, defaultdict

class LFUCache:
    def __init__(self, capacity):
        self.capacity = capacity
        self.min_freq = 0
        self.val = {}                              # key -> value
        self.freq = {}                              # key -> freq
        self.buckets = defaultdict(OrderedDict)      # freq -> {key: None}
        # buckets[f] is itself an LRU ring of all keys currently AT frequency f —
        # that's what makes the tie-break "oldest at that frequency" also O(1).

    def _bump(self, key):
        f = self.freq[key]
        del self.buckets[f][key]
        if not self.buckets[f] and f == self.min_freq:
            self.min_freq += 1                       # that bucket is now empty; the floor moved up
        self.freq[key] = f + 1
        self.buckets[f + 1][key] = None

    def get(self, key):
        if key not in self.val:
            return -1
        self._bump(key)
        return self.val[key]

    def put(self, key, value):
        if self.capacity <= 0:
            return None
        if key in self.val:
            self.val[key] = value
            self._bump(key)
            return None
        evicted = None
        if len(self.val) >= self.capacity:
            # popitem(last=False): the OLDEST key in the LOWEST-frequency bucket —
            # O(1) because min_freq is tracked, never scanned for.
            evicted, _ = self.buckets[self.min_freq].popitem(last=False)
            del self.val[evicted]
            del self.freq[evicted]
        self.val[key] = value
        self.freq[key] = 1
        self.buckets[1][key] = None
        self.min_freq = 1
        return evicted

Complexity, precisely stated: both classes give get and put worst-case O(1) per call — a fixed number of dict operations plus a fixed number of pointer/bucket rewrites, independent of how many keys are resident. Space is O(capacity) for LRU. For LFU it's O(capacity) for val/freq plus O(number of distinct frequency levels currently in use) for buckets, which is itself bounded by capacity — you can never have more populated frequency buckets than resident keys. The one honest asterisk: Python's dict is O(1) amortized average-case — an occasional resize is O(n) but happens rarely enough to amortize away, and worst-case O(n) is only reachable with adversarial hash collisions, essentially never in practice.

Identical operations, identical capacity, two different survivors. LRU evicted A — the single most-accessed key in the whole trace — purely because nothing touched it after step 4. LFU protected it, and evicted B instead once B and C tied on frequency and the tie broke to whichever was touched longer ago.

=== 10-op trace: one extra GET A inserted right before PUT D ===
 LRU   ... (same first 8 ops) ...
 LRU   GET A  -> 1
 LRU   PUT D=4  (evicted B)
 LRU final resident order (MRU->LRU): ['D', 'A', 'C']

 LFU   ... (same first 8 ops) ...
 LFU   GET A  -> 1
 LFU   PUT D=4  (evicted B)
 LFU final (key, freq): [('A', 5), ('C', 2), ('D', 1)]

LRU's victim flips — from A to B — because one extra touch was enough to push A back to the head, ahead of both B and C. LFU's victim doesn't move — it was already B, because LFU had already fully protected A on frequency alone; one more hit on an already-dominant key changes nothing about who's weakest. That's the practical difference between the two policies in one sentence: LRU's decision can flip on the very last operation before eviction; LFU's decision is usually already decided long before eviction happens.

the O(1) claim, illustrated against a naive O(n) LRU

A "naive" LRU using a plain Python list — list.remove(key) then list.insert(0, key) on every touch — is still correct. It just isn't O(1): both of those list operations are O(n) in the worst case. The numbers below are illustrative — a representative shape of what 15,000 mixed get/put operations at growing capacity looks like, not a specific captured run — because the actual crossover point shifts with your machine, Python build, and key-access distribution. Time it yourself with timeit against your own workload before quoting a number in an interview.

=== O(1) vs naive-O(n) LRU, 15,000 mixed get/put ops each, best-of-3 (illustrative shape) ===
  capacity   O(1) DLL+hashmap     naive list    ratio
        50          0.0062s        0.0042s     0.7x
       500          0.0062s        0.0128s     2.1x
      4000          0.0070s        0.0645s     9.2x
     20000          0.0069s        0.0710s    10.4x

Read the small-capacity row honestly: at capacity 50, the naive list is faster. list.remove/list.insert are C-level memmove over contiguous memory — extremely fast per element — while every DLL touch pays real Python-level object overhead (attribute access on a _Node, four separate pointer writes). Big-O is about the trend as N grows, not a promise that the asymptotically better algorithm wins at every size. By capacity 4,000 the O(1) structure's flat cost — it barely moves from 0.006s to 0.007s across a 400x range of capacity — pulls decisively ahead of a workload whose per-operation cost grows with capacity. That crossover point, not the O(1)-vs-O(n) label by itself, is what a staff-level answer should be able to locate and explain.

06 The senior/staff framing

What separates a strong answer from a weak one

  • Weak: "I'd use Python's OrderedDict — move_to_end and popitem(last=False) give me O(1) LRU for free." Strong: same starting point, but able to go one level down without hesitating: "OrderedDict is a doubly linked list plus a dict internally — that's exactly the structure I'd hand-roll if the interviewer took the built-in away, or if I were doing this in a language without one." Reaching for the built-in isn't the weakness; not being able to rebuild or explain the mechanism underneath it is.
  • The killer follow-up: "Your LRU cache backs a hot endpoint hit by 200 concurrent request-handling threads. Where exactly does the lock go, and what does it cost you?" Both get and put mutate shared state — a cache hit is not read-only here, because even a hit rewrites four pointers. Every call, hits included, needs the lock, which turns an O(1) cache into a serialization point for the whole endpoint. The GIL (lesson 01) protects one pointer write from tearing mid-instruction, but not the multi-step "unlink, then relink" sequence from a race between two threads unlinking the same node.
  • The second follow-up, specific to this lesson: "This LFU cache has been in production for months — does its hit rate degrade over time, and why?" Frequency counters only go up. A key that was hot during a launch three months ago can out-rank every genuinely hot key today and never get evicted, because nothing decrements it. LRU has no such failure mode — it has no memory beyond "was it touched recently," which is its own weakness (one big scan can evict the entire working set) but not this one. Naming the fix — periodic counter decay/halving, or Redis's actual lfu-decay-time — is what separates "I implemented LFU" from "I understand what LFU costs in production."

08 Spaced recap

Resurfacing: Lesson 13 — Caching Strategies & Invalidation at the Architecture Level

Lesson 13 zoomed all the way out — CDN, edge, application cache, database, and the coordination problems that appear the moment more than one of those layers is caching the same data on a different clock. Today's LRUCache/LFUCache classes are the mechanism sitting inside just one node of that picture: when lesson 13 talked about a cache "evicting a key," this is the literal code — hashmap plus doubly linked list, or hashmap plus frequency buckets — deciding which key, in O(1), with no scan of the keyspace. Get this layer wrong (a frequency counter that never decays, an eviction policy mismatched to the real access pattern) and lesson 13's invalidation problems don't go away — they compound, because stale-but-protected data now survives exactly when the multi-layer coordination story most needed it gone.
