Caching Strategies & Invalidation at the Architecture Level

Multi-layer caching — CDN, edge, application, database — turns "is this data fresh?" into a coordination problem across systems that have no idea the others exist. This is the real mechanism behind TTLs, purges, and versioned keys, why they disagree with each other by design, and how a cache-key mistake turns a performance feature into a data leak.

01 Why this is where interviews go sideways

Ask a mid-level engineer how they'd speed up a slow endpoint and the reflex answer is "add a cache." That instinct is correct and the answer is incomplete — caching is trivial to bolt on and dangerously easy to get wrong, and the part that actually separates levels isn't "do you know Redis exists," it's "what happens the instant the underlying data changes." A cache with no invalidation story isn't a cache. It's a bug with a TTL attached to it.

In any system past toy scale you don't have one cache, you have a stack of them: a browser's HTTP cache, a CDN edge, an application-level cache (Redis, per lesson 06), and the database's own internal buffer pool — each with an independently configured expiry clock that has no idea the other layers exist. The interview trap is treating "cache invalidation" as one problem with one fix. It's a coordination problem across N independently-clocked systems, and the honest answer to "is this data fresh" becomes "fresh according to which layer, measured when."

There's a second, sharper trap hiding in the same topic: cache key design. Get the invalidation strategy right but the key wrong — miss one dimension the response actually depends on, like which user is asking — and you don't get stale data, you get one user's private response served to somebody else. That's not a performance bug anyone escalates gently; it's a security incident. Both halves of this lesson — how caches lose track of what's true, and how caches accidentally mix up who's asking — sound like implementation detail and behave like staff-bar topics, because both failure modes are silent until the exact moment they aren't.

02 Reads go one way. Writes land somewhere else entirely.

Every read for the same product travels the same left-to-right path through every layer. A write skips all of it and lands directly at the source of truth — which means invalidation has to travel backward, against the grain of the read path, and it doesn't do it instantly.

Before any invalidation strategy matters, the cache key has to be designed correctly — get this wrong and the strategy is irrelevant, because you're serving the wrong content to the wrong person. A key needs to encode every dimension the response actually varies on: locale, currency, the requester's auth/entitlement level, feature-flag cohort, pagination and sort order, response encoding. Omit one of those at a shared layer — a CDN or reverse proxy sitting in front of many users — and you get a security bug, not a performance bug: User A's personalized response gets cached under a key that User B's identical-looking request also matches, and B is served A's data. This class of bug has a name, web cache deception / web cache poisoning, and it shows up in bug-bounty reports on a regular basis, almost always traced to a key that didn't include a dimension the origin response actually depended on.

The opposite mistake costs money instead of security: over-including dimensions fragments the cache. A key that varies on raw query-string order, or on a session ID that changes every login, can be technically correct and still have a near-zero hit rate — a cache that's never reused isn't a cache, it's overhead. The fix is canonicalization: sort query parameters before hashing them into the key, strip parameters that don't affect the response (tracking params are the usual offender), and fold in only the dimensions that genuinely change the output. The hands-on section below builds one specific, powerful key-design pattern — the content-hash / versioned key — that sidesteps the invalidation problem for an entire class of cacheable data.

04 How this shows up in systems you already use

  • Facebook/Meta's TAO, the read-through cache sitting in front of the social graph, solves cross-region coherence with an invalidation pipeline (historically called McSqueal) that pushes deletes out to every region's cache after a write commits — explicit purge, propagated at global scale, because TTL alone was too slow for a graph where "is this still my friend" needs to be right almost immediately.
  • Scaling Memcache at Facebook (NSDI '13) introduced leases — a token-based single-flight mechanism baked directly into Memcached — specifically to stop thundering herds: when a key misses, exactly one client gets a lease to go fetch it from the DB; everyone else is told to hold. The hands-on section below builds the same idea from scratch in ~20 lines of Python.
  • Fastly and Cloudflare's "surrogate keys" / cache tags let you tag many cached objects with one logical key and purge all of them in a single call — Fastly's own documentation states purges propagate across its edge network in well under a second. This is explicit purge at CDN scale, and it's exactly why large sites can invalidate "every page mentioning this product" instantly instead of waiting out a TTL.
  • Webpack, Vite, and basically every modern JS bundler ship assets as app.a3f9c2.js — a content hash baked into the filename. Paired with Cache-Control: public, max-age=31536000, immutable, this is the versioned-key pattern in production: a one-year browser cache is safe specifically because the filename changes the instant the content does, so there's nothing to invalidate.
  • MySQL removed its built-in query cache entirely in 8.0, after 15+ years, because the invalidation model was exactly this lesson's coherence problem taken to its worst case: one global mutex, and any write to a table invalidated every cached query touching it, which collapsed throughput under write-heavy load. It's the clearest real-world proof that an invalidation strategy can be so expensive it's worse than not caching at all.
  • stale-while-revalidate (RFC 5861), supported by most modern CDNs and browsers via the Cache-Control header, is the elegant middle ground this lesson's console doesn't have a tab for: serve the stale value immediately to whoever asks, kick off a background refetch, and let the next request get the fresh value — bounded staleness with zero added latency and, as a side effect, no thundering herd, because only one background refetch runs per expiry.

05 Hands-on: build the fix, not just the diagram

Two things worth proving with real code instead of taking on faith: that an unprotected TTL cache really does let a thundering herd through, and that a versioned key really does produce a different key for different content with zero coordination required.

bench_cache.py
import hashlib
import threading
import time

DB_CALLS = 0
DB_CALLS_LOCK = threading.Lock()


def slow_db_read(key):
    """Simulates a real DB round trip -- the thing every cache exists to avoid."""
    global DB_CALLS
    with DB_CALLS_LOCK:
        DB_CALLS += 1
    time.sleep(0.05)  # 50ms, roughly a realistic uncached read under load
    return f"value-for-{key}"


class NaiveTTLCache:
    """No stampede protection. Every thread that observes a miss/expiry
    goes straight to the DB itself -- this is the default behavior of a
    plain dict-with-expiry or an unprotected Redis GET-then-SET."""

    def __init__(self):
        self.store = {}  # key -> (value, expires_at)

    def get(self, key, ttl, loader):
        entry = self.store.get(key)
        now = time.monotonic()
        if entry and entry[1] > now:
            return entry[0]
        value = loader(key)
        self.store[key] = (value, now + ttl)
        return value


class SingleFlightTTLCache:
    """Stampede protection via a per-key lock ('lease' in Facebook's Memcache
    paper terminology). Only the first thread to see the miss calls the
    loader; every other thread blocks on that same lock and then reads the
    value the first thread just filled in -- no redundant DB calls."""

    def __init__(self):
        self.store = {}
        self.locks = {}
        self.locks_guard = threading.Lock()

    def get(self, key, ttl, loader):
        entry = self.store.get(key)
        now = time.monotonic()
        if entry and entry[1] > now:
            return entry[0]

        with self.locks_guard:
            lock = self.locks.setdefault(key, threading.Lock())

        with lock:
            # Re-check: whoever held the lock before us may have refilled it.
            entry = self.store.get(key)
            now = time.monotonic()
            if entry and entry[1] > now:
                return entry[0]
            value = loader(key)
            self.store[key] = (value, now + ttl)
            return value


def hammer(cache, key, ttl, workers=200):
    threads = [
        threading.Thread(target=cache.get, args=(key, ttl, slow_db_read))
        for _ in range(workers)
    ]
    t0 = time.perf_counter()
    for t in threads:
        t.start()
    for t in threads:
        t.join()
    return time.perf_counter() - t0


def content_hash_key(prefix: str, payload: bytes) -> str:
    """Versioned-key pattern: the key IS a fingerprint of the content, so a
    write never mutates an existing key -- it produces a brand-new one.
    Nothing needs to be invalidated because nothing was ever overwritten."""
    digest = hashlib.sha256(payload).hexdigest()[:10]
    return f"{prefix}:{digest}"

Read the wall-clock column again before you read the DB-call column. Both caches finish in ~0.06s — because the 200 threads are all I/O-bound and overlap freely (this is lesson 01's GIL lesson showing up again: time.sleep releases it). Wall-clock time hides the damage completely. The naive cache pushed 200x the query load the DB actually needed onto it, in the same instant, and nothing about "the endpoint feels fast" would tell you that happened. This is exactly why thundering herd is a production incident that shows up as "the database fell over" with no slow individual request to point at.

The exercise — predict before you run it, then check:

# SingleFlightTTLCache currently makes every waiting thread block until the
# leader finishes, then return the FRESH value. Extend it into a
# stale-while-revalidate variant instead:
#
#   - if a key is expired but an old value still exists in self.store,
#     let ONE thread acquire the lock and refill it in the background
#     (or just synchronously for this exercise) -- exactly as today --
#   - but every OTHER concurrent caller should return the OLD value
#     immediately instead of blocking on the lock.
#
# 1. Predict: does DB_CALLS change from the single-flight run above?
# 2. Predict: does the 200-thread wall-clock time change, and if so,
#    which direction?
# 3. Implement it, rerun hammer(), and check both predictions.

DB_CALLS stays at 1 — you still only refill once. Wall time drops close to zero for the 199 waiters, because they never touch the lock at all; they read entry[0] straight out of self.store even though entry[1] says it's expired. That's the entire trick behind stale-while-revalidate: staleness bounded to "however long one refill takes," paid by nobody's latency.

06 The senior/staff framing

What separates a strong answer from a weak one

  • Weak: "I'd just set a short TTL so the cache doesn't go stale." Strong: "TTL bounds staleness, it doesn't eliminate the coherence window — for that window, multiple layers can disagree about 'current' and both be technically correctly configured. Explicit purge shrinks that window on every layer you control, but it can't reach a client's local disk cache at all. Versioned keys eliminate the coherence bug entirely — nothing is ever mutated, so nothing is ever 'wrong' — at the cost of storage growth and needing one atomic place that says which key is current. I'd match the strategy to blast radius: cheap idempotent reads get TTL, anything financially or security sensitive gets purge-plus-versioning with a short TTL backstop."
  • The killer follow-up: "Your CDN purge succeeds instantly and Redis clears in milliseconds, but support tickets say some users see the old price for up to a year. What's actually happening, and how do you fix it without losing cacheability?" The trap answer is "the purge is broken." It isn't — purge has no path to a browser's local cache at all, and the response was almost certainly served with a long max-age. The fix isn't a bigger purge, it's a shorter client TTL on mutable data, or better: put the mutable field behind a versioned reference so the browser cache being long-lived stops being the problem in the first place.
  • The nuance worth naming unprompted: production systems don't pick one strategy, they layer all three — a short TTL everywhere as a universal backstop that bounds worst-case staleness even if a purge silently fails, explicit purge for the fast path on layers you control, and versioned/immutable keys for anything that can be content-addressed. A candidate who presents these as mutually exclusive hasn't operated a cache that mattered.
  • Know the real numbers, not just the shape of the argument: a fingerprinted static asset gets a max-age in the ~1-year range because it's provably safe to; an API response behind a CDN typically gets seconds-to-low-minutes; an app-level cache entry (Redis) is usually seconds-to-tens-of-seconds. Be ready to state which number you're assuming out loud and defend it — that's the same discipline lesson 11 pushed for capacity numbers.

07 Check your understanding

Before you move on

A product-price API is cached at three layers: CDN edge (TTL 300s), app-level Redis via cache-aside (TTL 30s), and the client's own HTTP cache (Cache-Control: max-age=600). A pricing bug is fixed and deployed at 2:00pm. A support ticket at 2:04pm says a customer is still seeing the wrong price.

Is that expected, and which layer is almost certainly responsible? Now the harder part: if the fix needs to be visible everywhere within 5 seconds for compliance reasons, which invalidation strategy would you switch to, for which layer or layers specifically — and which one layer can you never fully guarantee, even after switching?

Answer this back to your mentor before starting the next lesson.

08 Spaced recap

Resurfacing lesson 06 — Redis Caching Patterns

Lesson 06 covered the mechanics of a single Redis cache — cache-aside vs. write-through vs. write-behind, eviction under maxmemory (LRU/LFU), and why a per-key TTL is usually the right default. Everything in that lesson was about one cache with one clock. This lesson is what happens when you stack several of those — a browser cache, a CDN, and Redis itself — each faithfully running the exact patterns lesson 06 taught, with no shared awareness of each other. The single-flight lock built in the hands-on section above is a direct extension of lesson 06's cache-aside pattern: same "check cache, miss, fetch, populate" shape, with one lock added specifically to stop N concurrent cache-aside misses from becoming N concurrent DB hits. If lesson 06's patterns felt like "the whole story" at the time, this lesson is the reminder that a single Redis instance's correctness doesn't automatically add up to system-wide coherence.
