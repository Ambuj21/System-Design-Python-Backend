Design a Messaging System (WhatsApp-like)

The interview isn't "can you draw boxes for chat." It's whether you can name the exact receipt state machine, explain what happens when a recipient's phone has been off for six hours, and describe — correctly, not by buzzword — how a server that never sees plaintext still fans a message out to three of your devices.

01 Why this interview goes sideways fast

Ask "design WhatsApp" and most candidates start drawing boxes: client, load balancer, chat server, database, push notification service. Ten minutes in they've built a working sketch of — a forum with typing indicators. The messaging-product interview is graded almost entirely on the parts that sketch skips: what a "delivered" tick is actually asserting about state on a device you don't control, what happens to a message when the recipient's phone has been powered off since Tuesday, and whether the encryption you just claimed is really end-to-end or just "we use HTTPS" wearing a disguise.

The giveaway question, almost every time: "Your server just accepted a message for a user who has three linked devices — walk me through exactly what happens next, with one of those devices offline." A mid-level answer describes one flow: store the message, send a push notification, done. A senior answer names three separate deliveries — one ciphertext per device, because each device holds a different key — a per-device offline queue, and a receipt state machine that can only move forward. And it can explain, without hand-waving, why the server is able to mark a message "delivered" without ever being able to read it.

This lesson builds that full answer, mechanism by mechanism: the sent/delivered/read state machine, the offline-sync queue that makes "delivered" possible at all, and — at the conceptual depth an interview actually wants, not full protocol math — how key exchange lets two parties get to a shared secret without ever handing the server anything it can decrypt.

02 One message, N locked copies

Forget "the server relays your message." The server relays sealed envelopes it cannot open — and if you're signed into the same account on a phone and a laptop, the sender's app doesn't produce one envelope. It seals and sends two, because your phone and your laptop don't share a key.

That's the whole conceptual core of end-to-end encryption in a multi-device product: identity isn't the unit of encryption, the device session is. Everything else in this lesson — receipts, offline queues, fan-out — is bookkeeping built around that one fact.

04 How this shows up in systems you already use

  • Signal Protocol (X3DH + Double Ratchet) is the actual cryptographic basis for WhatsApp's end-to-end encryption (WhatsApp integrated it in 2016). X3DH lets two devices agree on a shared secret asynchronously — the recipient doesn't even need to be online at the moment the first message is sent — and the Double Ratchet then derives a brand-new message key for every single message, so a leaked key doesn't expose the messages before or after it.
  • Signal "Sender Keys" for group chats. Pairwise Double Ratchet sessions don't scale to a large group — that's an asymmetric encryption per recipient device, every message. Instead, each member generates one symmetric sender key, distributes it once (pairwise-encrypted) to every other member, and after that encrypts group messages a single time with that shared key.
  • Per-device fan-out queues are conceptually identical to a topic with N independent consumer offsets — the same pattern lesson 17's message queues and lesson 27's pub/sub both cover. A "device" here is just a durable subscriber with its own cursor into the conversation.
  • WhatsApp's original 2012 architecture: Erlang processes over FreeBSD, with the engineering team publicly describing roughly two million concurrently-held TCP connections on a single server (a widely cited 2012 engineering write-up). That number is about idle open sockets, not throughput — holding a connection open is cheap; the message rate flowing through it is a much smaller number.
  • APNs / FCM push is a distinct channel from the persistent socket. When the app isn't running there's no socket to push down, so a silent data notification is what actually wakes the device and triggers it to reconnect and pull the queued message from its own offline outbox.
  • iMessage and Signal use the same three-tick delivery semantics (sent → delivered → read), with the same underlying constraint: a client only reports "delivered" once it has physically written the ciphertext into that specific device's local store — not merely accepted it into a queue destined for that device.

05 Hands-on: build the delivery-state machine yourself

The three mechanisms behind the console above — a forward-only receipt state machine, per-device offline queues, and a reorder buffer — are about 120 lines of plain Python with no network and no crypto library. Isolating them like this is exactly what a good interview answer does: name the state, don't hand-wave it.

messaging_sim.py
from collections import deque
from enum import Enum, auto


# ---------------------------------------------------------------- receipts --

class State(Enum):
    SENT = auto()
    DELIVERED = auto()
    READ = auto()


# Only these forward edges are legal. Anything else is a bug in the caller
# (e.g. a delayed duplicate ACK arriving after a newer one already landed).
_ALLOWED = {
    State.SENT: {State.DELIVERED},
    State.DELIVERED: {State.READ},
    State.READ: set(),
}


class IllegalTransition(Exception):
    pass


class ReceiptTracker:
    """Tracks message_id -> current State. Idempotent: re-applying the same
    (or an already-passed) state is a silent no-op, because at-least-once
    delivery means the same ACK can legitimately arrive twice."""

    def __init__(self):
        self._state = {}

    def start(self, message_id):
        self._state[message_id] = State.SENT

    def advance(self, message_id, new_state):
        current = self._state[message_id]
        if new_state == current:
            return current  # duplicate ACK, ignore
        if new_state not in _ALLOWED[current]:
            raise IllegalTransition(
                f"{message_id}: cannot go {current.name} -> {new_state.name}"
            )
        self._state[message_id] = new_state
        return new_state


# ------------------------------------------------------------ device outbox --

class DeviceOutbox:
    """One per (user, device). Buffers messages while the device is offline
    and flushes them, in order, the moment it reconnects. `seen` makes
    enqueue idempotent so a client retry after a lost ACK never double-queues."""

    def __init__(self, device_id):
        self.device_id = device_id
        self.online = False
        self.queue = deque()
        self.seen = set()

    def enqueue(self, client_msg_id, payload):
        if client_msg_id in self.seen:
            return False  # dedup: this is a retry of a message we already have
        self.seen.add(client_msg_id)
        self.queue.append((client_msg_id, payload))
        return True

    def flush(self):
        delivered = list(self.queue)
        self.queue.clear()
        return delivered


# --------------------------------------------------------- reorder buffer --

class ReorderBuffer:
    """Server hands out a monotonic per-conversation sequence number on send.
    The client-side buffer only releases seq N once N-1 has already been
    released, holding later-arriving-but-earlier-numbered gaps until they
    fill in -- the same idea Signal's Double Ratchet uses to tolerate
    messages that arrive out of order (it caches skipped message keys)."""

    def __init__(self):
        self._next_expected = 1
        self._held = {}

    def receive(self, seq, payload):
        released = []
        self._held[seq] = payload
        while self._next_expected in self._held:
            released.append((self._next_expected, self._held.pop(self._next_expected)))
            self._next_expected += 1
        return released

Complexity is worth naming out loud, because it's exactly what a staff interviewer probes for: ReceiptTracker.advance and DeviceOutbox.enqueue are both O(1) — a dict lookup and a set membership check. ReorderBuffer.receive looks like it could be O(k) for a single call (seq=1 arriving last released four messages at once above), but across the whole stream every message is inserted into _held and popped out at most once, so total work is amortized O(1) per message, O(n) for n messages overall.

06 The senior/staff framing

What separates a strong answer from a weak one

  • Weak: "We end-to-end encrypt everything with AES, so it's secure." Strong: "Each device pair gets its own Double Ratchet session established via an X3DH key agreement, so the server only ever custodies ciphertext. Forward secrecy means a leaked key doesn't retroactively expose history; post-compromise security means the ratchet heals itself going forward too, once fresh key material is mixed back in."
  • The killer follow-up: "Your group chat has 500 members. Are you really running 500 pairwise Double Ratchet sessions per message?" No — that's O(N) asymmetric encryptions per message, which doesn't scale. The real answer is a Sender Key: an O(N) pairwise distribution cost paid once (or again on membership change / periodic rotation), after which steady-state cost drops to O(1) — one symmetric encryption, fanned out as identical ciphertext to every member holding that key.
  • Name the leak most engineers forget: backups. A message that's genuinely end-to-end encrypted in transit can still leave that guarantee at rest — WhatsApp's cloud chat backups were not end-to-end encrypted by default for years, a widely reported real gap between the marketing claim and the deployed system. A staff-level answer proactively flags where the encryption boundary actually ends, instead of assuming it covers everything with "E2E" in the name.
  • Metadata is not content: even a flawless E2E scheme leaves the server able to see who talked to whom, when, how often, and roughly how much — a real privacy surface "we encrypt the messages" doesn't close. Naming this unprompted is a strong signal.

08 Spaced recap

Resurfacing Lesson 27 — Build a Simple Pub/Sub System in Python

Lesson 27 had you build a minimal publish/subscribe core: topics, a registry of subscribers, and fan-out delivery of one published message to every current subscriber of that topic. Swap the vocabulary and today's system is the same shape under load — a conversation is a topic, and each of a user's devices is a subscriber with its own durable position, not a fire-and-forget callback. That's exactly why lesson 27's naive in-memory fan-out isn't enough on its own and needed the per-device queue you built in today's DeviceOutbox. The one genuinely new piece today adds on top of lesson 27's fan-out is durability across a subscriber being offline — plain pub/sub assumes a live subscriber; a messaging system can't make that assumption even once.
