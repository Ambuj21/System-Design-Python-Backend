System design fundamentals · Phase 2 · Lesson 12

Load Balancing

The rounded rectangle every system-design diagram draws without a second thought — until an interviewer asks what layer it actually operates at, how it picks a backend, and what happens the instant one of those backends stops answering.

01 Why this is an interview trap

Ask a mid-level engineer what a load balancer does and you'll get: "it spreads traffic across servers, usually round robin." That's not wrong. It's also three separate decisions collapsed into one sentence, and a staff-level conversation is precisely about pulling them apart.

Decision one: what layer does it operate at — does it ever see anything above IP:port, or does it terminate the connection and read the actual HTTP request? Decision two: which backend does it pick, given the pool it's allowed to choose from — round robin, weighted round robin, least connections, consistent hashing all answer this differently, and they are not interchangeable. Decision three: which backends are even eligible — health checks are what shrink and grow that pool underneath the algorithm, often without the algorithm's "knowledge" that anything changed.

The console below runs a real discrete-event simulation of four algorithms against the same backend pool, including one backend that's genuinely running behind. Two of the algorithms react to that completely differently — and predicting which one, before you press play, is a fair proxy for whether you actually understand the mechanism or just the vocabulary.

02 The envelope and the letter

Every load balancer is a piece of mail-sorting infrastructure. The only question is whether it's allowed to open the envelope.

That's the whole first fork: an L4 balancer picks a backend once, per TCP connection, from the address alone; an L7 balancer picks fresh, per HTTP request, from the content. Everything below — the algorithms, the health checks, sticky sessions — is downstream of which of these two boxes you're actually looking at.

Round robin cycles backend-1 → 2 → 3 → 4 on a fixed schedule. It never checks whether the backend it's about to pick is still catching up on the last one.

Read backend-3's lane on Round Robin, then flip to Least Connections without touching anything else. Same slow backend, same arriving traffic. Round robin stacks two requests on it at once because counting to four doesn't know or care that the last request hasn't finished. Least connections checks who's currently busiest before every single pick — an O(n) scan over a handful of backends, cheap at this scale — and it simply stops sending backend-3 new work while it's behind. Neither algorithm is "smarter" in general; least connections is reacting to live state that round robin structurally cannot see, and that reaction costs a scan round robin doesn't pay.

04 How this shows up in systems you already use

  • AWS NLB vs ALB is the L4/L7 split, productized. The Network Load Balancer forwards TCP/UDP at the packet level — it can push tens of millions of packets per second in software because it never parses HTTP — and preserves the client's source IP end to end. The Application Load Balancer terminates HTTP/HTTPS itself, which is what makes path- and host-based routing, WebSocket awareness, and per-target-group health checks possible at all. Picking NLB when you actually need ALB's routing (or the reverse, paying L7 tax for pure TCP passthrough) is a real, common design mistake.
  • nginx's upstream block ships round robin as the default, least_conn as an explicit directive, ip_hash as a crude consistent-hash-by-client-IP (a poor man's sticky session), and — worth knowing exists — hash $request_uri consistent;, which implements real ketama-style consistent hashing, most often put in front of a cache tier so the same URI keeps landing on the same warm cache.
  • Envoy and Istio's "least request" policy doesn't scan every backend on every pick the way naive least-connections does. At real scale it uses power-of-two-choices (P2C): sample two backends at random, route to whichever has fewer active requests. That's O(1) instead of O(n), and it's provably close to true least-connections behavior — a detail worth volunteering if an interviewer pushes on "does least connections scale to thousands of backends."
  • Google's Maglev (the 2016 NSDI paper, still the reference design for software L4 balancing) uses its own consistent-hashing variant specifically so that when a backend is added or removed, only the minimum necessary slice of flows remaps — the same K/N property the ring below demonstrates, engineered to hold at datacenter scale and line rate.
  • Kubernetes stacks both layers. kube-proxy (iptables or IPVS mode) does L4 load balancing across a Service's pod IPs — IPVS mode literally offers round robin, least connection, and a few other classic algorithms as a config choice. Above that, an Ingress controller (nginx-ingress, an Envoy-based gateway) does L7 host/path routing to different Services. And the pool IPVS or iptables is even allowed to route to is decided by readiness probes — the health-check mechanism, at the orchestration layer, that this lesson has been simulating.

05 Hands-on: prove consistent hashing's core property

The claim "consistent hashing only remaps ~1/N of your keys when a node changes, instead of nearly all of them" is the single most quotable fact about this algorithm — and also the one most people repeat without ever having checked it. Here's a real ring, hashing 10,000 keys, measured.

ring.py
import hashlib
import bisect
from collections import defaultdict


def stable_hash(key: str) -> int:
    """Deterministic hash — Python's built-in hash() is salted per-process
    (PYTHONHASHSEED) specifically so it CAN'T be used for anything that
    needs to agree across processes, which a hash ring always does."""
    return int(hashlib.md5(key.encode()).hexdigest(), 16)


class ConsistentHashRing:
    def __init__(self, nodes=None, vnodes=150):
        self.vnodes = vnodes
        self.ring = {}          # hash -> node name
        self.sorted_hashes = []  # kept sorted for O(log n) lookup via bisect
        for node in nodes or []:
            self.add_node(node)

    def add_node(self, node):
        for i in range(self.vnodes):
            h = stable_hash(f"{node}#vn{i}")
            self.ring[h] = node
            bisect.insort(self.sorted_hashes, h)

    def remove_node(self, node):
        for i in range(self.vnodes):
            h = stable_hash(f"{node}#vn{i}")
            del self.ring[h]
            pos = bisect.bisect_left(self.sorted_hashes, h)
            del self.sorted_hashes[pos]

    def get_node(self, key):
        if not self.ring:
            return None
        h = stable_hash(key)
        idx = bisect.bisect(self.sorted_hashes, h)
        if idx == len(self.sorted_hashes):
            idx = 0  # wrap around the ring
        return self.ring[self.sorted_hashes[idx]]


def naive_mod_hash(key, nodes):
    return nodes[stable_hash(key) % len(nodes)]


if __name__ == "__main__":
    nodes = ["backend-1", "backend-2", "backend-3", "backend-4"]
    keys = [f"session-{i}" for i in range(10_000)]

    ring = ConsistentHashRing(nodes, vnodes=150)
    dist = defaultdict(int)
    for k in keys:
        dist[ring.get_node(k)] += 1

    print("=== distribution across 4 nodes, 150 virtual nodes each, 10,000 keys ===")
    for n in nodes:
        pct = dist[n] / len(keys) * 100
        print(f"{n:12s} {dist[n]:5d} keys  ({pct:5.1f}%)")

    before = {k: ring.get_node(k) for k in keys}
    ring.add_node("backend-5")
    after = {k: ring.get_node(k) for k in keys}
    moved = sum(1 for k in keys if before[k] != after[k])
    print(f"\n--- scaling out: add backend-5 (4 -> 5 nodes) ---")
    print(f"consistent hashing remapped : {moved:5d}/{len(keys)} keys ({moved/len(keys)*100:4.1f}%)")
    print(f"theoretical expectation ~1/(n+1)     : {100/5:4.1f}%")

    before_mod = {k: naive_mod_hash(k, nodes) for k in keys}
    nodes5 = nodes + ["backend-5"]
    after_mod = {k: naive_mod_hash(k, nodes5) for k in keys}
    moved_mod = sum(1 for k in keys if before_mod[k] != after_mod[k])
    print(f"\n--- same change, naive `hash(key) % len(nodes)` ---")
    print(f"naive modulo remapped        : {moved_mod:5d}/{len(keys)} keys ({moved_mod/len(keys)*100:4.1f}%)")

That's the entire argument for consistent hashing in two lines: adding a fifth backend moves 19.2% of keys under the ring, versus 80.5% under naive modulo — because hash(key) % n changes for almost every key the instant n changes, while the ring only reassigns keys that actually fell in the new node's slice. And the reason this matters isn't only "less remap work" — it's that every key that didn't move is a key whose downstream cache (Redis, Memcached, an in-process LRU) is still warm. Consistent hashing is as much a cache-affinity tool as a resharding tool; that's usually the real reason it's sitting in front of a cache tier in production.

wrr.py — the same weighted round robin the console runs
class SmoothWeightedRoundRobin:
    """nginx's actual algorithm, not the naive 'expand backend-3 into the
    list 3 times' version. Every pick is O(n) over the backend list, but
    it never bursts — a weight-3 backend never gets picked 3 times in a
    row the way naive list-expansion would."""

    def __init__(self, weights: dict[str, int]):
        self.weights = weights
        self.current = {name: 0 for name in weights}

    def pick(self) -> str:
        total = sum(self.weights.values())
        for name in self.current:
            self.current[name] += self.weights[name]
        chosen = max(self.current, key=self.current.get)
        self.current[chosen] -= total
        return chosen


weights = {"backend-1": 1, "backend-2": 1, "backend-3": 3, "backend-4": 1}
lb = SmoothWeightedRoundRobin(weights)
print(" -> ".join(lb.pick() for _ in range(12)))
backend-3 -> backend-1 -> backend-2 -> backend-3 -> backend-4 -> backend-3 -> backend-3 -> backend-1 -> backend-2 -> backend-3 -> backend-4 -> backend-3

=== distribution over 6,000 picks ===
backend-1    weight=1  expected= 16.7%  actual= 16.7%
backend-2    weight=1  expected= 16.7%  actual= 16.7%
backend-3    weight=3  expected= 50.0%  actual= 50.0%
backend-4    weight=1  expected= 16.7%  actual= 16.7%

Notice backend-3 does land twice in a row once, right at the seam between cycles (positions 6-7). Smooth WRR bounds burstiness across the interior of a cycle, it doesn't guarantee zero repeats at the boundary — a small, honest nuance worth having in your back pocket if an interviewer pushes on "never" claims.

The exercise — predict before you run it. Using the exact same ring.py from above:

# Part A: what if a backend DIES instead of a new one joining?
# (health check fails -> node removed, 4 -> 3 nodes)
ring = ConsistentHashRing(nodes, vnodes=150)
before = {k: ring.get_node(k) for k in keys}
ring.remove_node("backend-2")
after = {k: ring.get_node(k) for k in keys}
moved = sum(1 for k in keys if before[k] != after[k])
# predict: what fraction moves? is it 1/(n+1) like scale-out, or 1/n_before?

# Part B: why 150 virtual nodes and not 1?
for vn in (1, 150):
    r = ConsistentHashRing(nodes, vnodes=vn)
    dist = defaultdict(int)
    for k in keys: dist[r.get_node(k)] += 1
    counts = [dist[n] for n in nodes]
    print(vn, counts, "spread:", max(counts) - min(counts))
=== backend-2 dies (health check fails), 4 -> 3 nodes ===
consistent hashing remapped : 2526/10000 (25.3%)
theoretical expectation ~1/n_before  : 25.0%
(every key that WAS on backend-2 must move somewhere; keys on
 backend-1/3/4 are untouched -- that's the whole property.)

=== fairness with vnodes=1 (no virtual nodes) vs vnodes=150 ===
vnodes=1    counts=[3311, 725, 3762, 2202]  max-min spread=3037 (30.4% of keys)
vnodes=150  counts=[2463, 2526, 2587, 2424]  max-min spread=163 (1.6% of keys)

Two real answers there. A node dying costs 1/n_before (25% for 4 → 3), not 1/n_after — you're redistributing the dead node's slice among the survivors, which is a different fraction than a node joining carves out for itself. And with exactly one hash point per physical node, luck of the draw gave one backend 5× another's share (725 vs 3762) — 150 virtual nodes per physical node is what turns a random single point into a smooth, near-uniform distribution. Both numbers are why production rings (Maglev, Envoy's ring hash, nginx's ketama) all use dozens to hundreds of virtual nodes per physical node, never one.

06 The senior/staff framing

What separates a strong answer from a weak one

  • Weak: "We put sticky sessions on so users keep hitting the same backend — simple, works." Strong: "Sticky sessions pin a client to a backend by cookie or source-IP hash, and they're a mitigation, not a fix — they exist to paper over a backend that holds session state in process memory. The moment that backend fails a health check, the client's sticky cookie points at a target that's no longer in rotation, and whatever wasn't durably stored (the in-memory cart, the WebSocket state) is just gone. I'd only reach for stickiness as a deliberate, temporary bridge — the real fix is externalizing that state to Redis or the primary DB, keyed by a token the client carries, exactly like lesson 11 covered for horizontal scaling generally."
  • The killer follow-up: "Your ALB uses duration-based sticky cookies because carts live in-process. A health check just marked that target unhealthy. Walk me through, precisely, what the next request from a client whose sticky cookie still names that target actually experiences." The honest mechanism: the LB detects the failed health check and drops the target from the healthy pool; on the next request, most real implementations (ALB included) detect the cookie points at a now-unhealthy target and transparently rebind the client to a new one, often issuing a fresh cookie — so the request usually still succeeds. What the candidate needs to say next is the part that actually matters: succeeding at the HTTP layer does not mean the cart survived. The LB solved connectivity; it did not and cannot solve the state loss, because that was never its job.
  • The nuance worth naming unprompted: a health check failing does not kill in-flight requests on that backend — it only stops new ones from being routed there. Killing in-flight work cleanly, on purpose, is a separate mechanism: graceful shutdown and connection draining, handled by the backend process itself, not the load balancer.
  • Know the cost axis, not just the behavior: L4 is cheap enough to run at line rate in software (tens of millions of packets/sec is a realistic order of magnitude for tools like Maglev); L7 costs real CPU per request for TLS termination and parsing — never quote a bare "requests/sec per core" number without immediately caveating it on payload size, TLS, and keep-alive reuse, because that number swings by an order of magnitude on those alone, and stating it too confidently is itself a tell.

08 Spaced recap

Resurfacing lesson 09 — Packaging & Deployment

Lesson 09 covered getting a build safely into production — immutable artifacts, containerized images, and a process that shuts down cleanly instead of just dying when it's told to stop. That last piece is the part that quietly determines whether every rolling deploy you ship is invisible to users or a trickle of dropped connections. This lesson's health checks are the mechanism on the other side of that same handshake: a load balancer only stops sending traffic to an instance once its health check goes red, and a process that gets a hard SIGTERM and dies immediately — instead of flipping its readiness endpoint unhealthy first, finishing in-flight requests, then exiting — will drop connections on every single deploy regardless of how good the algorithm choosing its traffic was. The load-balancing algorithm decides who gets picked; graceful shutdown from lesson 09 decides whether being un-picked actually happens before the box disappears.
