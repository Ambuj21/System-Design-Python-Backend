Python backend mastery · Phase 1 · Lesson 07

Testing Strategy for Backend Systems

Where exactly to put the mock boundary, why a green integration suite still lets two services disagree in production, and why your dashboard's average latency is quietly hiding the users who are having the worst day.

01 Why "we have 90% coverage" isn't an answer

Ask a mid-level engineer how their service is tested and you'll usually get one of two answers, and both are policies, not boundaries: "we mock everything so tests are fast and isolated" or "we don't mock much, our tests hit real staging." Neither survives a staff-level follow-up, because the actual skill being asked about is: which specific calls do you replace with a test double, and on what principle — not a blanket rule about mocking a lot or a little.

Coverage percentage makes this worse as a signal. A test that calls place_order() and asserts nothing executes every line inside it — 100% line coverage, zero verification. Coverage measures which code ran, not which code was checked. Mutation-testing tools (flip a < to <=, delete a line, see if any test fails) exist specifically because coverage lies about this, and a strong candidate volunteers that distinction unprompted.

This lesson covers four things that compound: the shape a healthy test suite takes (the pyramid), the rule that decides what gets mocked (not "external," but "outside your control"), contract testing — which catches a class of bug neither unit nor integration tests can see — and the basics of reading a p50/p95/p99 histogram, because "the API is fast" and "the API is fast for 99% of users" are different claims with different tests.

02 Mock at the edge of what you don't control

The naive version of the rule is "mock anything outside your class." The real rule is sharper: mock anything whose outcome you don't control — because it's nondeterministic, slow, or owned by someone else.

Notice what's not on this list: OrderRepository, your own class that talks to the database, isn't drawn as a permanent test double — it's drawn crossing the boundary because the database itself is the thing you don't control inside a single test run, not the repository class. That distinction is exactly why the rule survives contact with a real service better than "mock external classes" does. Section 03 shows precisely which of these three targets get promoted back to "real" as you climb the pyramid, and why one of them — Stripe — never does, even in end-to-end tests.

04 How this shows up in systems you already use

  • pytest + unittest.mock / pytest-mock / respx / responses. The standard Python boundary-mocking toolkit — respx and responses specifically intercept outbound HTTP at the transport layer, so your real client code (retry logic, header construction, error parsing) still runs; only the socket is faked. Mocking the client method directly instead is a common mistake — it skips testing the exact code most likely to have the bug.
  • Testcontainers. Spins up a real Postgres, Redis, or Kafka in a disposable Docker container for the duration of an integration test, then tears it down. This is why "integration test" doesn't have to mean "hits shared staging" — it can mean a real database that only your test process ever sees, gone in milliseconds after the run.
  • Pact (consumer-driven contract testing). Used at Atlassian, PayPal, and dozens of microservice shops. The consumer team writes expectations against the provider's API and publishes them as a "pact file" to a Pact Broker; the provider's CI independently replays those expectations against its real code. Neither side's test suite ever boots the other service — the broker's "can-i-deploy" check is what gates the release.
  • Schemathesis. Generates adversarial test cases directly from an OpenAPI spec (empty strings, boundary integers, missing required fields) and asserts the live API's responses still match the spec — property-based contract testing without hand-writing examples.
  • k6, Locust, wrk2, vegeta. Load-testing tools with one critical split: wrk (and naive scripts built on requests in a loop) are closed-loop — they wait for each response before sending the next, so during a slowdown they simply send fewer requests, quietly erasing the worst samples from the percentile calculation. wrk2, vegeta, and k6's constant-arrival-rate executor are open-loop — they issue requests on a fixed schedule regardless of how slow responses are, which is the only way to measure a percentile you can trust. This gap has a name: coordinated omission (Gil Tene).
  • Stripe's own testing guidance tells integrators to run end-to-end checkout flows against test-mode API keys, never production keys — the exact "even e2e respects the money boundary" pattern in section 03's diagram, straight from the vendor whose API it is.
  • "The Tail at Scale" (Dean & Barroso, Google, CACM 2013) is the origin of the fan-out math in section 03: if any one backend call has a 1% chance of being slow, a page that fans out to 20 of them has a much higher chance that at least one is slow — which is why p99 of a single service becomes p50-like behavior for a page built from many services.

05 Hands-on: the boundary rule, a contract check, and real percentiles

Three small, runnable pieces: a service with an explicit boundary, tests that mock at exactly that boundary and nowhere else, a contract check that catches schema drift a type-checker can't, and the percentile script behind every number in section 03.

orders.py — the service under test
class PaymentClient:
    """Talks to a third-party payment provider over HTTPS. Boundary #1 — never ours."""
    def charge(self, amount_cents: int, token: str) -> dict:
        raise NotImplementedError("real implementation makes a network call")

class OrderRepository:
    """Owns the SQL. Boundary #2 — but one we control, so integration tests
    run it for real against a local database instead of faking it."""
    def __init__(self, conn):
        self.conn = conn
        self.conn.execute("CREATE TABLE IF NOT EXISTS orders "
            "(id TEXT PRIMARY KEY, sku TEXT, qty INTEGER, total_cents INTEGER)")
    def save(self, order): ...
    def get(self, order_id): ...

class OrderService:
    """Pure business logic. Never mocked — it is always the thing under test."""
    def __init__(self, repo, payments):
        self.repo, self.payments = repo, payments
    def place_order(self, sku, qty, unit_price_cents, token):
        if qty <= 0:
            raise ValueError("qty must be positive")
        total = qty * unit_price_cents
        receipt = self.payments.charge(total, token)
        if receipt["status"] != "approved":
            raise RuntimeError(f"payment declined: {receipt['status']}")
        order = Order(id=str(uuid.uuid4()), sku=sku, qty=qty, total_cents=total)
        self.repo.save(order)
        return order
test_orders.py — unit vs. integration, same service
# UNIT: only PaymentClient is a double — kept minimal on purpose
def test_place_order_charges_and_saves_unit():
    fake_payments = Mock()
    fake_payments.charge.return_value = {"status": "approved"}
    fake_repo = Mock()
    svc = OrderService(repo=fake_repo, payments=fake_payments)
    order = svc.place_order(sku="WIDGET-1", qty=3, unit_price_cents=500, token="tok_x")
    fake_payments.charge.assert_called_once_with(1500, "tok_x")
    fake_repo.save.assert_called_once()
    assert order.total_cents == 1500

# INTEGRATION: real SQLite runs real SQL. Only the third-party
# payment provider — a boundary we truly don't own — stays a double.
def test_place_order_persists_for_real_integration():
    conn = sqlite3.connect(":memory:")
    real_repo = OrderRepository(conn)                 # real CREATE TABLE ran already
    fake_payments = Mock()
    fake_payments.charge.return_value = {"status": "approved"}
    svc = OrderService(repo=real_repo, payments=fake_payments)
    order = svc.place_order(sku="WIDGET-1", qty=2, unit_price_cents=1000, token="tok_y")
    fetched = real_repo.get(order.id)                  # real SELECT, real row back
    assert fetched == order

contract_check.py — catching drift neither test above can see
@dataclass(frozen=True)
class InventoryLevelContract:
    sku: str
    available_qty: int
    warehouse_id: str

def validate_contract(payload: dict, contract) -> list[str]:
    expected = {f.name for f in fields(contract)}
    errors = []
    missing = expected - set(payload)
    if missing:
        errors.append(f"missing fields: {sorted(missing)}")
    for f in fields(contract):
        if f.name in payload and not isinstance(payload[f.name], f.type):
            errors.append(f"{f.name}: expected {f.type.__name__}, "
                          f"got {type(payload[f.name]).__name__}")
    return errors

current_response = {"sku": "WIDGET-1", "available_qty": 42, "warehouse_id": "BLR-1"}
print("current response errors:", validate_contract(current_response, InventoryLevelContract))

# Inventory Service ships a routine-looking rename next sprint.
# Nothing on their side breaks — their own tests are all green.
drifted_response = {"sku": "WIDGET-1", "qty_available": 42, "warehouse_id": "BLR-1"}
print("drifted response errors:", validate_contract(drifted_response, InventoryLevelContract))
output — python3 contract_check.py
current response errors: []
drifted response errors: ["missing fields: ['available_qty']"]

Neither the unit test nor the integration test above touches Inventory Service at all — InventoryClient never even appears in orders.py. That's the point: this check catches the rename with no service running, no network call, in a few milliseconds, purely because both sides agreed on a shared shape ahead of time.

percentiles.py — the numbers behind section 03's histogram
def percentile(data, p):
    data = sorted(data)
    k = (len(data) - 1) * (p / 100)
    f = int(k); c = min(f + 1, len(data) - 1)
    return data[f] if f == c else data[f] + (data[c] - data[f]) * (k - f)

random.seed(7)
N = 5000
def base_latency():
    return max(5.0, random.lognormvariate(3.8, 0.35))   # right-skewed, ~40ms typical

healthy = [base_latency() for _ in range(N)]

regression = []                                          # same baseline, but 1% of
for _ in range(N):                                        # requests land during a
    lat = base_latency()                                   # GC pause / lock wait
    if random.random() < 0.01:
        lat += random.uniform(1200, 2200)
    regression.append(lat)

# fan-out: P(at least one of k independent backend calls is slow)
for k in (1, 5, 10, 20):
    print(k, 1 - (1 - 0.01) ** k)

The exercise — predict before you run it: the regression above uses a 1% fault rate. If you raise it to 5% with everything else unchanged, what happens to p50? What happens to p95 — does it stay clean like p50, or does it get swallowed by the tail too? Reason about it, then check:

rng = random.Random(7)
def make(fault_rate):
    out = []
    for _ in range(N):
        lat = base_latency_with(rng)
        if rng.random() < fault_rate:
            lat += rng.uniform(1200, 2200)
        out.append(lat)
    return out

for rate in (0.01, 0.05):
    data = make(rate)
    print(rate, mean(data), percentile(data,50), percentile(data,95), percentile(data,99))
fault_rate=1%  mean=   64.9ms  p50=   44.7ms  p95=   81.2ms  p99= 1262.5ms  max= 2223.6ms
fault_rate=5%  mean=  137.0ms  p50=   46.4ms  p95= 1288.2ms  p99= 2058.3ms  max= 2289.5ms

p50 barely moves even at 5x the fault rate (44.7ms → 46.4ms) — the median only cares about the middle of the distribution, and 95% of requests are still untouched. But p95 does move, dramatically, once the fault rate crosses 5%: at 1% only p99 sees it, at 5% even p95 gets swallowed by the tail. Which percentile catches a regression is a direct function of how often the regression fires relative to that percentile's threshold — a fact worth stating explicitly in an interview, because it's the reason teams track p99 and p95 rather than picking one.

06 The senior/staff framing

What separates a strong answer from a weak one

  • Weak: "We aim for high coverage and mock external calls so unit tests run fast." Strong: "We mock at the edge of what we don't control — third-party APIs, wall-clock time, randomness — and let integration tests exercise our own infrastructure for real. Contract tests decouple our deploys from other teams' deploys by checking a shared schema instead of booting their service. And we track p99, not average latency, because that's what a real user's worst request looks like."
  • The killer follow-up: "Your contract tests are green and your integration tests are green — but production breaks because one service sends timestamps in local time and the other expects UTC. Both are valid JSON, both are the correct type. Which of your test layers should have caught that, and why didn't it?" None of them, by default — a type-shape contract check (str, int) validates the wire's shape, not its meaning. Catching this requires example-based contract assertions with concrete, realistic values (Pact's "matching rules" against real payloads, not just types) for exactly the fields where meaning is easy to get wrong: timestamps, currency units, enums.
  • The fix worth naming: promote semantically risky fields out of "any string matching the type" and into "this exact example, this exact format" in the contract itself — it costs a few more lines per field and it's the only layer built to catch this class of bug.
  • Know where correctness testing stops: none of unit, integration, or contract tests tell you whether the system stays fast enough under real concurrency. A service can be 100% correct and still miss its SLA under load — that's a different question, answered by percentiles under load, not assertions. And know the trap inside load testing itself: a closed-loop load generator (wait for each response, then send the next) silently under-samples the exact window where the system is struggling — coordinated omission — which is why the tool you pick matters as much as the test you write.

07 Check your understanding

Before you move on

You're told to triple the size of OrderService's test suite without slowing down CI. Where do you add the new tests, at which layer, and what do you deliberately leave out at that layer and why?

Separately: a teammate runs a load test and proudly reports p50 = 40ms and p99 = 40ms — flat, identical, no matter how much simulated traffic they throw at it. Is that good news? What would you check before believing the result?

08 Spaced recap

Resurfacing lesson 04 — REST & GraphQL API Design

Contract testing only works if there's a contract worth checking in the first place. A REST resource with explicit status codes, a versioned schema, and a documented error shape — or a GraphQL schema, which carries its contract as part of the language itself via introspection — is exactly what lesson 04 was about, and it's the precondition for everything section 03 and 06 covered here: an API whose shape is implicit or inconsistent gives you a contract test that's either impossible to write precisely or too loose to catch anything. Good API design and good contract testing are the same discipline applied at two different points in the pipeline.
