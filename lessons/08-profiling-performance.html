Python backend mastery · Phase 1 · Lesson 08

Profiling & Performance

Where your request's 400ms actually goes, how to find it without guessing, and why the profiler you reach for out of habit might be lying to you about the very code you're trying to fix.

01 Why "it feels slow" isn't an answer

Ask a mid-level engineer how they'd find a slow endpoint and you'll often hear a tools list: "cProfile, or maybe py-spy." That's a vocabulary test, not an engineering answer. The staff-level question is narrower: which profiler, at which layer, at what cost to the system you're measuring — because the two most common tools in this space have almost opposite cost models, and picking the wrong one either gives you nothing or makes the outage worse.

cProfile is deterministic: it wires an instrumentation hook onto every single function call and return via sys.setprofile. It sees everything, exactly, but its overhead scales with how many Python-level calls happen — not with wall-clock time. Run it on a call-heavy pure-Python hot path and you can more than double the runtime. py-spy is statistical: it doesn't touch the target process's code at all. It reads the interpreter's frame objects directly out of the process's memory from the outside, on a fixed clock (default ~100 samples/second), and reconstructs the picture from enough snapshots. Overhead is roughly 1% regardless of call volume — which is the only reason it's safe to point at production.

The second trap is subtler and shows up constantly in real systems: the N+1 query. A handler that looks like three lines of clean ORM code can silently issue 51 database round trips instead of 1, and it will never show up as "one slow line" — it shows up as one function called an alarming number of times. Recognizing that shape in a profiler's output, cold, without running anything yet, is exactly the skill this lesson builds.

02 Two ways to find out where the time went

Both tools answer "what is this process doing," but they get the answer by fundamentally different mechanisms — and that mechanism is what determines their cost.

That distinction — instrument every event vs. sample on a clock — is why cProfile is a development-box tool and py-spy is a production tool. It also predicts the flame graph you're about to interact with: a flame graph is nothing more than thousands of these stack snapshots, stacked by function name and sorted by depth.

04 Where this shows up in systems you already use

  • py-spy in production. It attaches to a running PID via ptrace (Linux) or process_vm_readv, and reads CPython's frame objects straight out of the target's memory — it never asks the process to cooperate. That's not just a performance nicety: it's why py-spy can inspect a process that's deadlocked, holding the GIL forever, or mid-segfault, none of which cProfile could ever observe because cProfile is code running inside that same stuck interpreter.
  • Always-on continuous profilers — Datadog Continuous Profiler, Google Cloud Profiler, Grafana Pyroscope, Parca — all use statistical sampling (typically ~100Hz) for the same reason: they run 24/7 across an entire fleet, and a deterministic profiler's overhead would be an unacceptable, permanent tax on every request.
  • N+1 detection tooling exists because the pattern is this common. Django Debug Toolbar's SQL panel flags duplicate queries per request; the nplusone library raises on the pattern in tests; SQLAlchemy's before_cursor_execute event hook is commonly wired into CI to fail a build if one endpoint issues more than N queries; Datadog APM and New Relic auto-flag "N+1" by clustering identically-shaped SQL fired repeatedly inside one trace.
  • Flame graphs are Brendan Gregg's invention (originally for perf on Linux kernels and off-CPU analysis at Netflix/Sun), and the visualization — width=time, depth=stack — is now universal across languages. py-spy record --format flamegraph and speedscope.app both consume the same "collapsed stack" text interchange format (func;func;func count) that the original C tooling produces.
  • Memory leaks in long-running workers (Celery, gunicorn) are usually caught operationally before they're caught by a profiler: gunicorn --max-requests recycles workers periodically as a band-aid, and Kubernetes memory limits plus liveness probes restart a pod before it OOMs. tracemalloc only sees Python-level allocations — a leak inside a C extension needs RSS monitoring or objgraph instead.

05 Hands-on: profile a real N+1, for real

Everything below actually ran on this machine (CPython 3.10.12) — a real in-memory SQLite database, a real cProfile run, real overhead measurements, and a real tracemalloc snapshot. Nothing here is simulated.

bench_profile.py — the naive vs. optimized fetch
def naive_fetch(con):
    """Classic N+1: one query for orders, then one query PER order for its items."""
    cur = con.cursor()
    cur.execute("SELECT id, customer FROM orders")
    orders = cur.fetchall()
    result = []
    for oid, cust in orders:
        cur.execute("SELECT sku, qty FROM items WHERE order_id = ?", (oid,))
        result.append((oid, cust, cur.fetchall()))
    return result

def optimized_fetch(con):
    """Same result, one round trip via JOIN."""
    cur = con.cursor()
    cur.execute("""
        SELECT o.id, o.customer, i.sku, i.qty
        FROM orders o LEFT JOIN items i ON i.order_id = o.id
        ORDER BY o.id
    """)
    rows = cur.fetchall()
    result = {}
    for oid, cust, sku, qty in rows:
        entry = result.setdefault(oid, (cust, []))
        if sku is not None:
            entry[1].append((sku, qty))
    return result
output — 200 orders × 8 items each, avg of 30 calls
naive (N+1)      :   6.978 ms/call   (201 queries)
optimized (JOIN) :   1.240 ms/call   (1 query)
speedup          :   5.6x

Read ncalls first, before you even look at time. naive_fetch itself was called 50 times (once per benchmark rep, as expected) — but execute and fetchall were each called 10,050 times. 10,050 / 50 = 201 calls per request. That ratio — one low-level DB primitive called two orders of magnitude more often than the function that owns the request — is the N+1 signature. You can spot it without ever looking at a single millisecond value.

Also note tottime vs cumtime: for naive_fetch itself, tottime (self time, excluding children) is 0.004s but cumtime (self + everything it calls) is 0.336s. When cumtime dwarfs tottime like that, the function you're looking at isn't the problem — its children are. You'd scroll down to whichever child has the big tottime, which here is split almost evenly between fetchall and execute: 10,050 round trips, not one slow query.

This is the concrete version of the claim from section 01. The exact same tool, cProfile, costs 2.2% on a workload where most wall-clock time is spent waiting inside a C-implemented sqlite3 call, and 170.9% — more than doubling total runtime — on a workload that's nothing but small Python function calls. sys.setprofile fires on every Python-level call/return event; it doesn't care how long each one takes, only how many there are. That's why "just cProfile it in prod" is bad advice in general but sometimes fine in practice — it depends entirely on call density, not on how slow the endpoint feels.

tracemalloc.take_snapshot() before and after, then snap2.compare_to(snap1, "lineno"), gives you growth attributed to the exact source line that allocated it — line 28 here is result.append((oid, cust, cur.fetchall())), the line building the per-order item tuples that the test deliberately kept alive. That's the whole technique for a leak hunt: take a snapshot, run N requests, take another snapshot, diff, and see which line's allocation count grew proportionally with N instead of staying flat. One caveat worth knowing cold: tracemalloc only tracks memory the Python allocator handed out — a leak inside a C extension's own malloc calls (a common libpq or numpy leak) is invisible to it and needs RSS-level monitoring instead.

the exercise

Predict before you run it, then check: if you wrap only the query-execution line — cur.execute(...) — with a decorator that calls cProfile.Profile().enable()/.disable() around just that one call, 10,050 times, does the measured overhead percentage go up, down, or stay about the same compared to profiling the whole naive_fetch() call as shown above? Reason about it from what sys.setprofile actually hooks (call/return events) before you test it — the answer follows directly from the call-count argument in this section, not from anything new.

setting a latency budget for a request path

A latency budget is just the p99 target allocated backward across the call graph, before you write code, so that a profiler tells you which specific frame blew it instead of you staring at one aggregate number. The method: start from the user-facing SLO (say, 300ms p99 at the load balancer), subtract fixed overhead you don't control (TLS handshake reuse, LB hop, gateway routing — commonly 30–60ms), and what's left is your service's budget. Split that budget across the phases you can actually see in a profile — auth, data fetch, render, serialize — with the data-fetch line getting the most scrutiny, because it's the one phase whose cost is a function of how many rows/round-trips, not fixed CPU work. The 200ms line drawn across the flame graph above is exactly this: not a vibe, a number derived from an SLO, that a profiler either respects or violates in one visible frame.

06 The senior/staff framing

What separates a strong answer from a weak one

  • Weak: "I'd run cProfile on the endpoint and see what's slow." Strong: "First I'd check whether I can safely profile the live path or only a repro locally. In prod, py-spy — attach, sample, detach, ~1% overhead, no deploy. Locally, on a specific slow request, cProfile — full instrumentation, and I can afford the overhead because I'm not serving traffic. I'd read cumtime for the shape of where time goes and ncalls specifically to rule N+1 in or out before touching any code."
  • The killer follow-up: "Your py-spy flame graph shows 40% of samples inside <built-in method time.sleep> on a worker thread. Is that your hotspot to optimize?" No — by default py-spy samples wall-clock time, including off-CPU time. A thread parked in sleep or blocked on a socket read gets sampled just as readily as one burning CPU; a wide frame in a wall-clock flame graph means "this thread's stack was captured most often while suspended here," not "this code is slow to execute." Confusing the two means "optimizing" a wait that was already free.
  • The distinction worth naming unprompted: on-CPU vs. off-CPU profiling. py-spy has a --idle/off-CPU mode and separate on-CPU sampling; cProfile's wall-clock cumtime has the identical trap — a function that calls a slow, blocking network request will show huge cumtime with the process doing nothing at all during most of it.
  • Know the fix vocabulary, not just the diagnosis: selectinload() / joinedload() (SQLAlchemy) or select_related() / prefetch_related() (Django) for N+1; loop.run_in_executor() for a CPU-bound frame found sitting inside an async handler (this is the Lesson 01 GIL lesson resurfacing inside a flame graph); and for genuine CPU-bound Python, the fix a profiler alone can't give you — push the hot function into C/Rust/NumPy or a process pool, because no amount of measuring makes a for-loop over pure Python bytecode faster.
