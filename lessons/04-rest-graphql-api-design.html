REST & GraphQL API Design

What actually happens when a paginated feed hits row 490,000, a payment POST gets retried by a flaky client, and a GraphQL query that "just asks for what it needs" quietly fires 51 database round trips — the parts of API design that don't show up in the CRUD tutorial.

01 Where API design interviews actually go wrong

Ask someone to design a REST API and they'll draw /users, /orders, /products, wire up GET/POST/PUT/DELETE, and call it done. That's the easy 80%. Staff-level interviews live in the other 20%: what happens on page 50,000 of a paginated feed, what happens when a client's POST times out and retries with no idea whether the first attempt succeeded, and what happens the day your GraphQL p99 goes from 40ms to 4 seconds without a single resolver's logic changing.

Four traps, all common enough to have taken down real production systems: offset pagination that gets measurably slower every page deeper a user scrolls, and silently duplicates or skips rows when the table changes underneath it; a POST /charge with no idempotency contract, so one client-side retry after a timeout becomes two charges; a URI versioning scheme that looks clean on day one and becomes three parallel route trees nobody can safely delete by year two; and a GraphQL schema where "give me 50 posts with their authors" fires 51 queries because nobody wired up batching — the classic N+1.

This lesson goes deep on all four, plus the resolver execution model that explains why the last one keeps happening even to teams who already know the term "N+1."

02 A fixed menu vs. a kitchen you can order from

REST hands the client a menu of pre-shaped resources reachable by URI. GraphQL hands the client a schema and lets it order the exact shape it wants from one endpoint — which moves cost from the client's round trips to the server's resolver graph, it doesn't delete the cost.

Resource modeling, briefly and precisely: a REST resource is a noun, addressed by a URI, manipulated by HTTP verbs — GET /orders/7 reads it, PATCH /orders/7 mutates it, the verb is never in the path. Nest a URI only when the child has no independent identity outside its parent (/orders/7/items is fine because a line item doesn't exist without its order; /orders/7/customer is a design smell — a customer has its own identity and lifecycle, so it should be a link, /customers/42, not a nested path). Collections are plural (/orders), members are the collection plus an id (/orders/7) — consistency here is what makes an API guessable, which is most of what "well-designed REST" actually means in practice.

Versioning, the three real strategies: URI versioning (/v1/orders) is the simplest to implement and the most cache-friendly, but it duplicates entire route trees the moment v2 diverges and makes "delete v1" a multi-year negotiation. Header/content-negotiation versioning (Accept: application/vnd.api+json;version=2, or a custom X-API-Version header — GitHub's REST API does exactly this) keeps the URI a stable identifier for the resource itself, which is more architecturally correct, at the cost of being invisible to curl and harder to test by hand. Date-based version pinning — Stripe's approach — freezes each API consumer to whatever API version was current the day their integration started; they upgrade explicitly, on their own schedule, by changing one string. GraphQL sidesteps the whole problem by convention: add fields, never remove them, mark the old ones @deprecated(reason: "..."), and because the client asks for exactly the fields it wants, an unused deprecated field costs nothing to leave in place for years.

Both cards make the same point from different angles. Offset pagination's cost is a function of how deep you page — O(offset + limit) — because the engine must walk and discard every row before the offset in index order; there's no way to skip ahead. Cursor pagination's cost is a function only of the page size — O(log n + limit) — a single B-tree seek to the anchor row, then a fixed number of sequential reads. The N+1 card is the same shape of bug one layer up the stack: cost as a function of how many objects a naive resolver touches, fixed the same way relational databases fixed it decades ago — batch the lookups instead of issuing one per row.

04 How this shows up in systems you already use

  • Stripe. Every mutating endpoint accepts an Idempotency-Key header, cached server-side for 24 hours; retry the same request with the same key and you get the original response replayed, not a second charge. Stripe also pioneered date-based API version pinning — your integration is locked to the API version active the day you generated your first key, upgraded only when you explicitly opt in.
  • GitHub. The REST API versions via an X-GitHub-Api-Version header rather than the URL path. The GraphQL API (v4) is a single /graphql endpoint and mandates Relay-style cursor pagination — edges { cursor node }, pageInfo { hasNextPage endCursor } — on every list field; there is no offset parameter to reach for.
  • Shopify, Slack, Twitter/X. All three explicitly deprecated or disallowed offset pagination on high-volume list endpoints in favor of opaque cursor tokens, precisely because of the scan-cost and consistency problems the console above demonstrates.
  • Meta (Facebook). Built GraphQL internally in 2012 to fix mobile over-fetching, open-sourced it in 2015 — and, in the same period, open-sourced DataLoader from the same team, because solving over-fetching on the wire reintroduced N+1 inside the resolver tree almost immediately. The two projects are a matched pair for a reason.
  • Payment platforms generally — Razorpay, PayPal, Adyen — converged on the identical idempotency-key contract as Stripe. When an entire industry with money on the line lands on the same pattern independently, that's a strong interview signal it's not optional.
  • Apollo Federation / GraphQL gateways at scale (Netflix, Airbnb-style architectures) split one graph across many backend services — and every subgraph still needs its own DataLoader instance per request, because batching that doesn't happen at the service boundary doesn't happen at all.

05 Hands-on: measure it yourself

Three real, runnable scripts — the resolver batching fix, the pagination cost curve, and an idempotency-key store. Nothing below is illustrative; every number was produced by the code directly above it.

n1_dataloader.py — the resolver execution model, made concrete

A GraphQL executor walks the query's AST and calls one resolve(parent, args, context, info) per field. For a list field like books, the executor resolves all five list items, then for each book independently resolves its author field — the executor has no built-in notion that five sibling resolvers are about to ask for overlapping data. That's resolve_books_naive below. resolve_books_batched is what DataLoader does under the hood: collect every key requested during the same tick, then fire one WHERE id IN (...) instead of N single-row lookups.

import sqlite3, time

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE authors (id INTEGER PRIMARY KEY, name TEXT)")
conn.execute("CREATE TABLE books (id INTEGER PRIMARY KEY, title TEXT, author_id INTEGER)")
conn.executemany("INSERT INTO authors VALUES (?, ?)", [
    (1, "Martin Kleppmann"), (2, "Alex Xu"), (3, "Susan Fowler"),
])
conn.executemany("INSERT INTO books VALUES (?, ?, ?)", [
    (1, "Designing Data-Intensive Applications", 1),
    (2, "System Design Interview Vol 1", 2),
    (3, "System Design Interview Vol 2", 2),
    (4, "Production-Ready Microservices", 3),
    (5, "Streaming Systems", 1),
])
conn.commit()

NETWORK_RTT = 0.002  # 2ms simulated round trip to a managed DB over the network
query_count = 0

def run_query(sql, params=()):
    global query_count
    query_count += 1
    time.sleep(NETWORK_RTT)          # every call pays one real round trip
    return conn.execute(sql, params).fetchall()

def resolve_books_naive():
    books = run_query("SELECT id, title, author_id FROM books")
    result = []
    for book_id, title, author_id in books:
        # a per-object resolver has no idea any sibling book needs the same author
        author_row = run_query("SELECT name FROM authors WHERE id = ?", (author_id,))
        result.append({"title": title, "author": author_row[0][0]})
    return result

def resolve_books_batched():
    books = run_query("SELECT id, title, author_id FROM books")
    author_ids = sorted({author_id for _, _, author_id in books})
    placeholders = ",".join("?" * len(author_ids))
    author_rows = run_query(
        f"SELECT id, name FROM authors WHERE id IN ({placeholders})", author_ids
    )
    by_id = {aid: name for aid, name in author_rows}
    return [{"title": title, "author": by_id[author_id]} for _, title, author_id in books]

for label, fn in [("naive N+1", resolve_books_naive), ("DataLoader batched", resolve_books_batched)]:
    query_count = 0
    t0 = time.perf_counter()
    rows = fn()
    elapsed = time.perf_counter() - t0
    print(f"{label:>20}: {query_count} DB round-trips, {elapsed*1000:6.1f} ms wall-clock, {len(rows)} books resolved")
output (actually run, CPython 3.10.12)
           naive N+1: 6 DB round-trips,   12.7 ms wall-clock, 5 books resolved
  DataLoader batched: 2 DB round-trips,    4.3 ms wall-clock, 5 books resolved

sanity check — both resolvers return identical data:
True

6 round trips vs. 2 doesn't sound dramatic at N=5. At N=500 it's 501 vs. roughly 2 — the naive resolver's cost is O(1 + N) round trips, the batched one is O(1 + ⌈N / max_batch_size⌉), independent of N in practice. A production DataLoader adds one more thing this snippet doesn't: per-request caching, so if two different fields in the same query both ask for author id 2, the second .load(2) is answered from the same in-flight batch for free.

pagination_bench.py — the cost curve behind the console
import sqlite3, time, statistics

N_ROWS, PAGE_SIZE = 500_000, 20
conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE events (id INTEGER PRIMARY KEY, payload TEXT)")
conn.executemany("INSERT INTO events (id, payload) VALUES (?, ?)",
                  ((i, f"payload-{i}") for i in range(1, N_ROWS + 1)))
conn.commit()

def time_it(fn, repeats=7):
    samples = [time.perf_counter() for _ in [0]]  # warm timer
    samples = []
    for _ in range(repeats):
        t0 = time.perf_counter()
        rows = fn()
        samples.append(time.perf_counter() - t0)
    return statistics.median(samples), len(rows)

def offset_page(offset):
    return conn.execute(
        "SELECT id, payload FROM events ORDER BY id LIMIT ? OFFSET ?",
        (PAGE_SIZE, offset)).fetchall()

def cursor_page(after_id):
    return conn.execute(
        "SELECT id, payload FROM events WHERE id > ? ORDER BY id LIMIT ?",
        (after_id, PAGE_SIZE)).fetchall()

for depth in [0, 10_000, 100_000, 250_000, 490_000]:
    t_offset, _ = time_it(lambda: offset_page(depth))
    t_cursor, _ = time_it(lambda: cursor_page(depth))
    print(f"{depth:>10,} rows in | OFFSET {t_offset*1000:6.3f} ms | CURSOR {t_cursor*1000:6.3f} ms")
output (actually run, CPython 3.10.12, SQLite 3.37.2)
         0 rows in | OFFSET  0.007 ms | CURSOR  0.007 ms
    10,000 rows in | OFFSET  0.071 ms | CURSOR  0.009 ms
   100,000 rows in | OFFSET  0.622 ms | CURSOR  0.007 ms
   250,000 rows in | OFFSET  1.543 ms | CURSOR  0.007 ms
   490,000 rows in | OFFSET  3.004 ms | CURSOR  0.007 ms

ratio at deepest page tested:
OFFSET 3.011 ms vs CURSOR 0.008 ms -> 355.7x slower

Notice what stays flat: CURSOR's time is indistinguishable from noise regardless of depth, because WHERE id > ? on an indexed column is a single B-tree seek — O(log n) to find the anchor, then O(limit) sequential reads. OFFSET has to materialize and discard every row before it in index order every single time; there is no index shortcut for "skip N rows," so it's O(offset + limit), and the console's insert-toggle shows the correctness bug on top of the performance one: shift the underlying rows between two offset-based page fetches and you duplicate or skip a record, silently.

idempotency.py — the exercise

Run this first, then extend it: right now IdempotencyStore keeps every key forever in a plain dict. Add expiry — keys should stop being honored 24 hours after they were first used — without doing an O(n) sweep over every stored key on each request. What data structure gets you there in-process (hint: you don't need to scan to expire), and what changes if the store is Redis instead of a Python dict?

import hashlib, json

class IdempotencyStore:
    def __init__(self):
        self._store = {}  # key -> (request_fingerprint, status_code, response_body)

    def _fingerprint(self, body: dict) -> str:
        return hashlib.sha256(json.dumps(body, sort_keys=True).encode()).hexdigest()

    def handle(self, key: str, body: dict, process_fn):
        fp = self._fingerprint(body)
        if key in self._store:
            cached_fp, status, response = self._store[key]
            if cached_fp != fp:
                return 422, {"error": "Idempotency-Key already used with a different request body"}
            return status, response          # replay — process_fn is NOT called again
        status, response = process_fn(body)
        self._store[key] = (fp, status, response)
        return status, response

charges_actually_processed = 0
def process_charge(body):
    global charges_actually_processed
    charges_actually_processed += 1
    return 200, {"charge_id": f"ch_{charges_actually_processed}", "amount": body["amount"]}

store = IdempotencyStore()
KEY, body = "req_9f8a2b", {"amount": 4999, "currency": "inr"}

r1 = store.handle(KEY, body, process_charge)                                   # first attempt
r2 = store.handle(KEY, body, process_charge)                                   # network retry, same body
r3 = store.handle(KEY, {"amount": 5999, "currency": "inr"}, process_charge)    # bug: same key, new body
print("charges actually processed:", charges_actually_processed)
output (actually run, CPython 3.10.12)
first attempt : (200, {'charge_id': 'ch_1', 'amount': 4999})
retry (same body)  : (200, {'charge_id': 'ch_1', 'amount': 4999})  <- cached replay, no new charge
retry (DIFFERENT body, same key): (422, {'error': 'Idempotency-Key already used with a different request body'})  <- rejected, not silently double-charged

charges actually processed: 1  (not 3)

One important precision point for the interview: POST is not idempotent by HTTP's own definition — PUT and DELETE are required to be by spec, POST never was. The Idempotency-Key header is an application-level convention layered on top by the API provider, not something the HTTP protocol gives you for free. Confusing the two is a fast way to lose points with a staff interviewer.

06 The senior/staff framing

What separates a strong answer from a weak one

  • Versioning — weak: "I'd add /v2 to the URL." Strong: "I'd evolve additively wherever possible — new fields, new optional params, @deprecated annotations with a sunset date — and reserve a hard version bump for the cases that genuinely can't be additive, like changing a field's type. Every version I ship is a route tree I have to keep alive; the real cost isn't writing v2, it's never being able to delete v1."
  • Pagination — weak: "LIMIT/OFFSET, it's simpler to implement." Strong: "Offset is fine for small, bounded, low-write lists — an admin table, a settings page. For anything large or high-write and user-facing, cursor pagination is the default: it's O(log n) instead of O(n) per page, and unlike offset it's correct under concurrent writes — no silently duplicated or skipped rows when something gets inserted mid-scroll."
  • Idempotency — weak: "Just make the POST endpoint idempotent." Strong: names that POST isn't idempotent by spec, and describes the actual mechanism — client-generated key, server-side fingerprint of the request body, cached response replay, conflict response (422/409) if the same key shows up with a different body.
  • N+1 — weak: "GraphQL is just slow." Strong: names the resolver-per-object execution model as the specific cause, DataLoader-style batching plus per-request caching as the fix, and volunteers that the identical bug exists in REST any time an ORM lazily loads a relation inside a loop — it's just less visible because REST rarely nests as deep as a GraphQL selection set does.

The sharpest follow-up an interviewer asks: "Your feed is sorted by a trending_score that updates every few minutes, not an immutable id. How do you build a stable cursor for that?" The honest answer is a composite cursor — (trending_score, id) as a tie-break so two rows never collide — and the admission that cursor pagination only guarantees no duplicates/skips when the sort key itself is stable during the scroll; a row can still shift out from under a slow client, and the right move is to document that trade-off rather than imply cursor pagination is unconditionally perfect.

08 Spaced recap

From lesson 02: the event loop is what makes batching possible

DataLoader's trick in section 05 isn't a library gimmick — it's a direct application of the event-loop mechanics from lesson 02. Every loader.load(key) call returns an unresolved future immediately and yields control without blocking. Because a synchronous GraphQL resolver never awaits mid-execution, every sibling resolver in that selection set gets to call .load() and register its key before the loop is idle enough to run the batch dispatch callback scheduled via call_soon — the exact same cooperative-yield-at-await boundary that made asyncio's concurrent I/O work in lesson 02's timeline. Miss that mechanic and DataLoader looks like magic instead of what it is: a callback that fires once per event-loop tick, collecting whatever accumulated during that tick.
