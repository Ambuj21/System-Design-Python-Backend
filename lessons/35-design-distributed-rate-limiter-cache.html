Design a Distributed Rate Limiter/Cache at Scale

The interview question isn't "build a rate limiter" — you already did that in Lesson 24. It's "now make that limit hold across 500 stateless app servers in three regions, without the limiter itself becoming the outage it was supposed to prevent."

01 The follow-up that turns Lesson 24 into a systems question

A candidate who's done the prep reaches for TokenBucket or SlidingWindowLog in the first minute, and that's the right instinct — for one process. The staff-level interviewer's next sentence is almost always some version of: "Good. Now this has to run identically on every one of your 500 app servers, enforcing one shared limit per API key, and half your fleet is on the other side of the planet from the other half." That single sentence deletes the answer you just gave. A 30-line class with a threading.Lock() only coordinates threads inside one interpreter — it has never heard of the other 499 processes about to import it.

Run this one like a real design interview, in order:

functional requirements
  • allow(api_key) -> bool, enforced as one logical limit no matter which of the fleet's nodes happens to receive the request
  • per-key configurable limits (free tier vs. paid tier vs. internal service)
  • the limiter must not become less available than the service it's protecting
non-functional requirements — this is where staff-level answers separate from mid-level ones
  • Latency budget is tiny. The check sits on every request's hot path. Low single-digit milliseconds added, not tens — this is the constraint that ends up mattering most, and most candidates never say it out loud.
  • The fleet itself isn't stable. It autoscales; the coordination story has to work whether there are 20 nodes or 500, without an operator retuning anything.
  • Exactness is negotiable — say so. Unlike a payments ledger, a rate limiter that admits 1,003 requests against a limit of 1,000 during a spike hasn't corrupted anything. Naming this out loud, unprompted, is the single biggest tell of a strong candidate versus a weak one.
capacity estimate (state every assumption out loud)

Assume 500 stateless app servers across 3 regions (say us-east, eu-west, ap-south), ~80,000 req/s aggregate traffic, and roughly 2,000,000 distinct active API keys in a given hour, each defaulting to 1,000 requests/minute (~16.7/s).

Check throughput first, because it's the wrong villain. If every one of those 80,000 req/s did a synchronous check against one central store, that's 80,000 ops/s against it. A single Redis instance's realistic ceiling for simple commands is on the order of 100K–1M ops/sec (single-threaded event loop, sub-millisecond per op — a well-known ballpark, not something benchmarked on this page). 80K/s isn't close to that ceiling. The store's CPU was never going to be the bottleneck.

Check latency next, because it is the real constraint. With one central store living in one region, roughly two-thirds of that traffic is now paying a cross-region round trip on every single request — commonly-cited ballparks put same-continent hops around 30–60ms and the longer intercontinental ones well past 100ms. If your whole request budget is 100–200ms, spending 120ms just to ask "am I allowed to proceed" is not a rounding error, it's most of the budget, gone before your handler even starts.

Check memory last, because it rules out an entire family of algorithms. 2,000,000 active keys, each potentially needing up to 1,000 entries if you used Lesson 24's exact SlidingWindowLog globally, at Lesson 24's own ballpark of ~80–100 bytes per logged timestamp (Redis sorted-set member overhead) → up to 2,000,000 × 1,000 × 90B ≈ 180GB for one data structure. That's not a scale-later problem, it's a wrong-data-structure problem, on day one. O(1)-per-key approximations (token bucket, sliding window counter) stop being an optimization at this scale and become close to mandatory.

Three numbers, three different conclusions — throughput is fine, latency-across-geography is the real limiter, and memory rules out exact per-request logs. All three of today's architectures are just different answers to "given that, where does the one source of truth live, and who has to travel to reach it?"

02 One shared quota, four different doors

Every node in the fleet needs to agree on the same number for the same key — without asking a stranger on the other side of the planet before every single decision. Consistent hashing (Lesson 26) is the trick that makes that tractable: it doesn't remove the need for a shared answer, it just guarantees every node asking about the same key always ends up asking the same shard.

That gap — same correctness question, wildly different cost depending on who's asking — is exactly what the console below lets you pressure-test, across three different ways of answering it.

Notice what centralized sync actually buys you: exactness, at the cost of a round trip on every single request. The lease hybrid buys back 75% of those round trips by only re-checking the shard once a node's local batch runs dry — and it's still exact, because the shard can never hand out more than it has. What it can't promise is that the twelve requests admitted are the "fairest" twelve possible; that's a separate property, with its own separate cost, covered in Section 06.

04 How this shows up in systems you already use

  • Kong API Gateway's rate-limiting plugin ships this exact fork as a literal config value: policy: local (each node keeps its own counter — architecture A, fast but not globally exact) versus policy: redis (one shared, centralized store — architecture B). Finding the precise tradeoff this lesson is built around spelled out as a documented checkbox in a mainstream gateway is the best confirmation it isn't an academic distinction.
  • Lyft's Envoy rate-limit service (ratelimit), widely reused across the service-mesh ecosystem, runs as a gRPC sidecar every proxy calls synchronously before forwarding a request — a production instance of architecture B, typically backed by a Redis layer that's itself sharded by key so no single instance becomes the throughput ceiling.
  • Google/YouTube's Doorman, open-sourced and described at USENIX ICAC 2015, is close to a reference implementation of architecture C: client libraries negotiate capacity leases from a set of coordinating servers, spend them locally, and renegotiate as their own demand shifts — the same borrow-and-spend mechanic the hands-on code below runs, at genuinely global scale.
  • Stripe's public engineering writeups describe a layered design: a fast, local, best-effort check first, backed by a Redis-based GCRA implementation (the same redis-cell-style mechanism named in Lesson 24) as the authoritative source of truth. A cheap local check in front of an expensive authoritative one is the same move this lesson's hybrid makes, arrived at independently.
  • DynamoDB's adaptive capacity is the same "hot shard" problem in a different costume: a table is partitioned by key exactly like a rate limiter's counters are sharded by key, and one popular partition key can pull far more traffic than its neighbors. DynamoDB's fix — isolating and reprovisioning the hot partition — and a rate limiter's fix for a hot key — batching harder or replicating just that one counter — are the same underlying move: absorb the imbalance, because sharding alone never fully prevents it.

05 Hands-on: build the shard, then race three strategies against it

Every number in Section 03's console and bar charts came from actually running this script — not hand-picked to make a point. It's a from-scratch consistent-hash ring (condensed from Lesson 26) plus one authoritative Shard, then three functions that hit that shard three different ways.

sharded_rl.py
"""
Distributed rate limiter: three coordination strategies compared.

Simulates one hot API key ("user:42") whose traffic arrives skewed across
a 4-node fleet (10 / 8 / 4 / 2 requests) against a single global window
limit of 12. All three architectures see the *identical* request stream --
only the coordination strategy changes.
"""

import hashlib


# ----------------------------------------------------------------------------
# Consistent-hash routing: which shard is authoritative for a given key.
# Same idea as Lesson 26's hash ring, condensed for this demo.
# ----------------------------------------------------------------------------
class HashRing:
    def __init__(self, shards, vnodes=100):
        self.ring = {}
        for shard in shards:
            for v in range(vnodes):
                h = self._hash(f"{shard}#{v}")
                self.ring[h] = shard
        self.sorted_points = sorted(self.ring)

    @staticmethod
    def _hash(s):
        return int(hashlib.md5(s.encode()).hexdigest(), 16)

    def get_shard(self, key):
        h = self._hash(key)
        for point in self.sorted_points:
            if h <= point:
                return self.ring[point]
        return self.ring[self.sorted_points[0]]


# ----------------------------------------------------------------------------
# The one authoritative counter for a key's window. Only this object is
# allowed to say yes -- everything else is a client of it.
# ----------------------------------------------------------------------------
class Shard:
    def __init__(self, limit):
        self.remaining = limit

    def take(self, amount):
        granted = min(amount, self.remaining)
        self.remaining -= granted
        return granted


def build_arrival_order(node_counts):
    """Round-robin the fleet: at each tick, every node with requests left
    sends one. Produces the merged, time-ordered stream the shard actually
    sees."""
    order = []
    remaining = dict(node_counts)
    while any(remaining.values()):
        for node in node_counts:
            if remaining[node] > 0:
                order.append(node)
                remaining[node] -= 1
    return order


# ----------------------------------------------------------------------------
# A) No coordination: each node runs its own full-capacity local bucket.
# ----------------------------------------------------------------------------
def run_local_only(node_counts, global_limit):
    admitted = {}
    for node, count in node_counts.items():
        admitted[node] = min(count, global_limit)   # misconfig: full L, per node
    return admitted, 0


# ----------------------------------------------------------------------------
# B) Centralized: every single request pays a synchronous round trip to
#    the one authoritative shard.
# ----------------------------------------------------------------------------
def run_centralized(arrival_order, global_limit):
    shard = Shard(global_limit)
    nodes = list(dict.fromkeys(arrival_order))
    admitted = {n: 0 for n in nodes}
    rejected = {n: 0 for n in nodes}
    rtts = 0
    for node in arrival_order:
        rtts += 1
        if shard.take(1) == 1:
            admitted[node] += 1
        else:
            rejected[node] += 1
    return admitted, rejected, rtts


# ----------------------------------------------------------------------------
# C) Sharded + lease hybrid: a node borrows a batch of tokens from the
#    shard and spends them locally; it only calls the shard again once its
#    lease is empty. Sum of granted leases can never exceed global_limit,
#    so this can never over-admit -- the cost it pays instead is far fewer
#    round trips, at the risk of short-term unfairness under skew.
# ----------------------------------------------------------------------------
def run_lease_hybrid(arrival_order, global_limit, lease_size=4):
    shard = Shard(global_limit)
    nodes = list(dict.fromkeys(arrival_order))
    local_lease = {n: 0 for n in nodes}
    known_empty = {n: False for n in nodes}
    admitted = {n: 0 for n in nodes}
    rejected = {n: 0 for n in nodes}
    rtts = 0
    for node in arrival_order:
        if local_lease[node] == 0:
            if known_empty[node]:
                rejected[node] += 1          # served from local cache, 0 RTT
                continue
            rtts += 1
            granted = shard.take(lease_size)
            local_lease[node] = granted
            if granted == 0:
                known_empty[node] = True
                rejected[node] += 1
                continue
        local_lease[node] -= 1
        admitted[node] += 1
    return admitted, rejected, rtts

Notice Shard.take() is the only place a decision is ever made. Everything else in this file is a client of it, deciding when to call it, not whether its answer is correct — the same separation of concerns as Lesson 24's classes, just relocated onto something network-addressable.

Read the last row carefully — it's the most interesting one. At lease_size=12 (equal to the whole global limit), N1 is first in line, asks for a lease, and the shard hands over the entire budget in one grant. But N1 only has 10 requests total — it uses 10 of its 12 borrowed tokens and the other 2 are simply stranded in a lease nobody spends, while N2, N3, and N4 get shut out entirely. Total admitted drops to 10, under the target of 12. This lease design never over-admits past the global limit — the shard physically cannot hand out tokens it doesn't have — but a lease size that's too large relative to real per-node demand quietly under-utilizes the budget instead. That's the real tuning knob: too small and you're paying near-per-request round trips again; too large and you strand capacity in leases that never get spent.

06 The senior/staff framing

What separates a strong answer from a weak one

  • Weak: "I'd put the counters in Redis and check them on every request." Strong: "The store's raw ops/sec is rarely the actual constraint — a single instance handles hundreds of thousands of ops a second. What breaks is the round trip: at fleet-and-multi-region scale, a synchronous check adds real, user-facing latency, and a meaningful slice of the fleet isn't even in the store's region. So I'd shard the store by key with consistent hashing to bound any one shard's load, and put a local, lease-based cache in front of it — accepting a slightly softer consistency guarantee to keep the limiter's own latency off the critical path. This is a PACELC 'else' branch in the wild, Lesson 15's framework showing up with no partition anywhere in sight: even when everything is healthy and reachable, you're trading consistency for latency on every single check, on purpose, because exact-every-time costs more milliseconds than the traffic pattern can afford."
  • The killer follow-up: "One API key just went viral, and its shard is now taking more traffic than most of your other shards combined. What do you do?" This is the exact same hot-partition problem from Lesson 14, wearing a rate-limiter costume — and consistent hashing doesn't solve it, it only bounds the blast radius to that one shard's other keys instead of the whole system. The real levers: dynamically widen that one key's lease size once it's detected as hot (fewer round trips exactly where they're expensive); or replicate that single counter across several shards, each enforcing a fraction of the limit, accepting a small bounded slop on that one key in exchange for spreading its load. Adding more virtual nodes redistributes future key placement — it does nothing for a key that's already hot on the shard it landed on.
  • Worth naming unprompted: fail-open vs. fail-closed when the shard itself is unreachable. Fail-closed rejects everything until the limiter recovers — which quietly turns a rate-limiter outage into a full outage of the thing it was protecting. Fail-open admits everything during the outage instead — protection lapses exactly when you can't verify it's needed, but the service stays up. For a rate limiter specifically (unlike, say, an auth check), fail-open is very often the right default, and saying so unprompted is a strong signal.
  • Know that sharding the store and caching locally solve two different problems: sharding spreads aggregate ops/sec across many machines; local leasing cuts the number of round trips any one node pays. A system at real scale generally needs both — don't let "so you sharded it, problem solved?" pass unchallenged.

08 Spaced recap

Resurfacing Lesson 24 — Build a Rate Limiter in Python

Lesson 24 built TokenBucket and SlidingWindowLog as single-process Python classes guarded by one threading.Lock() — correct, but only inside one interpreter's memory. Today's Shard is that exact same idea relocated onto a server every node in the fleet calls into: the counter is still just a couple of numbers, take() is still one check-then-decrement operation, and it still has to be atomic or the same over-admission bug Lesson 24's 50-thread concurrency test caught reappears — except now the "threads" are entire machines, and a Python Lock() can't reach across a network to stop them. Every architecture in this lesson is really just answering the one question Lesson 24 never had to: where does that single atomic operation live, and who has to travel to reach it?
