Redis Caching Patterns

Three different contracts for keeping a cache and a database honest, three failure modes that only show up under real production traffic, and the one mistake — the cache stampede — that has taken down real databases the instant a single popular key expired.

01 Why this is an interview trap

"We put Redis in front of it" is one of the most common sentences in a system-design interview, and also one of the most under-specified. Which pattern? Who writes to the cache, and when? What happens to the 4,000 requests that arrive in the same 50ms while the one key everyone wants is being recomputed? A candidate who says "cache-aside with a TTL" without being able to draw the exact read and write path, and without being asked to defend it against a stampede, is giving a mid-level answer wearing a senior vocabulary.

The three patterns — cache-aside, write-through, write-behind — aren't interchangeable implementation details. They trade latency for durability in genuinely different amounts, and picking the wrong one is the kind of mistake that survives code review, survives staging, and only shows up as a 2am page when a cache node dies mid-flight holding writes nobody else has seen.

The console below runs real traces of all three patterns' read and write paths, a real simulation of a cache stampede with four different mitigations, and a real eviction-policy trace showing LRU and LFU disagreeing about what to throw away. The hands-on section runs actual Python — real threads, a real lock, real measured wall-clock numbers — not illustrations.

02 Who's allowed to talk to the database

Cache-aside is the foundation the other two patterns are defined against. Its defining property: the cache has no idea the database exists. There is no automatic path from DB to cache — the application is the only thing that ever populates it.

That's the entire mechanism. Everything below — write-through, write-behind, and every stampede mitigation — is a variation on who is responsible for keeping the cache and the database in agreement, and how synchronously they do it.

04 How this shows up in systems you already use

  • Facebook's memcache tier (the "Scaling Memcache at Facebook" paper, NSDI 2013) is the canonical cache-aside deployment at extreme scale, and it's also where the industry's two most-cited stampede fixes came from: leases (a mutex token memcached hands the first miss and rejects to everyone else) and the probabilistic early-recomputation algorithm this lesson calls "early refresh," published separately as Vattani, Chierichetti & Löwenstein, "Optimal Probabilistic Cache Stampede Prevention," VLDB 2015 — the XFetch algorithm.
  • nginx's proxy_cache_lock and Varnish's grace mode implement request coalescing and stale-while-revalidate respectively as first-class reverse-proxy directives — the same two mitigations in the console above, running in front of origin servers billions of times a day. Cache-Control: stale-while-revalidate is this pattern standardized into HTTP itself.
  • CPU cache write policies are the literal namesake. L1/L2 hardware caches implement both write-through (every store also hits main memory, simple, slow) and write-back/write-behind (dirty cache lines flush later via an eviction or explicit flush) — the same tradeoff, one level lower in the stack, decades before Redis existed.
  • InnoDB's buffer pool defaults to write-back, exactly like write-behind — dirty pages sit in memory and flush later — but it's safe because the redo log (WAL) durably records every write before it's acknowledged. That's the missing piece naive write-behind caches skip: write-behind without a durable queue in front of the flush is where data actually gets lost; write-behind with one (Kafka, a WAL, Redis AOF) is just deferred, not risky.
  • Redis's own maxmemory-policy exposes the eviction choice directly: noeviction (the default — reject writes rather than silently drop data), allkeys-lru, allkeys-lfu, allkeys-random, and volatile-* variants of each that only ever evict keys carrying an explicit TTL, leaving permanent keys untouched. The Linux page cache and most CDN edge caches (CloudFront, Fastly) make the same approximate-LRU tradeoff for the same reason: exact LRU bookkeeping across millions of entries costs more memory than the cache is trying to save.

05 Hands-on: measure it yourself

This runs against a simulated cache and DB (a dict plus time.sleep standing in for network latency — no live Redis or Postgres server in this sandbox) but every number below is a real measurement of real Python execution: real threading.Thread objects, a real threading.Lock, real race conditions. The mechanics — how many threads actually reach the database, whether a lock serializes them — are identical to what happens against live Redis and Postgres.

cache_patterns.py — parts 1 & 2: read and write latency
DB_LATENCY = 0.010      # 10ms  ~ an indexed Postgres SELECT over a LAN
CACHE_LATENCY = 0.0003  # 0.3ms ~ a local Redis round trip

class FakeDB:
    def __init__(self, latency=DB_LATENCY):
        self.latency = latency
        self.data = {"user:42": {"id": 42, "name": "Ada"}}
        self.calls = 0
        self._guard = threading.Lock()

    def query(self, key):
        with self._guard:
            self.calls += 1
        time.sleep(self.latency)
        return self.data.get(key)

    def write(self, key, value):
        with self._guard:
            self.calls += 1
        time.sleep(self.latency)
        self.data[key] = value

class FakeCache:
    def __init__(self):
        self.store, self.expiry = {}, {}
    def get(self, key):
        time.sleep(CACHE_LATENCY)
        if key in self.store and time.time() < self.expiry.get(key, 0):
            return self.store[key]
        return None
    def set(self, key, value, ex):
        time.sleep(CACHE_LATENCY)
        self.store[key] = value
        self.expiry[key] = time.time() + ex

def cache_aside_read(cache, db, key):
    val = cache.get(key)
    if val is not None:
        return val, "HIT"
    val = db.query(key)
    cache.set(key, val, ex=5)
    return val, "MISS"

def write_through(cache, db, key, value):
    cache.set(key, value, ex=5)
    db.write(key, value)          # synchronous — blocks until DB commits
    return "durable"

def write_behind(cache, db, key, value, flush_queue):
    cache.set(key, value, ex=5)
    flush_queue.append((key, value))   # enqueued; request returns now
    return "acked"

part 3: stampede — no protection vs mutex lock (SET key val NX PX 5000)
def naive_get_or_load(cache, db, key, results, idx):
    val = cache.get(key)
    if val is not None:
        results[idx] = "HIT"; return
    val = db.query(key)              # every racing thread pays this
    cache.set(key, val, ex=5)
    results[idx] = "MISS->DB"

_locks, _locks_guard = {}, threading.Lock()

def mutex_get_or_load(cache, db, key, results, idx):
    val = cache.get(key)
    if val is not None:
        results[idx] = "HIT"; return
    with _locks_guard:
        lock = _locks.setdefault(key, threading.Lock())
    if lock.acquire(blocking=False):
        try:
            val = cache.get(key)          # double-check: winner might be done
            if val is not None:
                results[idx] = "HIT(after-wait)"; return
            val = db.query(key)           # exactly one thread reaches this line
            cache.set(key, val, ex=5)
            results[idx] = "MISS->DB(winner)"
        finally:
            lock.release()
    else:
        while True:                       # equivalent of losing the SET...NX race
            time.sleep(0.0005)
            val = cache.get(key)
            if val is not None:
                results[idx] = "HIT(after-wait)"; return

Six identical threads, one expired key, zero protection: six full database queries at once. Add one threading.Lock playing the role of Redis's SET key val NX PX 5000, and it's one — the other five simply wait for the winner's result. That's the entire stampede fix in eight lines.

bonus: the eviction console above, verified against a real O(1) LRU cache
from collections import OrderedDict

class LRUCache:
    def __init__(self, capacity):
        self.capacity = capacity
        self.store = OrderedDict()      # insertion/access order IS recency order

    def get(self, key):
        if key not in self.store:
            return None
        self.store.move_to_end(key)     # O(1): mark as most-recently-used
        return self.store[key]

    def put(self, key, value):
        if key in self.store:
            self.store.move_to_end(key)
        self.store[key] = value
        if len(self.store) > self.capacity:
            evicted, _ = self.store.popitem(last=False)   # O(1): drop LRU
            print(f"  evicted: {evicted}")

c = LRUCache(3)
for k in ["A","A","A","A","B","C","D"]:
    if c.get(k) is None:
        c.put(k, k)
    print(f"access {k}: cache = {list(c.store.keys())}")
access A: cache = ['A']
access A: cache = ['A']
access A: cache = ['A']
access A: cache = ['A']
access B: cache = ['A', 'B']
access C: cache = ['A', 'B', 'C']
  evicted: A
access D: cache = ['B', 'C', 'D']

Real OrderedDict, real O(1) move_to_end/popitem, and it evicts A — the exact same key the LRU tab of the console evicts, and for the exact same reason: A was accessed four times, more than B or C, but not recently. LRU only remembers "when," never "how often."

The exercise — predict before you check: the mutex code above has no lock timeout. If the winning thread crashes after acquiring the lock but before calling cache.set(...), what happens to the other five threads? Now add a TTL to the lock (mirroring Redis's mandatory PX on SET...NX) so a crashed winner can't hold it forever — what failure mode does that TTL trade in return, and how would you size it?

06 The senior/staff framing

What separates a strong answer from a weak one

  • Weak: "I'd just cache it with a TTL." Strong: "Cache-aside for most read-heavy paths — it degrades gracefully, a dead cache just means every read falls through to the DB. Write-through when the cache and DB can never be allowed to disagree, even briefly, and I can afford the write-latency cost. Write-behind when write throughput matters more than the durability window — but only with a durable queue (WAL, Kafka, AOF) in front of the flush, never a bare in-memory list."
  • The killer follow-up: "You added a mutex lock to stop the stampede. What happens to the five waiting clients if the winner crashes mid-query, still holding the lock?" Without a TTL on the lock, they wait forever — you've traded a stampede for a deadlock. SET key val NX PX 5000's PX isn't optional; it's the only thing that bounds the outage when the winner dies mid-flight.
  • The fix worth naming, for TTL-bound locks: losers need randomized backoff on their retry/poll loop, not a tight spin — six threads busy-polling every 0.1ms is its own small thundering herd against the cache itself.
  • Know the durability axis, not just the latency one: cache-aside never risks data loss (DB is always truth); write-through risks nothing either but pays full DB latency on every write; write-behind is the fastest and the only one of the three that can silently lose an acknowledged write if the cache dies before flushing.

08 Spaced recap

Resurfacing lesson 01 — the GIL & the concurrency model

Lesson 01 spent most of its time on one idea: CPython's GIL means only one thread ever executes bytecode at once, so anything that happens between two bytecode instructions can't be torn by a second thread — no extra locking required. Redis's own single-threaded command loop is that same guarantee, taken further: one thread executing the entire server, not just the interpreter. That's exactly why the mutex mitigation above works as a single command, SET key val NX PX 5000 — Redis never interleaves two clients' commands, so "check if it exists, then set it" is atomic for free, with no compare-and-swap loop and no separate lock manager. The same single-execution-context trick that made Python's own data structures safe under the GIL is what makes Redis usable as a distributed mutex in the first place.
